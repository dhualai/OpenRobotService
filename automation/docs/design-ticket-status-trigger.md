# 工单状态触发自动化测试设计（候选）

> 状态：设计稿，待人工确认
> 日期：2026-09-14
> 背景：原计划按 GitHub 代码提交触发，但提交到生产部署窗口只有数小时；调整为以工单为触发对象。

## 1. 目标

把自动化测试触发点从“代码提交”调整为“工单业务状态”：

```text
工单新建
-> 开发/部署进入 in_progress
-> 工单变为 resolved
-> 触发自动化测试
-> 生成 Allure 报告
-> 结果回写工单
-> 通过后允许 test -> dev
```

核心目标是让自动化测试跟业务工单绑定，而不是跟一次 Git commit 绑定。

## 2. 需要先确认的语义

### 2.1 工单是“触发单”还是“用例实例”？

建议区分：

1. **触发单**：只承载测试条件，例如套件、环境、版本、项目。
2. **用例实例**：业务链路用例运行时创建的真实测试工单。

如果不区分，自动化自己创建的工单在变成 `resolved` 时会再次触发测试，形成递归。

### 2.2 `resolved` 的语义

建议把 `resolved` 定义为“候选版本已部署到测试环境，等待自动化验证”，而不是“人工已经验收完成”。

推荐门禁：

```text
resolved
-> 自动触发测试
-> 测试通过：允许 test -> dev
-> 测试失败：回到 in_progress 或打回
```

如果 `resolved` 已经是“全部人工完成”，自动化会在窗口期之后才触发，失去门禁价值。

## 3. 推荐架构

第一版不依赖后端改代码，采用轮询触发；后端事件化作为二期。

### 3.1 一期：轮询触发

```text
测试环境工单表/API
        |
        | 每 30-60 秒扫描一次
        v
触发器服务（本地脚本 / 测试服务器定时任务 / GitHub schedule）
        |
        | 发现 resolved 的 AUTO-TRIGGER 工单
        v
调用测试运行入口
        |
        v
pytest 套件 -> Allure 报告 -> 回写工单
```

优点：

- 不需要马上修改后端业务代码。
- 能利用现有工单状态和 API。
- 可以先验证业务价值和报告形态。

缺点：

- 有最多一个轮询周期的延迟。
- 需要自己维护扫描游标和幂等。

### 3.2 二期：后端事件化

后端在 `update_ticket_status` 成功变为 `resolved` 后，发布一条事件：

```json
{
  "event": "ticket.resolved",
  "ticket_id": 123,
  "project_id": "Leo_test",
  "automation": {
    "enabled": true,
    "suite": "call_to_ticket_close",
    "env": "test",
    "version": "sha-or-tag"
  },
  "resolved_at": "2026-09-14T10:00:00+08:00"
}
```

事件通道可复用：

- Redis Pub/Sub 或 Stream
- MQTT
- 后端 outbox 表 + 触发器轮询
- HTTP Webhook

推荐 outbox 表，避免状态提交成功但事件丢失。

## 4. 触发工单契约

只有满足以下条件的工单才允许触发自动化：

- 项目：`Leo_test` 或专用测试项目
- 状态：`resolved`
- `metadata_info.automation.enabled = true`
- 工单不是自动化自己创建的被测工单

建议 metadata：

```json
{
  "automation": {
    "enabled": true,
    "suite": "call_to_ticket_close",
    "env": "test",
    "version": "test-20260914-01",
    "source_commit": "abc1234",
    "trigger": "resolved",
    "run_id": null,
    "last_resolved_at": null
  }
}
```

推荐标题规范：

```text
[AUTO-TRIGGER] 摇人问答提单到关闭
```

## 5. 触发和运行流程

1. 创建触发工单，记录套件、环境、版本和 commit。
2. 代码部署到测试环境，工单进入 `in_progress`。
3. 工单变为 `resolved`。
4. 触发器发现新 resolved 工单。
5. 生成幂等键：

```text
ticket_id + resolved_at + suite
```

6. 触发对应测试运行入口。
7. 测试执行，生成 Allure 结果和 HTML 报告。
8. 报告链接和摘要回写工单。
9. 更新 metadata 的 `run_id` 和 `last_resolved_at`，防止重复触发。

## 6. 测试范围选择

触发器按工单 metadata 选择套件：

| suite | 内容 |
|---|---|
| `access_smoke` | 健康检查、账号登录、测试环境连通性 |
| `call_to_ticket_close` | 摇人问答到工单关闭完整链路 |
| `ticket_lifecycle` | 提单、派单、处理、解决、关闭 |
| `full_api` | 全部单接口 Mock/real-safe 用例 |

第一版建议只支持显式配置，不做自动推断。

## 7. 运行入口选择

有三种可选方式：

1. **内部自动化服务**
   - 最推荐。
   - 触发器直接调用 pytest runner。
   - 适合测试环境内网、无需 GitHub token。

2. **GitHub repository_dispatch**
   - 触发器调用 GitHub API，workflow 接收 ticket payload。
   - 需要 workflow 在默认分支上存在。
   - 需要 GitHub token 和网络访问。

3. **自托管 runner**
   - workflow 在测试环境同网 runner 上运行。
   - 不依赖 SSH 隧道，但需要维护 runner。

## 8. 报告回写

建议工单中回写：

- Allure HTML 链接
- 总用例数、通过、失败、跳过
- 运行耗时
- 失败摘要前 N 条
- 本次测试版本/commit

如果失败，可选择：

- 仅评论告警，不自动改状态
- 自动回退到 `in_progress`
- 新增“自动化验证失败”标签

第一版建议只评论，不自动改状态，避免误操作。

## 9. 防递归和幂等

必须满足：

- 自动化创建的测试工单不能触发自动化。
- 同一个 `ticket_id + resolved_at` 只能触发一次。
- 重复扫描不会重复起任务。
- 测试失败后重新 resolved 可生成新的运行。
- 触发器重启后能从持久化游标恢复。

建议触发器状态存储：

```json
{
  "last_seen_updated_at": "2026-09-14T10:00:00+08:00",
  "processed_keys": ["123:2026-09-14T10:00:00+08:00:call_to_ticket_close"]
}
```

## 10. 版本和部署窗口

触发工单应记录：

- `source_commit`：代码版本
- `test_version`：测试环境部署版本
- `resolved_at`：进入待验证状态时间

测试运行前先验证：

- 测试环境版本 == 工单要求版本
- commit 在测试分支中可追溯
- 如果版本不一致，报告标记“版本不匹配”并停止测试

## 11. 安全边界

- 触发工单只允许出现在测试项目。
- `dev`/生产环境不执行会创建业务数据的测试。
- 触发服务使用只读工单权限 + 最小测试执行权限。
- 报告链接不得包含 secrets。
- 触发器账号与业务账号隔离。

## 12. 实施阶段

### 阶段一：设计确认

- 确认 `resolved` 语义。
- 确认触发单和被测工单的区分。
- 确认版本来源和测试运行位置。

### 阶段二：轮询触发器

- 扫描测试环境 resolved 工单。
- 识别 `automation.enabled`。
- 去重并调用本地 runner。

### 阶段三：链路执行和回写

- 执行 `call_to_ticket_close` / `ticket_lifecycle`。
- 生成 Allure 报告。
- 回写工单评论和 metadata。

### 阶段四：事件化

- 后端在状态变更事务内写 outbox。
- 触发器改为消费事件。
- 轮询作为兜底保留。

## 13. 待确认问题

1. `resolved` 表示“开发已解决”还是“待自动化验证”？
2. 用普通工单，还是新增专用 `AUTO-TRIGGER` 类型/标签？
3. 测试版本以工单关联 commit、test 分支，还是测试环境部署版本为准？
4. 自动化失败是否阻止 `test -> dev`？
5. 第一版能否接受 30-60 秒轮询延迟？
6. 运行入口选内部服务、GitHub repository_dispatch，还是自托管 runner？
7. 报告是否必须回写工单？失败是否自动改状态？
8. 如何排除自动化自己创建的工单，避免递归？

## 14. 推荐结论

第一版建议：

```text
专用 AUTO-TRIGGER 工单
+ resolved 状态触发
+ 轮询扫描
+ 本地/测试环境 runner
+ Allure 报告回写工单
+ 不自动改状态，只评论告警
```

第二版再切换为后端事件驱动，轮询作为兜底。

## 15. 变体：扫描生产工单，测试环境执行

### 15.1 是否可行

可行，但它是“生产事件驱动的回归测试”，不是生产环境验证。  
生产工单只负责提供触发信号和测试上下文，实际 pytest 仍在测试环境运行。

建议流程：

```text
生产环境新建工单
-> 只读扫描并登记候选工单
-> 工单变为 resolved
-> 按工单上下文选择测试套件和测试版本
-> 在测试环境执行 pytest + Allure
-> 报告回写生产工单或内部看板
```

### 15.2 两个阶段

1. **新建阶段**
   - 只登记候选工单，不立即执行测试。
   - 捕获项目、模块、类型、关联版本、关联 commit、标签等上下文。
   - 如果工单缺少必要字段，标记为“不可触发”，等待人工补充。
2. **resolved 阶段**
   - 只对已登记候选执行。
   - 生成幂等键：`ticket_id + resolved_at + suite`。
   - 触发测试环境 runner。

### 15.3 生产扫描边界

- 必须只读访问，优先走只读 API、只读从库或数据导出，不直接连接生产主库。
- 只读取必要字段：
  - `id`
  - `title`
  - `ticket_type`
  - `project_id`
  - `status`
  - `resolved_at`
  - `labels` / `metadata`
  - `source_commit` / `version`
- 不读取或落盘客户隐私、附件、聊天明细等敏感数据。
- 扫描账号使用最小权限，不能修改生产工单。

### 15.4 过滤条件

不能对生产环境所有 resolved 工单都触发测试。建议至少满足：

- 生产项目固定为 `001` / `摇人吧服务号`。
- 项目在允许列表内。
- 工单类型在允许列表内。
- 带 `automation.enabled=true` 或专用标签。
- 不是自动化或其他机器人创建。
- 关联版本或 commit 可解析。

否则只登记，不执行，并在内部看板标记跳过原因。

### 15.5 工单到测试的映射

建议第一期使用显式映射，不做自动推断：

项目映射：

| 来源 | 项目 |
|---|---|
| 生产触发项目 | `001` / `摇人吧服务号` |
| 测试执行项目 | `Leo_test` / `摇人吧服务号-测试` |

测试工单只在测试项目 `Leo_test` 中创建，不能直接写入生产项目。

| 工单信息 | 测试套件 |
|---|---|
| 模块=我要摇人，类型=problem/bug | `call_to_ticket_close` |
| 模块=系统任务 | `ticket_lifecycle` |
| 模块未知 | `access_smoke` 或跳过 |

测试版本优先级：

1. 工单关联的 `source_commit`
2. 工单关联的 `test_version`
3. 测试环境当前部署版本

如果测试环境版本与工单要求版本不一致，报告标记“版本不匹配”，不能把结果当成该生产工单的验证结论。

### 15.6 结果回写

如果允许写生产工单，建议只新增评论：

- Allure 报告链接
- 通过/失败/跳过数量
- 失败摘要
- 测试环境版本和 source commit

不建议自动修改生产工单状态。写权限不允许时，结果只进内部看板，按 `ticket_id` 关联。

### 15.7 主要风险

- 生产工单数量多，若无过滤会产生大量无关测试。
- 工单缺少模块、版本或 commit，无法选择正确套件。
- 测试环境版本不等于生产版本，测试结果可能不能代表该工单修复。
- 生产工单只读权限和隐私合规需要安全团队确认。
- 如果扫描延迟过长，测试可能在窗口期之后才运行。

### 15.8 推荐结论

第一版可以采用：

```text
生产工单只读扫描
+ 新建时登记候选
+ resolved 时触发
+ 显式套件/版本映射
+ 测试环境内部 runner 执行
+ 结果回写评论或内部看板
```

但当生产工单缺少版本映射时，必须跳过或降级为 smoke，不能默认对全部工单跑完整链路。
