# 自动化测试框架重构：业务链路化需求与待确认清单

> 状态：链路规范已 review 通过；U1/U2 已创建；CI 安全边界与端口转发密钥已加固；可控回复与清理配置待确认后实施
> 日期：2026-09-04
> 范围：仅需求对齐，尚未编写测试代码或修改框架代码

## 1. 背景

当前自动化测试用例主要按接口/模块组织，报告里每个用例展示的是接口和断言，看不出它对应什么用户操作、验证什么业务。本次重构希望把测试视角从“接口用例”提升为“业务链路”，并让自动化测试能在 GitHub 提交后自动运行并立即给出报告。

## 2. 核心目标

1. 自动化测试框架能识别 GitHub 代码提交，自动运行对应自动化测试，并立即给出测试报告。
2. 测试用例按真实业务链路组织，而不是按单个接口平铺。
3. 报告主视角是业务链路，每一步清楚展示中文操作、角色、接口调用和业务状态，让不写代码的人也能判断业务链路是否通过。

## 3. 已确认的决策

| 主题 | 结论 |
|------|------|
| 链路来源 | 先从 `frontend/` 和接口实现中梳理真实调用顺序，再提炼成“业务链路规范” |
| 链路确认 | 规范由人 review 和确认，确认后的规范作为测试框架的执行源头 |
| 第一版 CI 范围 | 只自动跑“摇人问答到工单关闭”这一条真实后端业务链路 |
| 底层接口用例 | 保留，作为底层执行层，暂不进 CI；不承担报告主视角 |
| 触发边界 | PR 仅跑 Mock/无 secret 测试；真实后端链路仅允许 `push` 到 `develop` 和 `workflow_dispatch` |
| 运行目标 | 真实后端环境 |
| 问答控制 | 固定问题 + 预设/可控回复，先验证业务流程；AI 质量验证后续再做 |
| 链路角色 | U1：提问、补充信息、确认提单，并在已解决后确认关闭；U2：接收、处理并提交已解决 |
| 测试账号 | `u1_auto` / `自动化提单用户`，`u2_auto` / `自动化处理人`；已在测试环境创建并验证登录 |
| 工单类型 | 第一版使用 `problem`，3 阶段：初步诊断 / 临时解决 / 最终解决 |
| CI 访问方式 | GitHub Actions 使用专用 SSH key 建立端口转发；key 仅允许访问 `127.0.0.1:9400`，不能执行远程命令 |
| 报告输出 | GitHub Actions 产出 Allure HTML 报告链接，并评论到对应 commit/PR |
| 报告层级 | 按业务链路聚合，每一步显示中文操作、角色、接口、状态和通过结果 |
| 数据清理 | 跑完后自动清理测试工单；清理失败时在报告明确告警并保留待人工处理 |

## 4. 试点业务链路

试点链路暂定如下：

1. 提单用户进入“摇人”模块，进行问答。
2. AI 在固定问题与预设回复控制下完成信息收集，前端发起提单。
3. 系统创建工单，进入对应业务状态。
4. 处理人接收工单，并按 `problem` 的 3 个阶段推进处理。
5. 处理人提交已解决。
6. 提单用户确认关闭工单。
7. 测试结束后自动清理本次链路产生的测试数据。

链路规范应以中文业务动作为主线，并保留每个动作对应的接口、角色、请求要点、业务状态和预期结果，供人 review。

### 5.3 数据隔离与清理

- 清理范围是否包含通知记录、派单记录、统计数据、文件附件等关联数据？
- 清理失败后的人工处理流程由谁负责？

## 7. GitHub 现有框架调研结论

> 日期：2026-09-09
> 结论：GitHub 上没有能整套搬走的“前端业务链路 + 真实后端双账号 + 工单闭环 + Allure 评论 commit”现成成品；现有 `automation/` 框架与主流开源 API 自动化框架同构，建议按层借用，不整套替换。

### 7.1 候选仓库与可借层

| 项目 | 定位 | 建议 |
|---|---|---|
| `pytest-dev/pytest-bdd` | Gherkin/BDD 场景，步骤由 pytest 实现 | 可借“业务链路可读描述”语法，不迁移整套用例 |
| `taverntesting/tavern` | YAML 编写多步 REST API，接 pytest/Allure | 可借多步骤编排写法，不解决双账号协作、SSE、可控回复 |
| `Hellen-Zhu/python-api-test` | 数据驱动企业级 API 框架，请求/响应/断言/变量提取均进入 Allure 步骤 | 可借“报告按业务步骤细化”的报告模型 |
| `pytest-auto-api2`、`fqhd-1003/PytestAutoApi` | YAML/Excel 用例 + 多环境/多角色 + 参数关联 + 数据库断言 | 可借双角色 fixture、token 切换与参数关联经验 |
| `chenhaijun02/ApiTesting` | 抓包/导入请求生成全链路接口用例 | 可借链路生成思路 |
| `LunarLink`、`apigobetween` | 流量录制，页面操作转接口调用链/用例 | 可借“页面操作倒推接口链路”的采集思路 |
| `allure-framework/allure-action` | GitHub Action，生成 Allure 摘要并评论 PR | 可直接用于报告评论；现有 `test.yml` 已有 Pages 发布 |

### 7.2 建议选型

1. 保留现有 `pytest + _api() + Allure` 作为执行底座。
2. 借 `Hellen-Zhu/python-api-test` 的报告模型：每个 Allure step 展示“角色 + 中文操作 + 接口 + 业务状态 + 断言结果”。
3. 借 `pytest-bdd` 场景语法或定义“链路剧本 YAML/JSON”，将业务链路规范翻译为多个 `_api()` 步骤。
4. GitHub Actions 补齐：`push develop` / `workflow_dispatch` → 跑真实后端业务链路 → 生成 Allure HTML → 评论到 commit/PR 并给出报告链接；PR 仅跑 Mock/无 secret 测试。
5. 不整套替换为 `Tavern`、`Robot Framework` 或 `HttpRunner`，避免迁移现有 Excel 用例、Mock、生成器与报告历史。

### 7.3 待确认点

- 业务链路采用 `pytest-bdd` 的 `.feature` 文件，还是内部“链路剧本 YAML/JSON”。
- 双角色 token 管理是否直接复用现有 `src/clients`，还是新增会话切换层。
- 报告链接采用 GitHub Pages 长期历史页，还是仅本次运行 artifact 链接。
