# 服务号业务场景验收

## 来源与范围

Codex 的「进入前端页面测试」窗口记录了摇人吧测试站的双角色工单验证，覆盖从新建会话到重新打开已关闭工单的 17 步。窗口也梳理了知识归档、知识出题和高价值问题的流程。服务号测试站实跑、隔离环境的后台规则检查和待验证的前台链路分别说明。

| 场景 | 角色与验收条件 | 验证范围 |
| --- | --- | --- |
| 报障工单从提单到关闭 | 提单人确认草稿，系统自动派给处理人，处理人接单并推进初步诊断、临时解决和最终解决，提单人验收并重新打开核对关闭状态 | 测试站页面，17 步 |
| 工单知识发布与奖励审核 | 内容审核通过后奖励待财务审核，财务批准后归档并发布知识，财务拒绝时知识不发布 | 本地数据库规则，奖励状态，重复审核 |
| 知识出题与开卷预览 | 敏感材料脱敏后交给模型，人工确认内容后生成草稿题，审核启用后才可用，多选答案完全匹配才得分 | 后台接口与评分规则。服务号用户答题并保存进度待验证 |
| 高价值问题评选 | 有管理权限的角色发布，用户作答和点赞，截止后按答案点赞评选，奖励进入待财务审核 | 本地数据库规则，实际发放待验证 |

## 报告验收

- 首页显示测试来源、结果、角色、操作和预期。实际结果只保留明确的断言状态和业务结果，缺少步骤、跳过和失败分别显示。
- 可选加载测试站 Allure 结果。历史结果带时间标识，独立于本次 Test Gate 的结论与计数。页面截图、账号、接口原始报文和失败堆栈不导入业务 HTML。
- 后台规则用隔离数据执行，按业务场景关联断言。无产物时报告按计划展示，学习中心前台流程设独立待验证项。

## 执行和产物

- Test Gate 在原「工单功能场景」观察任务中运行 `automation/tests/test_service_account_rules.py`，复用 7 条隔离后台断言，并增加 2 条使用现行管理权限的高价值问题用例。规则检查使用 SQLite 和模拟模型，并验证财务批准、拒绝和重复处理状态。
- `automation/tests/ui/test_service_account_ticket_lifecycle.py` 沿用双账号 UI 测试运行配置。启用 `UI_REGRESSION_E2E=1` 并填写测试环境账号、网关参数和 `UI_REGRESSION_U2_DISPLAY_NAME` 后，可使用 `--alluredir` 生成 17 步结果。以「USP 使用问题」作为新用例的模拟报障内容。
- 生成报告时，可用 `--service-account-ui-results <独立运行的 Allure 目录>` 载入窗口中已实跑的工单记录。报告样本使用 2026-11-23 16:37（UTC+8）的运行，内容为模拟机器人故障。报告只取步骤与断言的状态，正文使用固定业务描述。
- 已验证后台规则、缺失／失败历史证据、来源分组，以及历史实跑不会改变 Test Gate 的判定和统计。专项业务报告与 Allure 样本通过合并产物生成。当前工作区未配置双账号测试站连接，本次新 UI 用例按环境开关跳过。
