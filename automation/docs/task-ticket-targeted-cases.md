# 合入自动触发的工单定向用例

## 触发与范围

```
任意分支 ──PR 合并──▶ test
                        │ push 事件
                        ├─ 抓提交信息里的 ORS-<id>
                        ├─ 查只读 API 拿状态
                        └─ 对 resolved/closed 的工单跑 promoted-cases/<id>/test_gen.py
```

| 项 | 值 |
| --- | --- |
| 合入源 | 任意分支（含 fork），只要 PR 合并进 `test` |
| 目标分支 | `test` |
| 触发事件 | `push`（与 Test Gate 同一个事件） |
| 执行环境 | GitHub 托管 runner + 临时 MySQL + 本地后端（不碰测试站和生产） |
| 工单号来源 | 本次 push 范围内提交信息的 `ORS-<id>`，去重后并行 |

## 两个 job

| job | 作用 |
| --- | --- |
| `ticket-resolve` | 解析提交范围，输出工单号数组；没有则输出 `[]` |
| `ticket-cases` | 矩阵并行，每个工单一个 job：校验转正状态 → 查生产状态 → 跑用例 |

## 失败语义（关键）

| 情况 | 行为 | 理由 |
| --- | --- | --- |
| 提交里没有工单号 | 跳过，摘要写明 | 回归由四套件覆盖 |
| 工单号没有转正用例 | **失败** | 合了代码但没可执行用例，属于流程缺失 |
| API 返回 404（查不到工单） | 跳过 + 警告 | 可能是跨库/历史单号 |
| API 返回 5xx / 网络失败 | **失败** | 无法判断状态时不能当成「未关闭」 |
| 工单状态非 resolved/closed | 跳过 + 通知 | 合代码和关工单顺序可能反 |
| 工单项目与 manifest 不一致 | **失败** | 防止别的项目的同号工单触发 |

## 与手动验收的区别

| | 手动 acceptance | 自动定向 |
| --- | --- | --- |
| 触发 | 人点 workflow_dispatch | push 到 test |
| 工单未关闭 | **失败**（人明确要求验这张） | **跳过**（合入时可能还没关） |
| 目的 | 发布前确认某张单 | 合入即验证 |

## 已知限制

- Test Gate 有 paths 过滤（`automation/` `backend/` `frontend/` `ai/`）。只改文档的合入不会触发本流程，也就不会跑定向用例。
- 一次合并涉及 N 个工单时，起 N 个 job，每个都各自安装依赖、起后端；工单多时耗时会线性增长。
- 用例质量取决于 promoted-cases 本身；生成器写死数据的问题（如 995）会让定向用例假失败。
