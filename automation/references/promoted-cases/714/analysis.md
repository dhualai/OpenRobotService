# 工单概述

- 工单编号：714
- 项目：摇人吧服务号
- 类型：feature
- 状态：in_progress
- 背景：用户反馈服务号更新频繁、bug 频发，询问是否经过 AI 自动化测试。经排查，当前服务号平台仍依赖人工测试和用户反馈发现问题，尚未建立 AI 自动化测试流程。
- 用户期望：
  - 自动化回归测试覆盖常用基本功能；
  - 每次发版更新时自动触发回归测试。
- 当前主要卡点：
  - 微信生态对端到端自动化的限制；
  - 服务号逻辑与后端强耦合，测试环境搭建成本高；
  - 现阶段人工回归加小流量观察的投入产出比更优。
- 结论：用户需求明确，建议作为功能需求提交至平台侧评估。

# 功能点清单

| 编号 | 功能点 | 说明 |
|---|---|---|
| REQ-01 | 常用基本功能回归范围定义 | 明确“常用基本功能”的具体范围、优先级和纳入标准，作为自动化回归测试的覆盖边界。 |
| REQ-02 | 自动化回归测试流程建设 | 建立可执行的自动化回归测试流程，替代或补充当前依赖人工测试和用户反馈的发现方式。 |
| REQ-03 | 发版自动触发回归测试 | 每次服务号发版更新时，自动触发回归测试，减少人工触发遗漏。 |
| REQ-04 | 测试环境与数据支撑能力 | 针对服务号逻辑与后端强耦合、测试环境搭建成本高的问题，需评估可落地的测试环境和数据准备方案。 |
| REQ-05 | 微信生态限制的应对方案 | 针对微信生态对端到端自动化的限制，需明确替代或补偿方案，例如可执行范围、人工补充或其它测试手段。 |
| REQ-06 | 人工回归与小流量观察协同 | 在自动化回归尚未完全覆盖的场景下，保留人工回归和小流量观察作为补充手段，并明确协同关系。 |
| REQ-07 | 平台侧评估与接入 | 将该需求提交平台侧评估，确认可行性、实现方式、排期和投入产出。 |

# 业务规则

- 自动化回归测试的覆盖范围为“常用基本功能”，不要求覆盖服务号全部功能。
- 每次发版更新时必须自动触发回归测试，而不是仅依赖人工触发或用户反馈。
- 当前基线为：尚未建立 AI 自动化测试流程，主要依赖人工测试和用户反馈发现问题。
- 方案设计需考虑微信生态对端到端自动化的限制。
