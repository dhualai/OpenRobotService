# 工单概述

**工单编号**：995
**工单标题**：拓扑平台功能移植升级到问题文档
**工单类型**：feature（功能需求）
**所属项目**：摇人吧服务号（project_id: Leo_test）
**当前状态**：in_progress（进行中）

**工单目标**（依据工单描述归纳）：

1. **文档迁移**：将拓扑平台已有的需求文档内容，迁移到服务号中该需求对应工单的“问题文档”内。
2. **文档持续维护**：迁移完成后，需求内容的补充、修改、更新统一在服务号工单的问题文档中进行，不再回到拓扑平台维护。
3. **信息关联**：保证需求文档与对应需求工单之间存在可追溯的关联关系，支撑后续的需求评审、任务拆分与研发跟踪。
4. **管理入口统一**：需求文档的维护与管理入口从“拓扑平台 + 服务号”双入口收敛为服务号工单单入口。

**测试定位**：本次属于“文档载体迁移 + 维护方式变更”，测试核心不是新业务功能逻辑，而是**迁移数据的一致性、关联关系的正确性、迁移后维护闭环的可用性，以及旧入口停用后的业务连续性**。

# 业务规则

> 以下规则有的直接来自工单描述，有的为验证迁移类需求所必需的检查维度；工单未明确的部分已标注，不做臆断。

1. **单一维护入口规则**：迁移后，需求文档的补充、修改、更新“直接在服务号工单的问题文档中进行”，即服务号问题文档为唯一维护入口。
2. **内容等价规则**：迁移不得造成需求内容丢失、截断、错位；迁移前后文档承载的信息应等价（格式差异是否可接受 → 待确认）。
3. **归属正确规则**：每份需求文档必须迁移到其“对应的”需求工单下，不能跨工单错挂或挂到无对应关系的工单。
4. **关联可追溯规则**：需求文档与需求工单之间的关联需可在后续评审、任务拆分、研发跟踪场景中被使用（以何种形式呈现关联 → 待确认）。
5. **迁移一次性 / 持续维护规则**：迁移为一次性动作，迁移完成后的增量内容不再由拓扑平台同步；迁移后拓扑平台侧内容的处置策略（保留只读、归档或下线）→ 待确认。
6. **变更可追溯规则**：问题文档修改后是否需保留历史版本 / 修改记录 → 工单未明确，列入待确认。

# 测试重点

## 一、迁移正确性（核心）

1. **内容一致性比对**：对每份迁移文档进行源/目标逐段比对，含标题层级、正文段落、列表、表格、图片、附件、超链接、特殊符号与换行。
2. **归属正确性**：文档迁移到对应工单，不串单、不重复挂载、不遗漏。
3. **映射完整性**：迁移清单中每一份源文档都能在目标侧找到，目标侧不出现来源不明的文档。
4. **多份文档 / 单个工单**：一个工单对应多份需求文档、或一份文档拆到多个工单的场景下，关联关系是否正确（业务是否允许 → 待确认）。

## 二、关联关系（核心）

5. 从需求工单可定位到其问题文档；从问题文档可回溯所属需求工单。
6. 关联关系在“需求评审、任务拆分、研发跟踪”场景下可被正常引用与打开。
7. 关联关系在文档被编辑后是否保持有效（不因编辑/改名而断链）。

## 三、迁移后维护闭环

8. 在问题文档中新增内容 → 保存 → 重新进入，内容存在且格式正常。
9. 修改已有内容 → 保存 → 内容更新正确，未影响其他段落。
10. 删除内容 → 保存 → 删除生效且不误删相邻内容。
11. 多次连续编辑、并发编辑（多人同时编辑同一文档）的行为 → 待确认后验证。
12. 编辑后是否存在版本/历史记录 → 依据确认结果验证。

## 四、入口切换与连续性

13. 迁移完成后，从拓扑平台侧是否仍可访问原文档（只读/下线），用户是否被正确引导到服务号工单。
14. 迁移前已在拓扑平台侧产生的文档外链、收藏、通知中的链接，迁移后是否可正常访问或给出合理提示。
15. 用户按原习惯在拓扑平台寻找/维护需求文档时的行为是否符合预期（避免出现双份内容并行维护）。

## 五、异常与容错

16. 迁移过程中断（网络异常、源文档不可读、目标侧写入失败）后的表现：是否可识别失败、是否可重试、是否产生半迁移脏数据。
17. 迁移内容超限场景（超大文档、超多图片/附件）的处理。
18. 源文档含特殊字符、编码差异时的内容是否正常。

# 风险与边界

| 类别 | 风险 / 边界点 | 影响 |
|---|---|---|
| 数据完整性 | 图片、附件、表格在迁移中丢失或不可打开 | 需求信息缺失，研发按错误信息实施 |
| 格式保真 | 富文本样式、层级结构在目标文档编辑器中被破坏 | 可读性下降，后续维护成本高 |
| 归属错误 | 文档挂错工单或重复挂载 | 需求与工单错配，评审与拆分依据错误 |
| 关联断裂 | 关联关系在文档编辑、工单状态变化后失效 | 无法从工单追溯到需求来源 |
| 双入口并行 | 迁移后仍有用户在拓扑平台继续维护 | 出现两份不一致的需求文档，需明确停用策略 |
| 权限落差 | 迁移后可见范围变化 | 信息泄露或需求相关人员无法查看 |
| 历史链接 | 旧链接/书签/通知失效 | 用户无法找到原需求文档 |
| 不可回退 | 迁移后若发现问题，是否有回退/回滚方案 | 迁移失败时无法恢复原状 |
| 边界数量 | 源文档体量大（数量多、单篇长、附件多） | 迁移耗时、超时、部分失败 |
| 并发 | 迁移动作与用户在目标侧编辑同时发生 | 内容覆盖、数据冲突 |
| 存量范围 | 是否存在“历史已关闭工单对应的需求文档”未纳入迁移 | 部分需求文档游离在统一入口之外 |

# 待确认问题

1. **迁移范围**：本次需迁移的拓扑平台需求文档清单是什么？是否包含历史已结束/已关闭需求对应的文档？是否有明确的迁移完成判定标准（数量、清单签收）？
2. **文档粒度**：拓扑平台侧文档与需求工单的对应关系是 1:1、1:N 还是 N:1？一个工单是否允许多份问题文档？
3. **迁移方式**：是人工复制粘贴，还是系统/工具批量迁移？是否有迁移执行入口与操作日志？
4. **格式要求**：迁移后格式保真到什么程度可接受（图片、附件、表格、代码块、外部链接是否必须可用）？是否存在拓扑平台独有、目标侧不支持的文档元素？
5. **拓扑平台侧处置**：迁移完成后，拓扑平台上的原需求文档是保留只读、归档、还是下线？下线时间点与用户告知方式？
6. **入口唯一性**：是否存在过渡期双入口并行？过渡期多长？期间内容冲突如何处理？
7. **权限映射**：拓扑平台原文档的可见/编辑范围在服务号中如何映射？服务号工单问题文档的权限模型（角色、授权方式）是什么？
8. **版本与留痕**：问题文档是否需要版本历史、修改记录、操作人留痕？
9. **工单状态联动**：工单状态（如 in_progress、已完成、已关闭）是否影响问题文档的可编辑性？
10. **关联呈现形式**：文档与工单的“关联”以何种形式呈现（工单内的文档入口、文档上的工单引用、双向链接等）？关联是否可解绑/重建？
11. **回退方案**：迁移失败或迁移后发现内容缺失时，是否有回滚机制与责任方？
12. **验收标准**：本工单的验收口径是“迁移清单 100% 迁移完成且抽查一致”，还是需全量逐篇核对？抽查比例如何确定？
13. **是否有评审流程**：迁移后的需求文档是否仍需走评审流程？评审记录是否随文档迁移？
14. **通知与告知**：迁移完成后通过什么方式通知原拓扑平台使用方（站内信、公告、培训）？
