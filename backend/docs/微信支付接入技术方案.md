# OpenRobotService 微信支付接入技术方案

> 版本：v1.1（方案评审稿）
> 日期：2026-10-06
> 适用范围：OpenRobotService `backend`（Python FastAPI）接入微信支付
> API 版本：**APIv3**（V2 已存量维护、不再新增功能，本方案不使用）
> 接入模式：**普通商户（直连）**，商户号 `mchid` 自有，资金结算到本商户账户
> 业务形态：**奖励记录 + 立即提现**（无卡包 / 无余额账户）

---

## 0. 需求确认结论

| 项目 | 结论 | 说明 |
| --- | --- | --- |
| 资金方向 | **付款为主**：商家转账（商户 → 用户零钱） | 对应产品「商家转账」（原企业付款到零钱升级版，2025-01-15 上线升级版） |
| 辅助方向 | **收款**：JSAPI 支付 | 复用现有服务号 `openid`，覆盖微信内浏览器场景 |
| 接入模式 | 普通商户直连 | 无 `sp_mchid` / `sub_mchid`，不涉及分账佣金 |
| 技术形态 | **待定，本文档给出对比**（第 2 章） | 倾向独立 Go 微服务，理由见 2.3 |
| 境外/跨境 | 不涉及 | 官方文档 SDK 明确仅支持境内商户接入 |
| **业务形态** | **奖励记录 + 立即提现**，**不做卡包/余额账户** | 用户侧唯一入口为「我的历史奖励」；奖励先记账，用户点「立即提现」时才创建转账单。详见第 4 章 |
| **免确认收款授权** | **v1 不做**，降级为二期可选增强 | 无卡包批量提现场景后，授权不再是必需项；仅用于优化「每次提现都要弹确认页」的体验，见 4.9 |

## 1. 现状与接入基础

### 1.1 现有系统

- 后端：`backend/`，**FastAPI + Pydantic Settings + SQLAlchemy + MySQL**，入口 `backend/main.py`（uvicorn，默认端口 8400）
- 配置：`backend/app/core/config.py`，`Settings` 类已含 `WECHAT_APP_ID` / `WECHAT_APP_SECRET` / `WECHAT_TOKEN` / `WECHAT_ENCODING_AES_KEY`
- 微信模块：`backend/app/wechat/`，已实现服务号消息回调、OAuth 授权、`openid` 获取、菜单/标签管理、主动消息推送
- 用户模型：`backend/app/models/identity.py` → `users` 表，已有 `wechat_openid`（`String(128)`，带索引）、`name` 字段
- 现有外部调用习惯：`httpx.AsyncClient`（`app/core/llm_client.py`、`app/integrations/sources/*`）

### 1.2 可复用的既有能力

| 能力 | 现值 | 对微信支付的价值 |
| --- | --- | --- |
| 服务号 `appid` | `WECHAT_APP_ID` | 「商家转账」和「JSAPI 支付」都要求 `appid` 与 `mchid` 绑定，且转账/下单的 `appid` 必须与调起页面的 `appid` 一致 |
| 用户 `openid` | OAuth 已获取，存 `users.wechat_openid` | 商家转账收款人 `openid`、JSAPI 下单 `payer.openid` 直接复用，无需重新授权 |
| 用户姓名 | `users.name` | 商家转账单笔 ≥ 2000 元时**必须**传 `user_name` 做实名校验，该字段可作来源（需评估是否已实名） |
| 公网 HTTPS 域名 | 服务号回调已在用 | 支付/转账回调要求 `notify_url` 必须为公网 HTTPS、不能带参数 |

### 1.3 必须新增的前置条件（非代码）

1. **申请商户号**（若无）：微信支付商户平台注册，主体类型须支持（商家转账**暂不支持小微商户**）
2. **开通产品权限**：
   - 商家转账：商户平台 → 产品中心 → 运营工具 → 商家转账 → 申请开通，需**选择转账场景**并提交场景证明资料
   - JSAPI 支付：商户平台开通 JSAPI 支付权限；仅有**服务号 / 政府或媒体类型公众号**且**已完成认证**才可申请
3. **`appid` 与 `mchid` 绑定**：商户平台发起 APPID 授权绑定 → 公众平台确认。绑定后**不可解绑**
4. **配置 JSAPI 支付授权目录**（仅收款需要）：未配置目录的网页无法调起支付
5. **设置商家转账接口安全 IP**：**强制项**。仅设定 IP 可调用商家转账 API，未设置会报「此IP地址不允许调用接口」
6. **获取开发参数**：`mchid`、商户 API 证书（+私钥、证书序列号）、**微信支付公钥（推荐）+ 公钥 ID**、APIv3 密钥
7. **设置转账额度**（按需提额，见 4.4）
8. **运营账户充值**：商家转账从商户「运营账户」出资，余额不足会停在 `PROCESSING` 或转 `FAIL`

## 2. 技术形态选型对比（Go 微服务 vs Python 直连）

### 2.1 关键事实（决定选型）

| 事实 | 依据 |
| --- | --- |
| 官方服务端 SDK **只有 Java / PHP / Go 三种**，**没有官方 Python SDK** | SDK 概述文档明确列出 Java `wechatpay-java`、PHP `wechatpay-php`、Go `wechatpay-go`；Python 仅存在于「社区 SDK」，官方声明「不对资源的质量负责，建议以参考为主，不要直接拷贝使用」 |
| 商家转账全部接口官方示例代码**只有 curl / Java / Go**，无 Python | 官方「发起转账」「撤销转账」「查询转账单」等请求示例均为 curl / Java / Go 三份 |
| Go SDK 提供：自动签名验签、敏感信息加解密、回调自动验签+解密，并封装业务接口 | SDK 概述 + Go SDK 文档 |
| Go SDK 环境要求 Go 1.16+，`github.com/wechatpay-apiv3/wechatpay-go` | 使用 Go SDK 文档 |
| 平台证书每 5 年需更换；**微信支付公钥长期有效，官方推荐优先使用** | 开发必要参数说明 / 微信支付公钥验签文档 |

### 2.2 三方案对比

| 维度 | 方案 A：独立 Go 微服务 | 方案 B：Python 直连（自研签名） | 方案 C：Python + 社区 SDK |
| --- | --- | --- | --- |
| 官方支持 | ✅ 官方 SDK + 官方 Go 示例全覆盖 | ❌ 无任何官方 Python 示例/SDK 可用 | ❌ 社区维护，官方不背书 |
| 签名/验签/加解密正确性风险 | 低（SDK 已封装，经官方迭代测试） | **高**：需自行实现 RSA-SHA256 签名、AES-256-GCM 回调解密、公钥验签 | 中（取决于社区实现质量） |
| 敏感信息加密 | SDK 提供（`user_name` 需 RSA-OAEP 加密） | 需自行实现 RSA-OAEP + 公钥加载 | 视社区实现 |
| 回调验签 + 解密 | SDK 内置 | 需自行实现，**此处出错＝资金损失（假通知）** | 视社区实现 |
| 接口升级/新增扩展 | 更新 SDK 即可 | 全部手写 | 依赖社区跟进 |
| 与现有 FastAPI 融合度 | 需跨服务调用（一次内部 HTTP） | 天然融合，直接写业务逻辑 | 天然融合 |
| 运维成本 | **+1 个部署单元**（进程/容器/监控/日志） | 无新增 | 无新增 |
| 团队技能栈 | 需引入 Go 技术栈 | 纯 Python | 纯 Python |
| 隔离性与安全边界 | **高**：商户私钥/APIv3 密钥只落在 Go 服务，Python 侧零密钥 | 低：密钥进入主应用进程 | 低 |
| 性能 | Go 更优（100 QPS 限频下差异不明显） | 足够 | 足够 |
| 二次复用 | 可被其他语言/系统复用同一支付中台 | 绑定 Python | 绑定 Python |

### 2.3 推荐结论

**推荐方案 A：独立 Go 微服务（`wxpay-service`）。**

理由（按权重排序）：

1. **资金安全是首要约束而非开发便利**。商家转账是**资金出账**动作，回调验签失败会导致「假通知入账」的资损；`user_name` 需 RSA-OAEP 加密。官方 SDK 已封装且经官方迭代，自研 Python 实现等于把最高风险环节交给一次性手写代码。
2. **官方生态支持差距是硬差距**。官方示例代码明确无 Python；出了问题只能靠 curl 文档自行排错，而 Go 路径可直接使用官方示例与 SDK Issue 支持。
3. **密钥隔离**。商户 API 私钥、APIv3 密钥只存在于 Go 服务，Python 主应用完全不接触支付密钥，缩小泄露面；也便于后续对 Go 服务单独做网络策略（固定出口 IP 满足「接口安全 IP」要求）。
4. **成本可控**。服务仅需暴露 4～6 个内部接口 + 2 个回调入口，边界很小；用 `wechatpay-go` 的 `core` + `services` 层，实际代码量远小于自研签名体系。

**回退条件**（满足任一则可改用方案 B）：
- 团队明确不接受引入第二语言栈，且愿意承担自研签名/验签/加解密的测试与审计成本；
- 或仅接入「JSAPI 收款」而**暂不接入商家转账**（收款方向资损风险显著低于出账）。

> ⚠️ 若最终选择方案 B，请务必：① 严格按官方文档实现签名串构造（三行、`\n` 结尾）；② 回调必须验签 + 解密后才落库；③ 补齐单元测试覆盖签名验签与 AES-GCM 解密；④ 上线前做官方「签名探测流量」兼容验证（不得以 `WECHATPAY/SIGNTEST/` 前缀做特殊放行）。

## 3. 总体架构

### 3.1 部署视图

```
                    ┌──────────────────────────────────────┐
   用户微信客户端 ──▶ │  服务号 H5 页面（微信内浏览器）        │
                    │  · JSAPI 支付: WeixinJSBridge         │
                    │  · 商家转账: requestMerchantTransfer  │
                    └───────────────┬──────────────────────┘
                                    │ HTTPS
                    ┌───────────────▼──────────────────────┐
                    │  反向代理 / Nginx（公网 HTTPS 域名）    │
                    │  /api/**        → FastAPI            │
                    │  /wxpay/notify/** → Go wxpay-service │
                    └───────┬──────────────────────┬───────┘
                            │                      │
              ┌─────────────▼──────────┐  ┌────────▼─────────────────┐
              │  backend (FastAPI)     │  │  wxpay-service (Go)      │
              │  · 奖励记录/转账单/订单   │  │  · wechatpay-go SDK      │
              │  · 用户、权限、openid   │  │  · 签名/验签/加解密       │
              │  · 内部 HTTP 调用 ↓     │  │  · 回调验签+解密          │
              └─────────────┬──────────┘  │  · 商户私钥/APIv3密钥     │
                            │             └────────┬─────────────────┘
                            │  内网 HTTP            │ HTTPS
                            └──────────▶ ┌─────────▼──────────┐
                                         │ api.mch.weixin.qq.com│
                            ┌────────────┴────────────────────┐
                            │  MySQL（奖励记录/转账单/订单/回调流水）│
                            └─────────────────────────────────┘
```

要点：
- **回调入口直达 Go 服务**（`/wxpay/notify/**`），避免密钥相关逻辑经过 Python；也可由 Python 转发，但前者更简洁
- Go 服务**固定出口 IP**，用于商户平台「接口安全 IP」白名单
- **MySQL 完全由 FastAPI 侧持有，Go 服务不直连数据库**。Go 侧完成「验签 + 解密」后把结果推送给 FastAPI 内部接口，由 FastAPI 落 `wxpay_notify_log` 并驱动业务状态机；推送失败则应答 5xx 让微信重试，配合 FastAPI 兜底查单保证最终一致

### 3.2 Go 服务内部分层（已落地，见 `wxpay-service/`）

```
wxpay-service/
├── cmd/server/main.go               # 启动、优雅退出、日志初始化
├── internal/
│   ├── config/config.go             # 环境变量配置与校验
│   ├── wxpay/                       # APIv3 内核（纯标准库，零第三方依赖）
│   │   ├── keys.go                  # PEM 密钥加载（PKCS#1/PKCS#8/PKIX）
│   │   ├── sign.go                  # 请求签名 + 应答验签
│   │   ├── cipher.go                # AES-256-GCM 解密 / RSA-OAEP 加密
│   │   ├── verifier.go              # KeyProvider（微信支付公钥/平台证书）
│   │   ├── client.go                # APIv3 HTTP 客户端（自动签名验签）
│   │   └── notify.go                # 回调：验签 → 解析 → 解密
│   ├── transfer/                    # 商家转账
│   │   ├── service.go               # 发起/撤销/查询 + 参数与额度校验
│   │   └── model.go                 # 转账单状态机与请求响应模型
│   ├── store/dedupe.go              # 回调通知内存去重（第一道防线）
│   ├── downstream/fastapi.go        # 推送解密结果给 FastAPI
│   └── httpsrv/                     # 路由、鉴权中间件、错误处理
├── Dockerfile / Makefile / .env.example
└── go.mod                           # 无第三方依赖
```

> **实现说明**：落地时未使用官方 SDK `wechatpay-go`，改为纯标准库实现。原因：① 官方 Go 示例本身采用 `wxpay_utility` 自签方式，商家转账在 SDK 中无强类型 Service；② 签名/验签/AES-GCM/RSA-OAEP 四个环节均有单元测试覆盖；③ 无 `go.sum` 与版本漂移风险。若需切回官方 SDK，**只需替换 `internal/wxpay/` 一个包**（`Client.Do` / `VerifyAndParse` / `EncryptOAEP` 三个入口）。详见 `wxpay-service/README.md`。

**路由注册**（`app/__init__.py`）：

| 路由器 | 前缀 | 说明 |
| --- | --- | --- |
| `wxpay_router` | `settings.API_V1_STR`（`/api`） | 用户端「我的历史奖励」，走 JWT 登录态 |

## 4. 商家转账（核心）设计

### 4.1 业务形态：奖励记录 + 立即提现（无卡包）

产品形态确定为：**不做卡包 / 余额账户**，用户侧只有唯一入口「我的历史奖励」。

```
达成条件
  └─▶ 创建奖励记录 reward_record（纯商户侧记账，status = 待提现）
        └─▶ 服务号模板消息通知（复用 app/wechat 现有主动推送能力）

「我的历史奖励」列表
  └─▶ 点「立即提现」
        └─▶ 后端 POST /v3/fund-app/mch-transfer/transfer-bills
              └─▶ 返回 package_info（state = WAIT_USER_CONFIRM）
                    └─▶ 前端 requestMerchantTransfer 调起确认页
                          └─▶ 用户确认 → 资金实时到账
                                └─▶ 回调 MCHTRANSFER.BILL.FINISHED → 更新奖励状态
```

**两条铁律：**

| # | 规则 | 原因 |
| --- | --- | --- |
| 1 | **奖励发放时绝不创建转账单**，必须等用户点「立即提现」 | `package_info` 24 小时过期；且发起转账受理成功后资金**立即锁定**，提前建单会白占单日额度 |
| 2 | **奖励记录状态机独立于微信转账单状态机** | 一笔奖励在重试场景下会对应**多笔**转账单（换 `out_bill_no`），两者不可等同 |

> 这是业界主流做法（签到奖励、任务奖励、邀请返现、报销补贴）。去掉卡包后**免确认收款授权不再是必需项**，v1 只需一条链路。

### 4.2 奖励记录状态机

```
                   ┌──────────────────────────────┐
                   │  待提现 PENDING              │◀────────────┐
                   └───────────┬──────────────────┘             │
                               │ 用户点「立即提现」                │
                               │ → 创建转账单（新 out_bill_no）    │
                               ▼                                │ 转账单终态
                   ┌──────────────────────────────┐             │ FAIL / CANCELLED
                   │  提现中 WITHDRAWING           │─────────────┘ （可换单重新提现）
                   │  存在非终态转账单               │
                   └───────────┬──────────────────┘
                               │ 转账单 SUCCESS
                               ▼
                   ┌──────────────────────────────┐
                   │  已到账 SUCCESS（终态）        │
                   └──────────────────────────────┘

   定时任务：超过 reward.expire_at 仍未提现 ──▶ 已失效 EXPIRED（终态）
```

**映射规则（奖励状态 ← 转账单状态）**

| 转账单 `state` | 奖励记录 `status` |
| --- | --- |
| 无转账单 | `待提现` |
| `ACCEPTED` / `PROCESSING` / `WAIT_USER_CONFIRM` / `TRANSFERING` / `CANCELING` | `提现中` |
| `SUCCESS` | `已到账` |
| `FAIL` / `CANCELLED` | `待提现`（可重新提现，**须换新的 `out_bill_no`**） |

**前端按钮文案**

| 奖励状态 | 按钮 | 行为 |
| --- | --- | --- |
| `待提现` | 「立即提现」 | 创建新转账单 → 调起确认页 |
| `提现中` | 「去确认」 | **复用** `package_info` 重新调起确认页 |
| `已到账` | — | 展示到账时间 |
| `已失效` | — | 展示失效原因 |

### 4.3 提现入口三分支决策（防重复出资，最高优先级）

任何一次提现动作，后端**必须先查单再决策**，绝不可直接新建转账单：

```
点「立即提现」/「去确认」
   │
   ├─ 查该 reward_id 下当前有效（非终态）转账单
   │
   ├── 存在且仍为 WAIT_USER_CONFIRM
   │        └─▶ 复用原 package_info，直接调起确认页（不建新单）
   │
   ├── 存在且为其它非终态（ACCEPTED/PROCESSING/TRANSFERING/CANCELING）
   │        └─▶ 调查单接口刷新状态；仍非终态则提示「处理中，请稍后」
   │
   └── 不存在 / 已为终态（FAIL/CANCELLED）
            └─▶ 生成【新的 out_bill_no】→ 发起转账 → 返回新 package_info
```

- 🔴 **同一笔奖励上同时存在两笔非终态转账单 ＝ 重复出资**
- 官方明确：用户取消确认收款页面后，**可以重新调起确认收款页面**
- 并发防护：以 `reward_id` 为键加分布式锁（或 DB 行锁），保证同一时刻只有一个建单流程

### 4.5 转账单状态机（微信侧，必须严格实现）

```
ACCEPTED ──▶ PROCESSING ──▶ WAIT_USER_CONFIRM ──▶ TRANSFERING ──▶ SUCCESS(终态)
   │              │                │
   │              │                ├── 用户24h未确认 ──▶ FAIL(终态) ─┐
   │              ├── 余额不足超24h未充值 ──▶ FAIL(终态)              ├─▶ 奖励回到「待提现」
   │              └── 网络抖动等异常 ──▶ FAIL(终态)                   │
   └── 用户确认收款前，商户可主动撤销 ──▶ CANCELING ──▶ CANCELLED ────┘
```

- **终态只有三个**：`SUCCESS` / `FAIL` / `CANCELLED`
- `package_info` **仅在 `WAIT_USER_CONFIRM` 时返回**，用于前端调起确认收款页
- 单据创建后用户 **24 小时**未确认将自动关单退款；系统关单完成时间可能超过 24h，**换单重新提现前必须查单确认已到终态**，否则可能重复出资
- 官方明确：**微信不会主动推送收款确认消息**，必须由商户调起确认页 —— 因此「提现中」状态必须有明显入口，并建议配合服务号模板消息提醒

### 4.6 关键请求参数（`发起转账`）

| 参数 | 必填 | 约束 |
| --- | --- | --- |
| `appid` | ✅ | 必须与 `mchid` 有绑定关系，且与实际调起收款页的 appid 一致 |
| `out_bill_no` | ✅ | 商户系统内唯一，**只能由数字、大小写字母组成**，≤32 字符 |
| `transfer_scene_id` | ✅ | 商户平台「产品中心-商家转账-产品设置」获取，如 1000（现金营销）、1006（企业报销） |
| `openid` | ✅ | 用户在**该 appid** 下的 openid |
| `transfer_amount` | ✅ | **单位：分**，整型 |
| `transfer_remark` | ✅ | ≤32 字符，用户可见 |
| `transfer_scene_report_infos` | ✅ | 场景报备信息，按场景传固定 `info_type`（如现金营销需「活动名称」+「奖励说明」） |
| `user_name` | 条件 | **≥2000 元必须传**；0.3~2000 元可选；<0.3 元不支持。需用微信支付公钥/平台证书 **RSA-OAEP 加密** |
| `notify_url` | 推荐 | 公网 HTTPS，不能带参数 |
| `user_recv_perception` | 可选 | 覆盖默认收款感知文案 |
| `user_recv_style.type` | 可选 | `CONFIRM_PAGE`（默认）/ `RED_PACKET`（红包样式，**单笔 ≤ 200 元**，仅部分场景支持） |

⚠️ **场景报备信息必须随奖励落库**：现金营销场景（1000）的报备信息是**固定两条**——「活动名称」+「奖励说明」，缺一即报 `PARAM_ERROR`。因此 `reward_record` 必须持久化这两个字段（见 7.2），发起转账时原样带入。

### 4.7 额度限制（设计必须内置校验）

默认额度（**非个体工商户**主体）：

| 类型 | 默认 | 可调范围 |
| --- | --- | --- |
| 单笔限额 | 200 元 | 0.1 ~ 200 元 |
| 单用户单日限额 | 2,000 元 | 0.1 ~ 2,000 元 |
| 单日转账额度 | 5 万元 | 0.1 ~ 5 万元 |

> 提额需在商户平台申请并通过审核（需完成场景审核及安全能力设置）。**系统侧应做额度前置校验 + 失败告警**，避免大量 `NOT_ENOUGH` / 超限失败单。

    WeixinJSBridge.invoke('requestMerchantTransfer',
      { mchId: '<mchid>', appId: '<appid>', package: '<package_info>' },

### 4.9 可选增强：免确认收款授权（二期）

v1 使用纯确认模式（每次提现弹一次确认页）。若运营反馈体验不佳，二期可用「发起转账并完成免确认收款授权」接口 `pre-transfer-with-authorization`：

| 对比 | v1 确认模式 | v2 免确认模式 |
| --- | --- | --- |
| 接口 | `/v3/fund-app/mch-transfer/transfer-bills` | `/v3/fund-app/mch-transfer/transfer-bills/pre-transfer-with-authorization`（首笔，走确认页）→ `/transfer-bills/transfer`（后续，同步静默到账） |
| 用户流程 | 每次提现都要点一次确认 | **首次提现顺带授权，之后静默到账** |
| 额外成本 | 无 | 需存 `authorization_id`、处理授权结果回调、校验授权有效性（用户可解除） |
| 限制 | 无 | 授权单数量上限 **5 个**；免确认转账**不支持** `notify_url`，同步返回即终态 |

> 用户流程差异极小（首笔仍是一次弹窗），建议 v1 跑通后再评估。官方建议在用户首次收款或登录、报名、提交审核时引导授权。

### 5.2 时序要点

1. 后端下单 → 得 `prepay_id`，**有效期 2 小时**，过期需用原参数重新下单
2. 后端返回前端调起参数：`appId` / `timeStamp`(**秒级**) / `nonceStr` / `package`(`prepay_id=xxx`) / `signType`(`RSA`) / `paySign`

4. 支付成功 → 微信 POST `TRANSACTION.SUCCESS` → Go 服务验签+解密 → 更新订单
5. 兜底：未收到回调时按 5s/30s/1m/3m/5m/10m/30m 梯度查单；超时未付则关单
6. 订单状态：`NOTPAY → SUCCESS / CLOSED / REFUND`；7 天内可关单，超 7 天微信自动关单；支付成功后 1 年内可退款

### 5.3 前端注意

- **下单按钮必须防抖**，防止重复下单造成重复支付
- 需已在商户平台配置 **JSAPI 支付授权目录**，否则无法调起支付
- `time_expire` 可设支付截止时间（不早于下单 1 分钟，不超过 15 天；不传默认 7 天）

## 6. 回调统一设计（两类回调共用）

### 6.1 处理流程（**顺序不可变**）

```
1. 读取原始 Body（禁止框架篡改/重序列化）
2. 取 Header: Wechatpay-Serial / Wechatpay-Signature / Wechatpay-Timestamp / Wechatpay-Nonce
3. 构造验签串：timestamp\n + nonce\n + body\n （三行，末行也以 \n 结尾）
4. 验签：
   - Wechatpay-Serial 形如 PUB_KEY_ID_数字串 → 用微信支付公钥验签
   - 否则 → 用对应平台证书验签
   - SHA256 with RSA
5. 验签通过 → 立即返回 200/204（无包体）
   验签失败 → 返回 4xx/5xx + {"code":"FAIL","message":"..."}
6. 应答后再异步处理业务（解密、落库、更新状态）
```

**5 秒内必须应答**（商家转账/支付成功回调均要求），业务逻辑异步化。

### 6.2 解密

`AEAD_AES_256_GCM`，用 **APIv3 密钥** + `resource.nonce` + `resource.associated_data` 解密 `resource.ciphertext`。

- 商家转账解密后字段：`out_bill_no` / `transfer_bill_no` / `state` / `mch_id` / `transfer_amount` / `openid` / `fail_reason` / `create_time` / `update_time`
- 支付成功解密后字段：`out_trade_no` / `transaction_id` / `trade_state` / `trade_type` / `amount` / `payer.openid` / `success_time` / `attach`

### 6.3 重放与重入

- **同一通知可能多次发送**，必须幂等
- 处理前先检查业务数据状态：未处理→处理；已处理→**直接返回成功**
- 状态检查与处理之间**加数据锁**并发控制，避免函数重入造成数据混乱
- 建议建 `wxpay_notify_log` 表，以通知 `id`（`EV-...`）做唯一索引，天然去重

### 6.4 通知频次（用于设计兜底查单节奏）

| 类型 | 重试策略 |
| --- | --- |
| 商家转账 | 0s / 15s(×3) / 300s(×3) / 1800s(×3) / 1h(×22) |
| 支付成功 | 15s/15s/30s/3m/10m/20m/30m/30m/30m/60m/3h/3h/3h/6h/6h，最多 15 次 |

> 微信**不保证通知最终成功**。兜底查单是必选项，不是可选项。

### 6.5 回调网络白名单

若服务器有防火墙/安全组策略，需放行微信支付回调 IP 段（上海/深圳/香港电信联通 CAP 出口网段、广州腾讯云 IP，以及退款/分账、风险订单通知 IP）。完整列表以官方文档「回调通知注意事项」为准。

### 6.6 签名探测流量

微信会**极少数**返回以 `WECHATPAY/SIGNTEST/` 开头的**错误签名**以探测商户是否正确验签。

- **不得**对该前缀做特殊放行/特殊处理，必须走正常验签流程 → 验签必然失败 → 返回 4xx/5xx
- 用途仅在于排障时识别

> 已实际注册并校验通过的路由路径（含前缀）：
> `/api/wxpay/rewards/`、`/api/wxpay/rewards/stats`、`/api/wxpay/rewards/{reward_id}`、

> `/internal/wxpay/rewards/grant`。

`/withdraw` 响应约定（前端据此决定弹确认页还是提示）：

| `action` | 含义 | 前端动作 |
| --- | --- | --- |
| `confirm` | 有待确认转账单（新建或复用） | 用返回的 `package` 调起 `requestMerchantTransfer` |
| `processing` | 转账单处于其它非终态 | 提示「处理中，请稍后再试」，轮询 `/rewards/{id}` |
| `expired` | 奖励已失效 | 提示失效，不展示提现按钮 |

### 8.3 幂等约定

- `out_trade_no` / `out_bill_no` 由 FastAPI 侧生成，规则：`{业务前缀}{yyyyMMdd}{业务ID}{seq}`，全局唯一
- **`out_bill_no` 每次新建转账单都必须是新值**（含失败重试），禁止复用
- Go 服务对 `create` / `prepay` 做幂等键（同 `out_*_no` + 相同参数 → 返回首次结果）
- **提现入口幂等以 `reward_id` 为键**：同一 reward 并发提现只产生一笔非终态转账单（分布式锁 + `(reward_id, is_terminal)` 校验）
- 回调侧以 `notify_id` 唯一索引去重
- 奖励发放以 `(source_type, source_id)` 唯一约束防重复发放

### 8.4 FastAPI 侧核心流程

#### 8.4.1 提现三分支决策（`POST /api/wxpay/rewards/{id}/withdraw`）

单一入口，内部按「当前有效转账单」状态分流。**必须先查单再决策，绝不可直接建单**。

```python
async with 事务:                                   # 全程持有行锁
    reward = SELECT * FROM reward_record WHERE id=? AND user_id=? FOR UPDATE   # 行锁防并发
    if reward.status in (SUCCESS, EXPIRED): -> 终态，拒绝
    if reward.expire_at < now:               -> 置 EXPIRED，拒绝
    if reward.amount < MIN_WITHDRAW_FEN:     -> 拒绝（低于最低提现金额）

    bill = 最新一笔非终态 transfer_bill
    if bill is None:
        -> 分支 C：新建（生成新 out_bill_no）→ 调 Go create → 落 bill → 返回 package_info
    elif bill.state == WAIT_USER_CONFIRM and bill.package_expire_at > now:
        -> 分支 A：复用 package_info（不建新单）→ 直接返回
    else:
        -> 分支 B：先调 Go 查单刷新
           - 刷新后仍非终态            -> 返回 action=processing
           - 刷新后为 WAIT_USER_CONFIRM -> 复用 package_info
           - 刷新后为终态              -> 换新 out_bill_no 重建
```

- **行锁方案**：`SELECT ... FOR UPDATE` 锁 `reward_record` 行，同一 reward 的并发提现串行化；无需额外引入分布式锁
- **包内字段**：`out_bill_no` 每次新建都必须全新，规则 `{prefix}{yyyyMMddHHmmss}{seq8}`，仅数字+字母
- 🔴 该事务内**只允许存在一笔非终态转账单**，是防重复出资的最后一道闸

#### 8.4.2 回调接收（`POST /internal/wxpay/notify/transfer`）

```
1. 校验 X-Internal-Token（失败 401）
2. INSERT wxpay_notify_log(notify_id UNIQUE)  → IntegrityError 即重复通知，直接返回 200
3. 按 out_bill_no 找 transfer_bill
   - 找到：若已终态则保留终态不回退（防乱序通知），否则更新 state / fail_reason / update_time
   - 未找到：补建一条 bill 记录（回调先于本地落库的极端场景）
4. 按 reward_id 回写 reward_record.status（映射规则见 4.2）
5. 提交；记录 processed 状态
```

- **必须返回 2xx**，否则 Go 侧会应答 5xx 触发微信重试
- 该接口**无 JWT 登录态**，仅靠内部 Token 鉴权，且**不应暴露到公网**

#### 8.4.3 后台定时任务（`tasks.py`）

| 任务 | 周期 | 动作 |
| --- | --- | --- |
| 兜底查单 | 10 min | 非终态 `transfer_bill` 调 Go 查单刷新；`SUCCESS` 则回写奖励为「已到账」 |
| 奖励过期 | 1 h | `status=PENDING` 且 `expire_at < now` → `EXPIRED` |
| 一致性巡检 | 10 min | `reward=WITHDRAWING` 但无「非终态 bill」→ 回退 `PENDING`；非终态 bill 停留超 48h → 告警 |

> 微信**不保证回调送达**，兜底查单是必选项。转账单仅支持查询 **30 天内**，超期需走资金账单对账。

## 9. 安全设计

| 项 | 措施 |
| --- | --- |
| 商户 API 私钥 | 仅存于 Go 服务所在主机的受限目录（`0600`），**绝不进 Git / 环境变量明文 / Python 配置** |
| APIv3 密钥 | 同上；用于回调解密，泄露等于回调内容可被解密 |
| 微信支付公钥 | 官方推荐，长期有效；验签 + `user_name` 加密均用它（替代 5 年一换的平台证书） |
| 接口安全 IP | 商户平台配置 Go 服务**出口 IP**；密钥泄露后非白名单 IP 也无法调用 |
| 回调真实性 | 强制验签 + 解密 + 校验 `mchid`/金额/单号与本地一致，防「假通知」 |
| 内部接口 | `X-Internal-Token` + 仅内网监听（`127.0.0.1` 或内网网卡） |
| 回调路径 | 不做登录态校验（微信无登录态）；不放公网鉴权中间件 |
| 日志 | 打印 `Request-ID`（微信侧请求唯一标识，排障必用）；**禁止**打印私钥、APIv3 密钥、解密后的姓名明文 |
| 传输 | 全链路 HTTPS；回调 `notify_url` 必须为 `https://` 公网地址 |
| 出账风控 | 转账前校验：单笔/单用户单日/单日额度、用户实名、业务单据状态机；异常频次告警 |

## 11. 风险与强制注意事项

### 🔴 资金类（最高优先级）

1. **禁止「换单重试」**。接口返回非 200、或遇到 `SYSTEM_ERROR` / 新错误码时，**必须先用原 `out_bill_no` 查单**，明确为 `FAIL` / `CANCELLED` 后才换单重试。否则会造成**重复转账**。
2. **同一笔奖励不得存在两笔非终态转账单**。所有提现入口必须先走 4.3 三分支决策；并发以 `reward_id` 加锁。这是本形态下**最可能的资损点**。
3. **奖励发放时不得创建转账单**。`package_info` 24h 过期且资金立即锁定，提前建单必然关单退款并白占额度。
4. `ACCEPTED` 状态需检查运营账户余额，余额不足充值后**用原单号原参数重试**。
5. 撤销接口返回成功**仅代表受理**，需查单确认最终状态。
6. 回调**必须验签**才可信任内容；未验签直接更新业务状态＝资损入口。
7. 转账为**资金出账**，建议接入审批流 / 二次确认，并对单日累计出账做硬阈值熔断。

### 🟠 工程类

8. `transfer_amount` / `amount.total` **单位为分**，与前端元值转换处需统一且可测试。
9. `out_bill_no` **只能数字+大小写字母**；`out_trade_no` 6-32 字符（允许 `_ - | *`）。二者规则不同，生成器需分别校验。
10. 查询转账单**仅支持 30 天内**，超期需走资金账单对账。
11. 电子回单需同时满足：转账成功 + 传入过姓名 + 6 个月内。
12. 前端 `requestMerchantTransfer` / `getBrandWCPayRequest` 返回 `ok` **均不代表资金到账**，一律以回调+查单为准。
13. 红包样式 `RED_PACKET` 要求**单笔 ≤ 200 元**且仅部分场景支持。
14. 单笔 ≥ 2000 元**必须**传 `user_name`（RSA-OAEP 加密）；需确认 `users.name` 是否为真实姓名。
15. **报备信息「活动名称」+「奖励说明」必须落库**，缺一报 `PARAM_ERROR`；`reward_record.scene_name` / `reward_desc` 为必填。
16. **奖励状态必须由转账单推导**，不可在回调里直接把微信 `state` 写进 `reward_record.status`（两者取值域不同）。
17. 微信**不会主动推送收款确认消息**，「提现中」状态须有可见入口，建议配合服务号模板消息提醒。
18. `package_info` 失效后「去确认」必须走查单分支，禁止把过期 `package` 直接下发给前端。

### 🟡 运维类

19. 商户 API 证书**只能下载一次**，遗失需重新申请；私钥与 APIv3 密钥泄露须立即更换。
20. 未设置 APIv3 密钥时，微信支付**不会发送回调通知**。
21. 反向代理/CDN 可能过滤微信支付的扩展 HTTP 头，导致验签头缺失；需检查代理配置或直连。
22. 需配置定时任务巡检：`reward_record.status = 提现中` 但转账单已终态 / `package_expire_at` 已过期 的不一致数据，并自动回退为「待提现」。
23. 单日额度告警：单日累计出账接近 5 万、单用户单日接近 2000 元时告警，避免大面积 `NOT_ENOUGH` 失败单。
