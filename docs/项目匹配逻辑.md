# 项目匹配逻辑（通用规则）

> 适用于 AI 对话中「用户提到项目 → 系统识别 → 提单/回答预填」的场景。
> 实现位于 `ai/agents/AiDiagnosisPlatform/pipeline.py`（`_match_project_mention` / `_ambiguous_project_candidates`），本文是脱离代码的规则记录。

## 一、总原则

1. **宁空勿错，绝不猜**：识别收敛才预填；没收敛就反问或让用户选；任何时候不从多个候选里挑一个替用户决定。
2. **意图判断全交 LLM，机械判定归服务端**：抓什么词、怎么反问是 LLM 的事；「候选是否唯一、歧义是否成立」是确定性代码的事，不掺模型随机性。
3. **每个格子有兜底**：对话识别 → 反问 → 编号选择题 → 弹窗必选，四层防线，最坏情况用户总能自己选。

## 二、三层架构

```
用户说话
  │
  ▼
① 触发层（LLM）：从原话里"照抄"项目提及 ──不做任何判断
  │
  ▼
② 匹配层（服务端，确定性）：原话 × 项目池 → 唯一命中 / 歧义候选 / 拒收
  │
  ▼
③ 应用层：预填 / 反问 / 编号题 / 弹窗必选
```

### ① 触发层（LLM 抓词）

- 规划器每轮带 `mention_project` 工具，规则只有一条：**疑似提到公司/客户/场地/产品/项目就调，`project_name` 照抄用户原话，不要自己判断对应哪个项目，拿不准也调**（服务端会校验）。
- 为什么照抄不清洗：LLM 抠不干净简称——用户说「河南东昇那个潜伏车项目」，LLM 可能报「河南东昇那个潜伏车项目」整段或「东昇」片段，清洗规则追不上，让服务端枚举兜底。
- 指代支持：`project_name="last"` 表示「上次提单的项目」，从上一单提交记录直接取（真实数据无需校验）。

### ② 匹配层（确定性判定，核心算法）

输入：`mention`（用户原话）× `pool`（项目池 = 名下项目 + 票史候选）。

**第 0 步：快速路径**
- 提及为空 / 单字 → 拒收。
- 与某项目 `name` 或 `code` **完全相等** → 直接命中。

**第 1 步：子串枚举唯一指代**
- 枚举原话所有 ≥2 字子串，对每个子串查「项目名包含它的项目数」。
- 恰好 1 个项目包含 → 该子串是「唯一指代」，记下该项目。
- 收集所有唯一指代的项目（去重）：
  - **恰好 1 个 → 命中**（带修饰的原话如「河南东昇那个潜伏车项目」靠这步兜住）。
  - **≥2 个 → 歧义**（如「安吉中力」同时唯一指代智芯/富阳/AGV-USP…）。

**第 2 步：歧义候选判定（决定反问还是拒收）**

| 条件 | 结论 |
|---|---|
| 精确匹配已过 | 无需反问（已命中） |
| 唯一指代 ≥2 | 返回这些候选 → **反问** |
| 无唯一子串，但整体/子串命中 2~8 个项目 | 返回命中项目 → **反问**（覆盖「安吉」「中力」这类 2 字模糊词：抠不出更小的唯一词，但命中范围可读） |
| 命中 >8 个（高频词如叉车/潜伏车/仓储） | **拒收，不反问**——列表太长不可读，交编号题/弹窗兜底 |
| 零命中 | 拒收（不是项目名） |

### ③ 应用层（识别结果怎么用）

| 识别结果 | 对话流提单 | 点「转工单」按钮 |
|---|---|---|
| 唯一命中 | 跨轮持久化，提单意图出现时提升为**预填**，跳过项目题 | 弹窗**预填** + 提示"可修改" |
| 歧义（2~8 候选） | **自然语言反问**列出候选（话术由回答 LLM 生成，持续注入直到确认或跑题）；确认轮在候选池/全池再唯一命中 → 提升 | 弹窗项目**空白**，用户必选（绝不猜） |
| 拒收（高频词/无命中） | 提单闸门出**编号选择题**（服务端模板：票史项目优先 + 名下项目补位，≤5 个；回序号或全名经校验池还原） | 弹窗项目空白，用户必选 |
| 指代"上次的" | 从上一单提交记录直接取 → 预填 | 同预填 |
| 完全没提项目 | 同"拒收"：编号选择题 | 弹窗项目空白，用户必选 |

### 反问交互细节

- 歧义发生轮：服务端挂起候选 + 向回答 LLM 注入「项目待确认」资料块 → LLM 自然语言反问（列出候选、引导用户给**客户名或项目关键词**，不要臆断选一个）。
- 挂起期间**跨轮持续注入**：用户没答项目前每轮都带反问语境；用户转移话题则 LLM 判断不再追问。
- 确认轮：用户回的具体标识先在**候选池**里做唯一匹配（池小更易收敛），全池兜底。
- 边界：用户只回「第一个」这类**序号**（无项目名）→ 规划器不触发提及、服务端无词可匹配 → 解析不了。反问话术引导"说客户名或关键词"即自然规避；真发生了走编号题/弹窗兜底，不误收。

## 三、状态生命周期

| 状态 | 语义 | 清理时机 |
|---|---|---|
| `mentioned_project`（唯一命中） | 人的属性，跨轮/跨话题持久 | 提升为预填时；提交成功；取消提单。**换话题不清**（用户换问题不换身份） |
| `ambiguous_project_candidates`（歧义挂起） | 话题级临时澄清状态 | 确认命中；预填消费；取消提单；提交成功；LLM 判定换新话题。**五处必清**，否则上一话题的歧义污染下一单 |
| `pending_prefill_project`（预填） | 单向管道：mentioned → 弹窗 | 弹窗生成即消费；提交/取消清 |

- 提交收尾（`_reset_state_after_submit`）对话路径与按钮路径**共用同一份函数**，保证两条路清理行为永远一致。
- 下一单从零重新捕捉，绝不继承上一单的项目/歧义。

## 四、已知边界与风险

| 边界 | 处理 |
|---|---|
| 序号式确认（"第一个"） | 解析不了；反问话术引导规避 + 弹窗兜底 |
| 高频词大池（>8 命中） | 不反问（列表不可读），编号题/弹窗兜底 |
| 规划器偶发失败（flash 超时/兜底） | 该轮不识别，下一轮用户再提即恢复；自动化测试须带重试 |
| 挂起反问烦人风险 | 靠"用户转移话题不再追问"话术约束；属软约束，观察线上反馈 |
| 2 字模糊词 | 第 2 步第 3 分支专门覆盖（整体命中 2~8 即反问） |

## 五、性能口径

子串枚举为 O(|原话|² × 池大小) 朴素扫描。实测 150 项目池：中位 34~90µs，最坏长原话 ~0.6ms，相对每轮 LLM 调用（秒级）可忽略。池涨到数千再考虑倒排索引优化。
