## 二、服务端口与路由分发

```
客户端请求
  │
  ▼
nginx (HTTPS 443)
  ├── /api/ai/*    → AI 服务 (ai/run.py :8401)
  ├── /api/*       → 业务后端 (backend/main.py :8400)
  └── /*           → 前端 SPA (Vite / 静态文件)
```

| 服务 | 开发端口 | 路由前缀 | 说明 |
|------|---------|---------|------|
| 业务后端 | 8400 | `/api/auth` `/api/admin` `/api/tasks` `/api/call` `/api/wechat` | FastAPI, MySQL 直连 |
| AI 服务 | 8401 | `/api/ai/qa` `/api/ai/chat` `/api/ai/memory` `/api/ai/task` `/api/ai/ticketReferee` | FastAPI, 独立 MySQL 连接 + Qdrant |
| 前端 | 5173 (dev) | `/` | React SPA, vite proxy 代理 API |

### 3.4 仪表盘首页（Dashboard）数据契约 —— 待后端接入

> 本节由前端先行设计接口契约（`frontend/src/api/dashboard.ts`），后端按此契约实现即可对接，无需再对齐字段名。所有接口未就绪前，前端一律优雅降级为 0/空列表展示，不阻塞页面渲染。

**上段·工单状态监测概览**

- `GET /api/admin/dashboard/tickets/summary` → `{ code: 0, data: { total, pending_count, overdue_count, resolved_rate, by_status: { new, in_progress, paused, resolved, closed, cancelled } } }`
  - 数据源建议：系统任务模块 `tasks` 表按 `TaskStatus` 分组统计；`overdue_count` 依据 `deadline_at < now()` 计算（字段已存在，见 `backend/app/models/task.py`）
  - ⚠️ **状态口径缺口**：产品要求 6 个状态（新建/处理中/暂停挂起/已解决/已关闭/已取消），但当前 `TaskStatus` 枚举只有 5 个值，**没有「暂停/挂起」「已取消」对应值**。`backend/app/integrations/sources/zentao/mapper.py` 里禅道同步已经把外部的 pause/cancel 分别映射到 pending/closed，说明这两个状态是真实存在的业务需求，只是平台枚举未落地。后端接入前需先决定：扩展 `TaskStatus` 枚举，还是继续复用 pending/closed 语义合并
- `GET /api/admin/dashboard/tickets?status={key}` → `{ code: 0, data: { items: [{id, title, status, priority, assignee_name, created_at}], total } }`

**中段·跨项目看板**

- `GET /api/admin/dashboard/projects/summary` → `{ code: 0, data: { total, by_stage: { pre_sales, bidding, negotiation, contract_signed, factory_test, pending_entry, delayed_entry, in_implementation, implementation_suspended, in_trial_operation, acceptance_operation, project_suspended, project_terminated, project_changed, project_ended } } }`
  - 数据源（后期）：企业微信智能表格同步的调度项目数据（产品需求原文）；过渡期可由现有 `projects` 表 `status` 字段聚合
  - ⚠️ **枚举口径缺口**：产品要求 15 个调度阶段，当前 `ProjectStatus` 枚举（`backend/app/modules/admin/schemas_das/request_models.py`）只有 13 个值，且存在语义偏差：
    - 缺失 4 项：投标阶段、项目暂停、项目终止、项目变更
    - 现有「项目中止」与目标的「项目暂停」/「项目终止」语义重叠，需产品与后端对齐是重命名还是拆分为两个状态
    - 现有「实施运行」不在目标 15 项中，需确认去留
- `GET /api/admin/dashboard/projects/urgency` → `{ code: 0, data: { by_urgency: { important_urgent, urgent_not_important, important_not_urgent, not_important_not_urgent } } }`
  - 数据源：`projects` 表 `category_basis` 字段（已存在，见 `backend/app/models/delivery.py`），仅需新增按该字段 group by 的聚合接口，属于本周可低成本落地项，无枚举缺口
- `GET /api/admin/dashboard/projects?stage={key}` 或 `?urgency={key}` → `{ code: 0, data: { items: [{id, project_code, name, status, contact_person}], total } }`

## 四.x 对象存储（MinIO）本地开发配置

头像上传、评论附件等走对象存储。本地直连 MinIO 需先启动服务并正确配置前缀（相关修复见本次提交）。

### 启动 MinIO（Windows）

**方式 A：Docker（推荐）**

```powershell
docker run -d --name minio `
  -p 9000:9000 -p 9001:9001 `
  -e "MINIO_ROOT_USER=minioadmin" -e "MINIO_ROOT_PASSWORD=minioadmin" `
  minio/minio server /data --console-address ":9001"
```

**方式 B：minio.exe 直跑（无需 Docker，最省事）**

先下载二进制（已确认 `dl.min.io` 可达；Docker 镜像源 `mirror.ccs.tencentyun.com` 对大镜像会 `EOF`，故不推荐 Docker）：

```powershell
Invoke-WebRequest -Uri "https://dl.min.io/server/minio/release/windows-amd64/minio.exe" -OutFile "D:\minio.exe"
```

启动前设好 root 凭据（与 `.env` 的 `MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY` 一致；新版 minio 必须用 `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD`）：

```powershell
$env:MINIO_ROOT_USER="minioadmin"; $env:MINIO_ROOT_PASSWORD="minioadmin"
D:\minio.exe server D:\minio-data --address ":9000" --console-address ":9001"
```

# 不想占用窗口可后台启动（日志写 D:\minio.log）：
```powershell
$env:MINIO_ROOT_USER="minioadmin"; $env:MINIO_ROOT_PASSWORD="minioadmin"
Start-Process -FilePath "D:\minio.exe" -ArgumentList "server","D:\minio-data","--address",":9000","--console-address",":9001" -WindowStyle Hidden -RedirectStandardOutput "D:\minio.log"
```

凭据默认 `minioadmin/minioadmin`，需与 `.env` 的 `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` 一致（当前仓库 `.env` 已填 `minioadmin/minioadmin`）。

### 关键配置 `MINIO_API_PREFIX`

- 代码（`minio_client.py`、`resource_manager/api/minio.py`）原本**写死**请求路径前缀 `/minio-api`，该前缀是为**生产环境 nginx 网关**（`deploy/nginx/conf/nginx.conf` 的 `location /minio-api/`）设计的。
- **本地直连 MinIO 时不能带此前缀**，否则请求路径会变成 `/minio-api/bucket`，而 MinIO 原生 S3 API 无法识别，导致上传/下载失败（典型现象：`GET /minio-api/helpdesk?location=` 404 或签名错误）。
- 已将前缀改为可配置项 `MINIO_API_PREFIX`：本地 `.env` 留空 `""`，生产部署设为 `/minio-api`。
- 应用启动时（`app/__init__.py` 的 startup 事件）自动调用 `ensure_minio_buckets()` 创建 `helpdesk`、`helpdesk-comment`、`helpdesk-images` 等 bucket；MinIO 未启动仅打印告警、不阻塞应用启动。
- 对话附件上传接口（`ai/api/router.py` 的 `/api/ai/qa/upload`）的对象路径原本**写死** bucket 名为 `helpdesk`、不读配置；现已改为统一读取 `settings.MINIO_BUCKET`，因此与上述 `ensure_minio_buckets()` 自动建桶逻辑保持一致（生产端 `MINIO_BUCKET` 的值即为附件桶名，例如 `.env.example` 中的 `usp-helpdesk`）。
- **排查提示**：上传的附件**不在应用服务器本地磁盘**，而是落在 MinIO 对象存储中。真实查看路径为 `s3://{MINIO_BUCKET}/{session_id}/{文件名}`（`MINIO_BUCKET` 默认 `helpdesk`），可通过 MinIO 控制台（`:9001`）、`mc` 客户端（`mc ls local/{MINIO_BUCKET}/{session_id}/`）或后端返回的**预签名 URL**（有效期 24h）访问。若生产 MinIO 为独立远程服务，文件在 MinIO 服务器侧、不在应用服务器。

### 故障自检

上传报 `WinError 10061 由于目标计算机积极拒绝，无法连接` → MinIO 服务未在 `localhost:9000` 监听，按上方「启动 MinIO」操作即可。
