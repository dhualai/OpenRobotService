## 1. 本文解决什么问题

本系统一期跨「工单状态机 + 归档审核 + 奖励记账 + 微信提现 + 排名运营 + 前端多页面」，
参与人数多、各自的 AI 会话互相看不到对方上下文。若不约束，必然出现：

- 同一功能两个人各写一套接口（重复造轮子）；
- 表名/字段名/状态值/权限码各写各的，合并时冲突；
- 金额单位、幂等键、状态取值不一致，导致**重复发钱或漏发钱**；
- ORM 表定义没放进唯一归属目录，Alembic 看不到表；
- 前端页面绕过既有请求工厂/权限体系，风格分裂。

本文用「**先给现状、再给强制口径、最后给禁止清单**」的方式收敛这些风险。

## 3. 一期范围与非目标

**做什么**（一期）：工单关闭后选择进入知识审核 → 结构化解答报告 → 双盲审核 + 审核意见/价值点 →
审核通过生成单题奖励 → 月度排名奖励 → 优质问题点赞排名与期末结算 → 奖励提现 → 后台运营模块。

**明确不做**：

- 不新建独立的「提问—回答—审核」流程，全部挂在现有工单闭环上；
- 不做多期/第二批切换页面（后端可留 `campaign_code`，一期固定一个值）；
- 不在审核接口里直接发起支付（见 §5.2）；
- 不实现需求文档里「账户余额输入金额提现」的新形态，除非第 14 节该条决策完成（现状是**逐笔奖励提现**）。

### 4.2 奖励记账与微信提现（资金链路，已落地）

| 能力 | 位置 |
|---|---|

| 后台「奖励管理」页 | `frontend/src/pages/admin/WxpayRewardManage.tsx` |

**必须知道的既有事实**（决定了知识激励怎么接）：

1. `reward_record.amount` **单位是「分」**，整数，不接受元/浮点。
2. 防重复发放靠唯一键 `uq_reward_source(source_type, source_id)`（`models/wxpay.py:122`）。
   → **单题/月度/优质问题三类奖励各用一个 `source_type`，`source_id` 拼接业务主键**，
   这样才能「合法叠加」且「同类不重复入账」。
3. 发放奖励**不建转账单**；只有用户点「立即提现」才建单，且同一时刻至多一笔非终态转账单
   （防重复出资的关键约束）。
4. 提现形态现状是 **按奖励记录逐笔提现**，不是「账户余额 - 输入金额」。
   需求文档 §9.2 描述的是后者 → 见第 14 节待决策。
5. `RewardRecord.status` 由「当前有效转账单」推导，**禁止**把微信侧状态直接写进奖励表。

## 5. 代码分区与模块归属

**唯一的模块划分口径**（照此放，不要新建顶层目录）：

| 业务 | 归属 |
|---|---|
| 审核流转（进入审核、报告、双盲、通过/驳回） | `backend/app/modules/tasks/`（扩展 `api/archive_report.py`、`schemas/`、`models/task.py`） |
| 奖励、提现、排名、运营展示、审核人员名单 | `backend/app/modules/admin/`（新增 `api/knowledge_incentive.py` 等） |
| 微信支付/转账 | `backend/app/modules/wxpay/`（**已有**，只扩展不重写） |
| 用户侧「我的奖励」 | `frontend/src/pages/rewards/` |
| 后台运营页 | `frontend/src/pages/admin/` |
| ORM 模型 | `backend/app/models/`（**唯一定义点**） |

### 5.1 分层硬约束

- 路由层（`api/`）只做参数校验、鉴权、事务编排；业务逻辑进 `services/`。
- 跨模块调用走 `services/`，不要在 `api/` 里互相 import 对方 router。
- 前端**不直连**任何支付/转账接口；提现只走既有 `frontend/src/api/wxpay.ts`。

### 5.2 支付调用红线（最高优先级）

审核接口 `approve` 只允许做四件事：

1. 完成审核事务；2. 生成奖励流水（`RewardService.grant`）；3. 更新业务状态；4. 返回结果。

**严禁**在审核、排名、结算接口中直接调用微信转账 API。
到账一律由用户提现触发或异步任务处理（见 `backend/docs/微信支付接入技术方案.md` §4.3、§8.4）。

| 需求文档建议码 | 落地码（强制） | 用途 |
|---|---|---|
| `backend:tasks:knowledge_review` | `frontend:admin:knowledge-review:show` | 审阅知识报告（若审核在「系统任务」内，可复用任务权限） |

- 每个新权限码必须：① 在 `IdentityService.add_permission` 注册；② 有 `ensure_xxx_permission()` 幂等函数；
  ③ 前端权限常量从对应 `api/*.ts` 导出；④ 在 `AdminEntries`/`AdminLayout` 做可见性过滤。

### 6.2 路由前缀

- 用户侧：`/api/...`（在 `backend/app/__init__.py` 挂载，`settings.API_V1_STR`）。
- 管理侧：`/api/admin/...`（挂在 admin router 下，如现有公告 `router` 定义在 `announcement.py:33`）。
- 命名用**复数名词**（`/announcements`、`/reward-records`），动作型子路径用动词（`/publish`、`/offline`、`/approve`）。

### 6.3 响应结构

沿用仓库既有形态，不要引入新风格：

- 单条：`{"ok": true, "item": {...}}`
- 列表：`{"total": <int>, "items": [...]}`
- 动作：`{"ok": true, ...}`，失败用 `HTTPException(status_code=..., detail="中文提示")`。

### 6.4 状态值

- 用**小写字符串** + `class XxxStatus:` 常量类（同风格见 `announcement.py:15`、`models/wxpay.py:34`）。
- **不要用 DB Enum**（仓库既有做法是字符串列，避免枚举增删的迁移成本）。
- 对外输出统一 `.value`（SQLAlchemy Enum 值可能是枚举对象，见 `task.py:889` 的写法）。

### 6.5 前端

- 所有请求走 `createRequest`，地址进 `config/api.ts`；不要写裸 `fetch`/`axios`。
- 列表页与详情页的加载态、失败态要显式处理；**增强型模块（公告条、点赞）失败须静默降级**，不能打断主流程。
- 乐观更新（点赞、状态切换）必须**有失败回滚 + 防连点**，参考 `shared/hooks/useTaskLike.ts`。
- 路由懒加载用 `lazyImport`（`main.tsx` 既有写法）。

## 7. 数据模型与迁移强制口径

### 7.1 表与字段

- 新表/新字段命名沿用现有风格：表名复数蛇形（`reward_record`、`announcements`）、布尔字段 `is_xxx`、
  时间字段 `created_at/updated_at/published_at/archived_at`、外部主键 `user_id/task_id/report_id`。
- **金额一律 `Integer`、单位「分」**，字段名带 `_fen` 或 `amount`（与 `reward_record.amount` 对齐，二选一并全库统一）。
- 外键统一声明 `ondelete` 语义（如 `task_likes.task_id` 用 `CASCADE`）。

### 7.2 幂等键（资金相关，强制）

任何会「产生钱」的记录，必须有能表达业务唯一性的唯一约束，且**粒度不能过粗**：

- 单题奖励：`(campaign, task_id, user_id, reward_type)`
- 月度奖励：`(campaign, month, user_id, reward_type)`
- 优质问题奖励：`(campaign, settlement_batch, task_id, user_id, reward_type)`

映射到现有基座：用 `reward_record.source_type` 区分奖励类型，`source_id` 承载「任务/月份/批次 + 用户」的组合串，
由唯一键 `uq_reward_source` 兜底。**禁止只按 user_id 或 task_id 去重**（会误拦合法叠加奖励）。

### 7.3 Alembic 迁移

- 迁移脚本目录：`backend/alembic/versions/`；`down_revision` 必须接**当前唯一 head**（改前先 `alembic heads` 确认）。
- ⚠️ **本项目约定：迁移脚本只在本地保留，不推远端**（远端由专人执行数据迁移）。
  不要把迁移文件 `git add` 进 PR；漏提交是**故意的**，不是遗漏。
- **迁移脚本必须幂等**：先查 `information_schema.tables` 再建（参考 `a3c7e91b4d20_add_announcement_and_task_like.py:29`），
  因为应用启动的 `create_all` 可能已经建过表。

### 7.4 部署门禁约束（决定了新列怎么写）

线上结构由部署流水线的结构同步门禁（`backend/scripts/schema_sync.py`）比对并自动补齐，能力边界：

- **可自动补**：可空 或 带 `server_default` 的新增列；缺失索引（含 UNIQUE）。
- **会阻断部署（人工处理）**：`NOT NULL` 且无 `server_default` 的缺列、主键/自增列缺失。
- **只告警不自动改**：类型/长度不一致、库中多余的旧列。
- **不处理**：删列/改名/改类型、外键与 CHECK、数据回填。

→ **结论（强制）**：新增列一律**可空或带 `server_default`**，否则上线即被门禁阻断。

## 8. 状态机口径

### 8.1 工单 + 知识审核（扩展既有链路）

```text
new → in_progress → resolved → closed
                                  ├→ closed（不进入知识审核，无奖励）
                                  └→ archiving（接单人填解答报告）
                                           ├→ submitted
                                           │    ├→ archived（审核通过 → 生成奖励）
                                           │    └→ archiving（驳回补充）
                                           └→ invalid（判定无效，不计入）
```

`Task.status` 管工单主状态，`ArchiveReport.submit_status` 管报告审核状态，两者组合，**不要偷偷新增第三套状态字段**。

### 8.2 资金状态

```text
奖励流水：created → credited → frozen → reversed（异常）
提现记录：pending → processing → success
                        └→ failed → pending
转账单（微信侧）：ACCEPTED/PROCESSING/WAIT_USER_CONFIRM/TRANSFERING → SUCCESS|FAIL|CANCELLED（终态）
```

余额变化与提现记录必须在**同一事务**内保持一致；余额变化必须有不可删除的流水。

## 9. 安全与风控红线

### 9.1 通用（12 条自检，每次生成代码前逐条过）

参数化查询（禁止字符串拼 SQL）｜命令用 argv 形式｜路径固定基目录 + 边界校验｜SSRF 白名单 + IP 校验｜
鉴权 + 属主校验｜强加密 + CSPRNG｜反序列化到具体类型｜XSS 自动转义｜重定向同源白名单｜
CORS 白名单｜上传扩展名 + MIME 校验｜日志脱敏（密钥/令牌/token/openid 不入日志）。

### 9.2 本系统特有（强制）

- **越权**：所有「我的奖励/我的点赞/我的报告」接口，身份一律由服务端从 token 解析（`actor_username(current_user)`），
  **不接受前端传 user_id**。
- **自赞排除**：提问人、解答人、审核人对**自己参与**的问题点赞不计奖（需求文档 §8.3.1）。
- **双盲脱敏**：审核人视角的接口**不得返回**提问人/接单人/公司/部门/项目/头像/账号；
  匿名编号替代身份；真实身份只在管理员审计链路可见。
- **审核人不可自审**：接单人不能审核自己的报告。
- **金额**：一律整数分；不接受前端传入的金额作为记账依据（金额由服务端按规则计算）。
- **幂等**：重复请求、取消后重推、接口重试都不能重复累计/重复出资。
- **奖励不可回滚删除**：只能新增反向流水（`reversed`），不要 `DELETE` 资金记录。

## 10. 测试与验证要求

**改了什么就必须跑对应的验证，未跑通不得声称完成。**

| 范围 | 命令 |
|---|---|
| 后端 | `cd backend && pytest --ignore=tests/tasks` |
| 前端单测 | `cd frontend && npm run test` |
| 前端类型检查 | `cd frontend && npx tsc -b`（**必跑**：vitest 走 esbuild 不查类型，类型错会卡在 CI 构建） |
| 自动化框架 | `cd automation && pytest` |

**必须覆盖的测试点（资金/权限类）**：

1. 幂等：同一奖励重复发放只入账一次；同一用户对同一问题重复点赞只计一次。
2. 叠加：单题 + 月度 + 优质问题三类奖励**互不拦截**（能被唯一键误拦是典型 bug）。
3. 越权：非属主调「我的 XXX」接口拿不到别人数据；审核人视角断言响应体里**没有**身份字段。
4. 状态流转：非法状态跳转被拒（如 `draft` 直接 `approve`）。
5. 金额：断言单位是分、边界（0、最小值）不错。

**测试写法规范**：

- 前端断言只认行为与语义，用 `testid` / `getByRole` / `aria-*`，**禁止断言类名与 `toHaveStyle`**。
- 后端测试 override 鉴权依赖时注意：`admin/api/auth.py:37` 有一个**同名**的 `get_current_active_user_from_token`，
  既要用 core 的依赖也要用 admin 的依赖覆盖，否则 401（教训来自公告接口测试）。

## 11. 协作流程（分支 / PR / 提交）

1. **一功能一分支**，从 `test` 拉，命名 `{模块}-{feature|fix|chore|docs|refactor|test}-{英文简述}`；
   完成后 PR 合入 `test` 并删除该特性分支。`zjl-dev` 只用于同步与本地预览，**不在其上开发**。
2. 多人并行时用独立 worktree（`orswt` 工具，目录 `D:\OpenRobotService\wt\<名>`），
   **不要在主仓工作区并行开发**（本仓常有多个会话同时操作，出现过提交落错分支、分支被删）。
3. 提交前**重新确认当前分支**（`git branch --show-current`）与提交身份（`git config user.name/email`）。
4. 提交信息用 Conventional Commits，中文描述；中文用 `git commit -F <utf8 临时文件>`，
   **不要用 `-m`**（PowerShell GBK 会双重编码）；不要 `git add -A`。
5. `test` 分支有保护规则（必须他人 approve，`--admin` 也绕不过），PR 开完记得找协作者点批准。
6. 一个需求一次提交全部改动，不要拆 hunk 反复确认。
