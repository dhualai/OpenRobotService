# 工单信息补全 + 派单中状态 + 编辑功能 设计方案（P0+P1 已实现）

> 2026-08-01 · 状态:**已评审通过并实现**（功能一 P0 + 功能二 P1；P2 留后续迭代）
> 涉及页面：历史工单详情(TicketDetailPage)、历史工单列表(HistoryTickets)、系统任务详情(TaskDetailPage)
> 涉及服务：AI 服务(router.py / task_adapter.py / pipeline.py)、业务后端(tasks 模块)

---

## 一、现状摸底（探查结论）

### 1.1 字段现状

| 字段 | tasks 表 | AI 详情接口(`/qa/ticket`) | 历史工单详情页 | 系统任务详情页 |
|---|---|---|---|---|
| 发起人 created_by(_name) | ✅ 有 | ❌ 两条路径都不返回 | ✅ 靠二次合并(tasks `GET /{id}`)补齐 | ✅ 直接返回 |
| 处理人 assigned_to(_name) | ✅ 有 | ❌ 不返回 | ✅ 二次合并补齐,空显示 `-` | ✅ `-` |
| 项目名称 project_name | ✅ 有(`project_name`/`project_id`,转单时强制非空) | ✅ 返回(`project`+`project_id`) | ❌ **接口类型+渲染都没有** | ✅ 已展示(L784) |
| 联系人 contact | metadata_info.contact | ✅ | ✅ | — |

关键不一致:**列表接口 `/memory/tickets/all` 已返回 created_by/assigned_to(+显示名),详情接口 `/qa/ticket` 却不返回**——详情页只能靠"再调一次 tasks `GET /{ticket_id}`"二次合并补救。

### 1.2 派单生命周期(异步)

```
转工单(submit)
  → upsert_task:status=new, assigned_to=空,无 dispatch_status 字段
  → 加入 Redis 待派单池 usp:pending_tickets
  → 后台 Worker 每 60s 扫描「source=ai AND status=new AND assigned_to 空」
  → 派单成功:assigned_to=username, status=in_progress, metadata_info 写入 assign_* 详情
```

- **没有显式 dispatch_status 字段**;"派单中"的隐式判断 = `source='ai' && status='new' && assigned_to 空`
- 派单窗口最长约 60s,期间用户看到处理人是 `-`,不知道在派单
- 手动创建的单(source≠ai)assigned_to 也可能空,但那是「未指派」,**不能与「派单中」混淆**

### 1.3 编辑现状

- 历史工单详情页:**无任何编辑能力**(只有催办/上报/撤回)
- 系统任务详情页:仅**标题+描述**可编辑(`PUT /api/tasks/{id}`)
- 后端 `PUT /api/tasks/{id}` 实际支持 16 个字段(priority/project_name/assigned_to/tags/...),权限:
  - admin 任意改
  - 非 admin 须是 **处理人/客户/创建人** 之一;`status` 变更有额外角色-状态矩阵(只改普通字段不受矩阵限制)
- **前端能力是后端能力的子集**——扩编辑字段基本不需要动后端

### 1.4 数据一致性陷阱(编辑功能的关键)

历史工单详情页主数据源是 **AI 接口的 Redis 副本**(`_build_ticket`),DB 只是二次合并。若编辑只写 DB,Redis 副本不更新 → **详情页仍显示旧标题/旧描述**。方案必须解决这个,否则编辑"看起来没生效"。

## 二、功能一:工单信息补全 + 派单中状态

### 2.1 字段补全

**方案 A(推荐):AI 侧补全 + 前端渲染**

| 层 | 改动 |
|---|---|
| AI `task_adapter.task_to_dict` | 补返回 `created_by`/`assigned_to`,并用 `UserService.get_user_map()` 解析 `created_by_name`/`assigned_to_name`(与列表接口口径一致) |
| AI `pipeline._build_ticket`(Redis 路径) | 按 ticket_id 查库补同样 4 字段(查不到则留空,前端二次合并兜底——已有逻辑) |
| 前端 `TicketDetailPage` | `AiTicket` 接口加 `project_name`;二次合并时从 tasks `GET /{id}` 取 `project_name` 一并合并;渲染加「所属项目」行 |
| 前端列表 HistoryTickets | 卡片加项目名小字(可选,评审点 ①) |

效果:详情接口与列表接口字段口径一致;发起人/处理人/项目名三个关键字段全展示。

**方案 B(最省事)**:只改前端——二次合并多取 `project_name`,AI 侧不动。
缺点:AI 详情接口依然缺人名字段(数据源不一致的坑留给后人),且 Redis 路径下若 `ticket_id` 缺失则人名仍空。**不推荐单独用,可作为 A 的兜底保留**。

### 2.2 「派单中」状态

**判断口径(隐式,不加新字段)**:
```
source='ai' && status='new' && assigned_to 为空  →  处理人位显示「派单中」
source≠'ai' && assigned_to 为空                  →  「未指派」(手动单,文案区分)
```

**展示位置**(3 处):
1. 历史工单详情页:人员流转卡片处理人位 → `派单中…`(可加呼吸点动画)
2. 历史工单列表:处理人列 `-` → `派单中`
3. 系统任务详情页:处理人行同上

**自动刷新(评审点 ②)**:
- 方案 i:详情页在「派单中」时每 5s 轮询 tasks `GET /{id}`,派单完成自动变为处理人+状态(最长 60s)。体验好,成本低(仅详情页、仅派单中才轮询)。**推荐**
- 方案 ii:纯静态展示,用户手动刷新。改动最小
- 列表页不轮询(行数多,轮询成本高)

**不做**:加显式 `dispatch_status` 列——隐式判断已够用,加列要动迁移+双写,过度设计。

## 三、功能二:工单编辑功能

### 3.1 分期

**P1(纯前端,后端 `PUT /{id}` 已支持,推荐先做)**

| 项 | 内容 |
|---|---|
| 历史工单详情页 | 加「编辑」按钮 + 编辑弹窗:标题、问题描述、优先级 |
| 系统任务详情页 | 编辑弹窗字段扩展:标题、描述 + 优先级 |
| 权限(与后端对齐) | admin / 创建人 / 处理人 可见编辑按钮;其他人隐藏 |
| 一致性 | 详情页可编辑字段(title/description/priority/project_name)展示**以 DB(tasks `GET /{id}`)为准**,Redis 只提供 diagnosis/ai_summary 等 AI 特有数据 —— 编辑后立即可见,无缓存不一致 |

**P2(需后端配合,后续迭代)**

| 项 | 内容 |
|---|---|
| 项目名称编辑 | 下拉选择(需项目列表接口),联动 `project_id`;防止手输造成 name/id 不一致 |
| 联系人/诊断字段(robot_type、fault_code 等) | 存于 `metadata_info` 嵌套 JSON,编辑需整体替换,风险大,需要专门接口 |
| AI Redis 副本同步失效 | 编辑接口通知 AI 侧清 `agent_state` 的 ticket 缓存(若 P1 已切 DB 为准,此项优先级降低) |

### 3.2 权限矩阵(评审点 ③)

| 角色 | 标题/描述 | 优先级 | 项目名(P2) | 状态 |
|---|---|---|---|---|
| admin | ✅ | ✅ | ✅ | 受现有矩阵 |
| 创建人(发起人) | ✅ | ✅? | ✅? | 受现有矩阵 |
| 处理人 | ✅(现状) | ✅? | ❌? | 受现有矩阵 |
| 其他人 | ❌ | ❌ | ❌ | ❌ |

说明:后端现状是「三者之一即可改全部普通字段」;前端可按上表收紧,也可与后端完全对齐(三者相同权限)。**建议 P1 先与后端对齐(简单),后续按需收紧**。

### 3.3 编辑入口交互

- 详情页头部加「编辑」按钮(与催办/上报/撤回同排,权限控制显示)
- 弹窗复用系统任务详情页现有编辑弹窗的交互(标题 input + 描述 textarea + 优先级 select)
- 保存成功 → 重新拉取 DB 详情刷新;失败 → toast 错误
- 终态工单(resolved/closed/canceled)禁止编辑(按钮置灰)——与后端 400 校验一致

## 五、评审点（已评审，结论见下）

1. **列表页要不要加项目名?** ✅ 加
2. **派单中要不要 5s 轮询自动刷新?** ✅ 要；但不能干巴巴一直显示「派单中」文字,要有动效让用户理解是进行中 → **定稿:处理人位显示「派单中」+ 呼吸点动效（复用 AI 呼吸点风格）,详情页 5s 轮询**
3. **编辑权限**:✅ 与后端对齐——admin/创建人/处理人 三种人都可改全部普通字段
4. **P1 编辑字段**:三项太少 → **扩充为 5 项:标题、描述、优先级、类型(ticket_type)、联系人(customer)**;项目名编辑仍留 P2（需下拉接口+project_id 联动）
5. **数据源切换**:✅ 认可「可编辑字段以 DB 为准、Redis 只供 AI 特有数据」
6. **派单中/未指派文案区分**:✅ 认可（`source='ai'` → 「派单中」;手动单 → 「未指派」）

## 六、评审结论（2026-08-01 定稿）

- **功能一 P0**:AI 侧 task_to_dict/_build_ticket 补人名 4 字段;前端三页展示项目名;「派单中+呼吸点」3 处;详情页 5s 轮询
- **功能二 P1**:历史工单详情页加编辑（标题/描述/优先级/类型/联系人,5 字段）,系统任务详情页编辑同步扩展;权限=admin/创建人/处理人;可编辑字段展示以 DB 为准
- **P2（后续迭代）**:项目名下拉编辑、联系人/诊断字段(metadata_info)、Redis 缓存同步失效
