# 后台知识贡献榜与匿名审核实现方案

## 1. 文档范围

- 更新日期：2026年10月15日。
- 需求依据：《机器人行业知识红包激励系统一期需求文档》及本次用户确认。
- 当前阶段：榜单、匿名审核和综合月榜核验入账已完成代码实现与隔离测试；2026-10-15 已在本机 dev 执行增量迁移并重启业务后端，未部署生产或同步外部平台。
- 原则：后台增加榜单及审核入口，复用系统任务的归档流程，不新建第二套内容审核。

## 3. 统计口径

### 3.1 活动资格与月份

按“历史数据不计入”的要求，使用工单创建时间和首次有效归档时间共同约束活动资格。2026年11月1日前创建的工单，即使活动期间归档，也不自动获得一期资格。

活动期间创建的工单还须正常关闭、报告审核通过、首次有效归档发生在截止前，且未判重复、违规或无效。历史知识保留原有查询能力，不自动进入活动问题榜单及结算。

贡献月份按首次有效归档时间确定。例如11月创建、12月通过的活动工单，计入12月，不计11月；多版报告、重复提交或重试不跨月重复计数。各端统一北京时间及自然月边界。

### 3.2 一个用户一个综合名次

按“总排名”理解为先以用户归并贡献，再比较用户：

> 综合贡献数 = 有效提单数 + 有效接单数

- 有效提单数按原始提问人归属；有效接单数按通过报告对应的解答人归属。
- 每种贡献按工单去重，不能按报告条数或审核次数累计。
- 同一用户提单、接单两种贡献共同进入综合榜，只占一个名次、领取一份月度奖金。
- 示例：甲提单4个、接单6个，综合为10；乙提单9个、接单0个，综合为9，甲在前。
- 同一用户同一工单双角色计1次还是2次仍需确认，不提前确定受其影响的最终奖励。
- 历史账号及用户ID混用通过现有身份归一机制归并到用户ID，不能形成重复榜单用户。

### 3.3 同分获赞与冻结

主排序为综合贡献数降序，第二排序为有效获赞数降序。

建议的获赞聚合方式：汇总该用户计入本月贡献的工单收到的有效点赞，同一工单在该用户下只汇总一次；不统计用户点赞他人的次数，不使用活动前或其他月份工单的获赞数。该聚合细节仍需在赛制中确认。

月末同时冻结贡献工单集合、贡献数及有效点赞快照。下个月新增或取消的点赞不直接影响已冻结月榜；发现异常后更正，应留下异常标记、修订版本和核验记录。

综合贡献与有效获赞均相同的展示可标记同分，正式名次、奖金边界及是否增加名额待确认，不自动按用户ID决定奖金或扩大奖池。

## 4. 页面结构

### 4.1 首页顶部卡片

当前可见性：实际拥有全局角色“超级管理员”或“管理员”，或任意项目角色“调度研发”的用户可见，其他用户暂不可见；标题、右侧“查看榜单”、前三名卡片及顶部点赞说明作为整体隐藏，不保留空壳或禁用入口。可见性来自用户详情的服务端布尔标记，不直接匹配前端角色ID或通配权限。此限制不自动扩大为独立页面或接口权限变更。

实际后台首页是 `frontend/src/pages/admin/Dashboard.tsx`。在用户头像和名字的欢迎区下方、工单数据看板之前展示“知识贡献榜”；标题复用工单数据看板的 `SectionTitle`，卡片内仅保留月份和合并排名说明，不重复放置主标题。不改现有工单数据看板的数据源。

首页卡片在前三名预览上方、榜单中心在顶部提示区补充：每人每天最多点赞5个不同问题；北京时间每日0点重置，取消点赞不返还当日名额。复用原有浅色提示样式，不增加奖金规则或结算提示。

卡片采用左侧榜单标识、右侧三行排名的横向布局，展示当月综合前三的头像、昵称、综合贡献数和预计月度奖金；提单数、接单数和有效获赞数在完整列表中查看。前三均为100元；发放前显示“预计月度奖励”，不能显示为已到账。

活动开始前显示“11月1日开启”，不预填历史用户或奖金；不足三人显示空缺，失败显示重试。金额和结算状态取后端，不由前端自行推算到账状态。

### 4.2 榜单中心

点击卡片进入 `/admin/knowledge`，默认展示三个纵向排列的横向模块卡片，每张均可点击进入完整列表：

1. 问题榜单：预览当月按有效点赞排序的前三题，显示标题、提单/接单人及点赞数。
2. 最佳提单人榜单：预览综合月榜前三，突出提单贡献并显示预计月度奖金。
3. 最佳接单人榜单：预览同一综合月榜前三，突出接单贡献并显示预计月度奖金。

卡片左侧为蓝色榜单图标封面，右侧为三行预览，保留原平台浅色卡片、圆角和颜色变量，不照搬参考图的深色主题。不足三条明确展示空缺，加载失败显示错误和重试，不伪造数据。点击整张卡片或“查看全部”进入相应完整列表；列表中保留三个切换按钮和返回概览入口。

不新增第四个榜单主入口；综合榜由首页及两个用户榜单入口承载。两个用户入口默认查看同一综合月榜前十名，分别突出提单和接单数量，采用每行三个的头像网格。点击头像进入人员贡献工单页，可切换“全部工单 / TA的提单 / TA的接单”，每页20条，仅展示当前活动月内有效公开归档工单；不授予原始工单访问权限。若提供按单类数量排序，应标记为分类展示，不用于独立发奖。

页面提供月份切换，并区分实时榜、待异常核验、已确认最终榜及已发放。月份与问题排序保存在URL中，从卡片进入列表、返回概览或查看问题详情后返回列表时保持选中月份和排序。一个月最多一组综合前三和前十，不分提问人、接单人另开两组奖金。

### 4.3 公开问题及详情

问题榜单二级页面为“知识列表”，面向全部登录用户，逐条列出活动已有效归档的问题，支持归档时间倒序和有效点赞数倒序。问题卡片右侧可点赞，列表展示标题、摘要、归档时间、提单人/接单人、有效点赞数及本人点赞状态。

详情顶部展示提单人/接单人的头像及姓名，右侧可点赞；正文展示问题、完整已通过报告、通过意见和价值点。审核人姓名、头像、账号和ID不返回。公开提单人和接单人不代表公开客户、设备凭据或其他敏感数据，也不代表授予原始工单访问权限。

详情新增独立讨论区，所有登录用户可在已公开问题下发布1—2000字纯文本，按最新时间倒序分页，每页20条；空白内容禁止提交，失败保留草稿并提示重试。不复用或泄露原工单内部评论，讨论不计贡献或奖金，不改变工单状态。该问题当前及历史审核人发言的作者匿名，正文按公开知识同一口径隐藏审核身份及敏感信息。问题撤回或失去公开资格后，不再开放其讨论读写。

用户可以点赞和取消点赞，每人每题最多一个有效点赞；提问人、解答人及审核人不能为参与的问题点赞计奖。禁止使用资源模块现有简单点赞计数器代替问题点赞明细。

### 4.4 审核视角

榜单总览直接提供“评审工作台 · 待审N”入口；知识列表内部保留“知识列表 / 待我审核 / 我的审核意见”切换。平台指定名单、已有分配或本人意见记录的人员及管理员可看到入口，名单人员无需先收到任务。普通用户访问审核旧链接时显示权限说明，不静默回退成公开问题列表。

待审队列及待审数量不受活动月份限制，只展示分配给当前用户的报告；管理员打开工作台也不能代看或代审他人的报告。名单、队列、历史、审批及匿名读取限制统一使用用户ID/账号/OpenID匹配。待审问题不能公开、不能点赞、不计贡献。审核名单为空时应先由有权限的管理员在“开发者模式 → 归档审核”中按领域配置人员，不自动指定人员或回退自审。

系统任务的审核入口和榜单的审核入口共用匿名审核组件，读取同一份归档报告，不另填报告、不进行二次审核。审核人必须填写意见；通过必填价值点，驳回需说明原因和修改建议。

## 5. 审核与访问控制

### 5.1 流程

工单正常关闭后，由接单人决定进入归档，编辑符合格式要求的报告；提交后由指定名单按现有领域和负荷派审。通过后报告为 `approved`、工单为 `archived`，发布公开知识并计入符合条件的贡献；驳回后保留 `archiving`，接单人修改后重新提交。

派审必须排除提问人、解答人和报告提交人，无第三方可审时等待配置或改派，不回退自审。

### 5.2 可见性矩阵

| 内容 | 可见范围 |
|---|---|
| 待审问题和报告 | 分配审核人看到匿名视图，当事人按编辑权限看到自己的报告 |
| 待审提单人/接单人身份 | 不向审核视图返回 |
| 已通过问题及提单人/接单人 | 全部登录用户，仍需移除业务敏感信息 |
| 通过意见和价值点 | 公开问题详情，以及审核人本人历史记录 |
| 驳回意见 | 原提问人、对应接单人、意见作者本人 |
| 其他审核人的历史意见 | 不因具有审核角色而开放 |
| 审核人身份及派审链路 | 普通页面不公开，审计数据另行受控 |
| 后台历史风险/结算数据（无页面入口） | 受限兼容接口保留，不默认包含问题正文或意见 |

权限须覆盖报告接口、工单响应嵌入的报告、系统评论、操作日志、通知、附件以及相似工单。不因匿名接口新增而保留能绕过它的旧入口；若同一账号兼任管理员和审核人，按各视角与对象权限判断，而不是自动开放全部内容。

报告正文、署名、附件名及图片也可能暴露身份，需要格式提示及脱敏校验。对已无法可靠脱敏的材料，须明确处理方案后再进入双盲审核。

### 5.3 相似工单

接入指定接口：

```http
GET /api/tasks/{task_id}/similar?limit=8&min_score=0.02&scope=review
```

当前实现会附带审核人信息和项目名称，必须在接入前补鉴权及匿名投影。审核视角不返回实名字段，查看相似详情也不能跳入有实名讨论的原工单。

相似结果展示脱敏问题及已通过报告；无报告时标记“暂无已通过归档报告”。分数用于检索排序，不当作相似百分比或重复结论。检索失败应可识别、可重试，不把异常当作没有重复问题。

## 6. 奖励展示与后台兼容边界（2026-10-16更新）

奖金激励方式统一留给专门提醒入口。知识首页卡片、榜单总览、知识列表和人员榜不再展示前三/前十奖励规则、叠加领奖、核验后发放、已入账或结算状态等提示，不直接展示后端内部 `rule_notice`；仅保留名次、头像、贡献、获赞及此前确认的奖金数额。专门提醒入口不在本轮新增，也不在这些页面增加替代性占位提示。

知识榜单页面取消“异常观察与月度结算”入口及管理面板，包含异常标记、冻结快照、核验、暂缓和发放按钮；管理员亦不显示。月度贡献排名、前三/前十及预计奖金展示保持不变，知识列表、讨论区和评审工作台不受影响。

不删除既有奖励或结算数据，受限后端接口及幂等保护保留兼容；前端不再调用这些管理接口，也不因移除界面转为自动结算或自动发奖。以下发奖约束说明保留的后端能力，不代表当前页面仍提供对应操作。

内容审核与奖励异常核验分离：前者决定是否有效归档，由指定审核人负责；后者核验活动行为及奖金资格，由管理员负责。

历史异常数据仅包含活动行为、点赞、贡献和奖励元数据，不默认开放问题正文、报告和审核意见。

月度及优质排名奖金流转为：

> 冻结候选快照 → 待异常核验 → 核验通过 → 待发放 → 奖励入账

发现异常可以暂缓，记录原因、处理人、处理时间及受影响的点赞或贡献范围；需要调整榜单时产生可追溯修订。管理员不直接修改内容审核结论，不把异常核验做成第二次内容评审。

只有最终规则明确、异常核验完成的奖金才能生成可提现奖励记录。前端的预计奖金不代表余额；微信转账仍由提现链路承担，不在归档审核事务中发起。

单题6元是否也必须等待管理员异常核验尚未明确。本方案暂保留原单题审核通过入账口径，把它列为开发发奖链路前的确认项；不擅自将全部奖励自动发放，也不擅自延迟原有单题奖励。

单题、月榜、优质奖励使用独立业务来源和去重键，同一个用户合法叠加领取。同一个综合月榜仅发一份月度奖励，不能分别从提单榜和接单榜重复入账。

## 7. 技术方案与现有代码落点

### 7.1 前端

- `frontend/src/pages/admin/Dashboard.tsx`：首页新增综合前三卡片，独立请求，不阻塞原看板。
- `frontend/src/main.tsx`：注册榜单中心、公开详情及审核相关页面；历史 `router/index.tsx` 不是实际路由入口。
- 新增榜单卡片、榜单中心、公开问题详情及可复用匿名审核组件。
- `frontend/src/pages/tasks/TaskDetailPage.tsx`：旧通过/驳回入口统一填写意见并接入匿名审核组件。
- 沿用头像组件、TDesign及现有认证和请求机制；按账号、月份及权限隔离缓存，不复用跨账号待审缓存。

### 7.2 后端及数据

- 复用 `Task`、`ArchiveReport`，扩展通过意见、价值点、匿名编号和报告必填校验。
- 知识发布关联记录一工单一条，固定通过报告、原提问人、解答人、首次有效归档时间和活动资格。
- 点赞明细使用 `(task_id, user_id)` 唯一约束，支持取消及风控有效性。
- 审核历史按提交版本和审核轮次留存，重新提交不覆盖旧意见；公开详情只取当前已通过记录。
- 综合月榜快照记录提单数、接单数、综合数、获赞数、规则版本和异常核验状态；按活动、月份、用户及综合榜类型唯一。
- 有效归档、发布记录及贡献资格保持事务一致；审核加行锁或条件更新和版本校验，过期请求返回冲突，不重复计数。
- 复用现有 `backend/app/modules/wxpay/` 奖励及提现能力，不另建支付产品；发奖幂等键区分单题角色、综合月榜和优质奖励。
- ORM定义放 `backend/app/models/`，通过Alembic迁移，不新增另一套Base。

### 7.3 接口建议

以下榜单及匿名读取接口已实现：

| 接口 | 用途 |
|---|---|
| `GET /api/admin/knowledge/overview?month=2026-11` | 首页综合前三、活动状态及预计奖金 |
| `GET /api/admin/knowledge/rankings?month=2026-11` | 唯一综合月榜及提单/接单明细 |
| `GET /api/admin/knowledge/questions?sort=archived_at` | 公开问题，支持时间和有效点赞数排序、分页 |
| `GET /api/admin/knowledge/questions/{task_id}` | 已通过公开报告、双方信息及匿名审核意见 |
| `GET /api/admin/knowledge/contributors/{user_id}/questions?month=2026-11&role=all&page=1&size=20` | 人员当月公开归档工单；role可选all/questioner/answerer |
| `GET /api/admin/knowledge/questions/{task_id}/discussions?page=1&size=20` | 独立讨论列表，不读取原工单内部评论 |
| `POST /api/admin/knowledge/questions/{task_id}/discussions` | 发布讨论，正文为content，成功201 |
| `PUT /api/admin/knowledge/questions/{task_id}/like` | 幂等点赞 |

审核动作复用当前真实路径，必须同步更新原系统任务调用方：

```http

POST /api/tasks/archive-report/archive-reports/{report_id}/reject
```

两者都要求意见，通过另要求价值点，并校验报告版本、状态、当前审核分配及回避条件。新接口和旧接口使用统一服务及可见性规则，不返回现有未经投影的完整工单或报告对象。
