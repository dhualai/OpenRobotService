# 红包激励机制实施方案

## Context

当前项目的微信支付模块（`backend/app/modules/wxpay/`）基础设施完备：RewardRecord 模型、TransferBill 模型、RewardService.grant（记账）、WithdrawService.withdraw（发起微信商家转账）均已就绪。奖励管理页面 `WxpayRewardManage.tsx` 目前只是开发者联调用的转账测试工具，面向运维而非财务/管理员。

需求是将其升级为**完整的红包激励机制**，包含三类奖励：基础闭环奖励、月度排名奖励、优质点赞奖。核心约束：**工单通过归档审核（archived）自动生成奖励记录，根据审核决策引擎判断是直接通过（自动发转账）还是进入 pending_audit 待财务审核**。

### 关键用户决策

| 决策点 | 结论 |
|---|---|
| 月度排名口径 | 仅按接单人 `assigned_to` 的闭环工单数统计 |
| 点赞奖励流程 | 点赞 → 创建 reward → 审核决策 → 自动通过或 pending_audit |
| 月度排名奖励流程 | 系统生成快照 → 创建 reward → 审核决策 → 自动通过或 pending_audit |
| 审核通过后行为 | **自动发起微信转账**（不再停留 `pending`） |
| 财务压力缓解 | **加入审核决策引擎**：小额/低风险奖励自动通过，大额/高频用户强制财务审核 |

### 审核决策引擎（核心新增）

奖励创建时**即时执行**决策，决定该条奖励走哪条路：

```
reward 创建 → AuditDecisionEngine.evaluate(db, reward)
                │
    ┌───────────┴────────────┐
    ▼                        ▼
  自动通过                  强制审核
    │                        │
    ▼                        ▼
  status=pending          status=pending_audit
  立即调 Withdraw()        （财务在管理页操作）
```

**自动通过条件（全部满足才自动通过）：**

| 条件 | 配置项 | 默认值 | 说明 |
|---|---|---|---|
| 金额 ≤ 阈值 | auto_pass_max_fen | 500（5元） | 单笔小于等于 5 元自动过 |
| 用户累计奖励次数 < 阈值 | force_audit_user_total_count | 10 | 同一用户历史奖励总条数 ≥ 10 强制审核 |
| 用户当日奖励金额 < 阈值 | force_audit_user_daily_fen | 2000（20元） | 同一用户当天累计奖励金额 ≥ 20 元强制审核 |
| 奖励类型在启用列表中 | enabled_scenes | ["task_archive","quality_like","monthly_rank"] | 可按奖励类型关闭自动通过 |

任一条件不满足 → 强制审核 → status=pending_audit。

财务可在规则配置页调整这些阈值，甚至把 auto_pass_max_fen 设为 0（等于全局关闭自动通过，所有奖励都走 pending_audit）。

### 新状态机

```
奖励创建
  │
  ├── 审核决策引擎 evaluate()
  │     │
  │     ├── 自动通过 → status=pending → 立即调 WithdrawService.withdraw()
  │     │                                      │
  │     │                                      ├── WAIT_USER_CONFIRM → withdrawing（等用户确认）
  │     │                                      ├── 受理中 → withdrawing
  │     │                                      ├── 直接 SUCCESS → success
  │     │                                      └── FAIL → pending（待重试，不自动重发）
  │     │
  │     └── 强制审核 → status=pending_audit
  │                          │
  │                 ┌────────┴────────┐
  │                 ▼                 ▼
  │              财务审核通过       财务驳回（rejected，终态）
  │                 │
  │                 ▼
  │           调 WithdrawService.withdraw() → 同上分支
  │
  └── WithdrawService 失败后可重试
```

原 `RewardStatus.PENDING` 现在有了明确语义："审核已通过，待/正在提现"。

## Phase 1：数据模型 + 状态机扩展

### 1.1 RewardStatus 扩展 — `backend/app/models/wxpay.py`

```python
class RewardStatus:
    PENDING_AUDIT = "pending_audit"   # 强制财务审核（新增）
    REJECTED = "rejected"             # 财务驳回（新增，终态）
    PENDING = "pending"               # 审核通过，可提现（原义保留）
    WITHDRAWING = "withdrawing"       # 提现中
    SUCCESS = "success"               # 已到账（终态）
    EXPIRED = "expired"               # 已失效（终态）
```

### 1.2 RewardRecord 模型扩展 — `backend/app/models/wxpay.py`

新增字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `role` | String(32), nullable | reporter / assignee / reviewer / liker / ranker / manual |
| `audit_by` | String(64), nullable | 财务审核人 users.id（自动通过时为 "AUTO"） |
| `audit_at` | DateTime, nullable | 审核时间（自动通过时也写当前时间） |
| `audit_remark` | String(255), nullable | 驳回原因或自动通过标记 |

唯一约束修改：

```python
# 删除旧 UniqueConstraint("source_type", "source_id", name="uq_reward_source")
# 改为：
UniqueConstraint("source_type", "source_id", "role", name="uq_reward_source_role"),
```

理由：同一工单要发三条奖励（reporter/assignee/reviewer），三元组自然去重；并发重试时 grant_batch 只跳过已存在的。

索引补充：
- `Index("ix_reward_audit_status", "status")` — 待审核列表高频查询
- `Index("ix_reward_task_role", "source_id", "role")` — 按工单查三条奖励
- `Index("ix_reward_user_created", "user_id", "created_at")` — 审核决策引擎查用户累计/当日金额用

### 1.4 WithdrawService 前置校验 — `backend/app/modules/wxpay/service.py`

拦截未审核的奖励：
```python
if reward.status in (RewardStatus.PENDING_AUDIT, RewardStatus.REJECTED):
    return WithdrawOut(action="rejected", message="奖励尚未审核通过，暂不可提现")
```

### 1.5 审核决策引擎 — 新增 AuditDecisionEngine（同文件 service.py 或独立文件）

```python
class AuditDecisionEngine:
    """奖励审核决策：自动通过 or 强制财务审核。"""

    @staticmethod
    async def evaluate(db: AsyncSession, reward: RewardRecord, audit_policy: dict) -> str:
        """返回 RewardStatus.PENDING（自动通过）或 PENDING_AUDIT（强制审核）。

        决策步骤（任一步触发强制审核即短路返回）：
        1. 检查 reward.amount > auto_pass_max_fen
        2. 检查 reward.role 对应的 scene 是否在 enabled_scenes 里
        3. 查该 user 的历史奖励总条数 → force_audit_user_total_count
        4. 查该 user 当天已发奖励金额 → force_audit_user_daily_fen
        """
```

### 1.6 Alembic 迁移

单份迁移 `alembic/versions/<new_hash>_expand_reward_for_incentive.py`：
1. `op.create_table('reward_config', ...)` 并插入 4 条默认种子数据
2. RewardRecord 加 role / audit_by / audit_at / audit_remark 四列
3. `op.drop_constraint('uq_reward_source', 'reward_record', type_='unique')`
4. 历史数据回填：`UPDATE reward_record SET role='manual', audit_by='MANUAL_INIT' WHERE role IS NULL`
5. `op.create_unique_constraint('uq_reward_source_role', 'reward_record', ['source_type', 'source_id', 'role'])`
6. 创建新索引

## Phase 2：后端自动发放 + 审核决策 + 财务审核 API

### 2.1 RewardService 扩展 — `backend/app/modules/wxpay/service.py`

```python
class RewardService:
    @staticmethod
    async def resolve_config(db: AsyncSession, key: str) -> Optional[dict]:
        """读 RewardConfig，enabled=false 或不存在返回 None。"""

    @staticmethod
    async def grant_batch(
        db: AsyncSession,
        items: List[GrantRewardIn],
        role: str,
        audit_policy: Optional[dict] = None,
    ) -> tuple[int, List[RewardRecord]]:
        """批量记账 + 执行审核决策引擎 + 自动通过的立即发起 withdraw。

        返回 (新建条数, 所有 RewardRecord)。
        - 逐条查重 (source_type, source_id, role)
        - 新建后立即调 AuditDecisionEngine.evaluate()
        - 自动通过的：status=pending + 写 audit_by='AUTO' + audit_at
        - 强制审核的：status=pending_audit + audit_by/audit_at 留空
        - flush 后，自动通过的那批循环调 WithdrawService.withdraw()（同事务 flush）
        """
```

原 `grant()` 增加 `auto_commit=True` 参数保持向后兼容（管理端转账测试仍自己 commit，不走审核决策）。

### 2.2 ArchiveReportService.approve() 注入 — `backend/app/modules/tasks/services/archive_report_service.py`

```python
async def approve(db, report_id, operator_id):
    report = ...
    task = ...

    # 1. 原有：更新 report + task 状态
    report.submit_status = 'approved'
    report.reviewed_at = func.now()
    report.updated_by = operator_id
    task.status = TaskStatus.ARCHIVED
    task.archived_by = operator_id
    task.archived_at = func.now()

    # 2. 新增：自动生成三条奖励（带审核决策）
    from app.modules.wxpay.service import RewardService
    cfg = await RewardService.resolve_config(db, "task_archive")
    policy = await RewardService.resolve_config(db, "audit_policy")
    if cfg is not None:
        items = []
        if task.created_by and cfg.get("reporter_fen", 0) > 0:
            items.append(GrantRewardIn(user_id=task.created_by, amount=cfg["reporter_fen"],
                scene_name="工单闭环奖励", reward_desc="工单提单人奖励",
                source_type="task", source_id=str(task.id)))
        if task.assigned_to and cfg.get("assignee_fen", 0) > 0:
            items.append(...)  # 接单人
        if operator_id and cfg.get("reviewer_fen", 0) > 0:
            items.append(...)  # 审核人

        await RewardService.grant_batch(db, items, role="task", audit_policy=policy)

    # 3. 一次性 flush
    await db.flush()
    return report, task
```

关键：flush 在 grant_batch 之后，reward / task / report 同事务。grant_batch 内部自动通过的奖励调了 withdraw，但 withdraw 是异步创建 TransferBill（也是 flush，不 commit），所以 TransferBill 也在同事务里。

## Phase 4：月度排名 + 优质点赞（独立 PR）

### 4.1 月度排名

```sql
CREATE TABLE monthly_rank_snapshot (
  rank_month VARCHAR(7) PRIMARY KEY,        -- "2026-10"
  user_id VARCHAR(64) NOT NULL,             -- 接单人 assigned_to
  task_count INT NOT NULL,
  task_ids JSON NOT NULL,
  rank_no INT NOT NULL,                     -- 1..10
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uq_month_rank_user (rank_month, user_id),
  INDEX ix_month_rank_rank (rank_month, rank_no)
);
```

定时任务每月 1 号 00:05：
- `tasks.status='archived' AND assigned_to IS NOT NULL AND archived_at BETWEEN 上月1日 AND 本月1日`
- GROUP BY assigned_to，取 TOP 10
- 创建 reward_record（role="ranker", source_type="monthly_rank", source_id="{rank_month}:{rank_no}"）→ 走 grant_batch + 审核决策

### 4.2 优质点赞

```sql
CREATE TABLE task_quality_mark (
  task_id INT PRIMARY KEY,
  marked_by VARCHAR(64),
  marked_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE TABLE task_like (
  id VARCHAR(32) PRIMARY KEY,
  task_id INT NOT NULL,
  user_id VARCHAR(64) NOT NULL,             -- 点赞人
  liked_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uq_task_like_user (task_id, user_id),
  INDEX ix_task_like_user_day (user_id, DATE(liked_at))
);
```

API（tasks 模块）：
```
POST /api/tasks/{task_id}/mark-quality     # 仅 archived 工单可标
POST /api/tasks/{task_id}/like             # 日上限 5 条/人 → 给接单人发 pending_audit 或直接 pending
GET  /api/tasks/{task_id}/like-count
```

## 验证方案

1. **迁移验证**：Alembic migration 跑通，RewardConfig 4 行种子数据就位，历史 reward_record role 回填 manual
2. **自动通过验证**：5 元以下 + 新用户（累计 < 10 次）→ 创建后直接 pending，立即调 withdraw
3. **强制审核验证**：10 元以上 / 累计 ≥ 10 次 / 当日 ≥ 20 元 → 创建后 pending_audit，风控原因可追踪
4. **财务审核验证**：batch-audit → audit_by/audit_at 写入 → withdraw 被调
5. **驳回验证**：batch-reject → rejected 终态 → WithdrawService 拒绝
6. **规则热更验证**：管理员改 audit_policy → 下次 grant_batch 立即生效，无需重启
7. **归档事务原子性验证**：RewardConfig 未初始化时 grant_batch raise → approve 整体回滚，task.archived_by 不写入
8. **月度排名验证**：手动触发统计 → 快照生成 → reward 批量创建 → 审核决策分流
