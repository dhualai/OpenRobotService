## 一、根因：confirm 弹窗为何从未被触发

两条转工单路径，只有按钮路径走 confirm，对话路径直接入库：

| 路径 | 入口 | 字段齐全后 | 是否弹窗 |
|---|---|---|---|
| 按钮路径 | `POST /qa/ticket/prepare` → `prepare_ticket()` 返回 `stage=draft_ready` | 前端 `handleSubmitTicket` 弹 `ticketConfirm` → `qaConfirmTicket` → `confirm_submit` 入库 | ✅ 弹（但用户很少点按钮） |
| **对话路径** | SSE `/qa/ask/stream`，LLM `action=submit` | `pipeline.py:1934` **直接 `self.submit()` 入库** → 发 `stage:submitted` | ❌ **不弹，直接入库** |

根因代码（`pipeline.py:1932-1944`，SSE stream interceptor 的 `action=submit + 字段齐` 分支）：
```python
else:
    yield {"event": "status", "data": {"stage": "submitting"}}
    ticket_data = await self.submit(request.session_id, created_by=request.created_by, force=_force_submit)  # ← 直接入库，绕过 confirm
    ...
    yield {"event": "status", "data": {"stage": "submitted", "ticket_id": ...}}
```

**结论**：`confirm_submit`（`pipeline.py:1409`）和前端 `ticketConfirm` 弹窗、`handleConfirmTicket`、`qaConfirmTicket` 全都已就绪，只差对话路径不调它。改造点聚焦：**对话路径字段齐时不入库，改发 review 事件 → 前端弹窗 → confirm_submit 入库**。

## 三、设计方案

### 3.1 后端改动（`pipeline.py` SSE interceptor，~1932-1944）

**当前**（直接入库）：
```python
else:
    yield {"event": "status", "data": {"stage": "submitting"}}
    ticket_data = await self.submit(request.session_id, created_by=request.created_by, force=_force_submit)
    ...  # 发 stage:submitted
```

**改为**（弹窗确认）：
```python
else:
    # 字段齐全 → 不直接入库，存草稿到 memory + 发 review 事件 → 前端弹窗 → 用户确认后 POST /qa/ticket/confirm → confirm_submit 入库
    memory.metadata["ticket_draft"] = draft
    await self._memory_manager.save_memory(memory)
    yield {"event": "status", "data": {"stage": "review", "draft": draft}}
    parsed["message"] = "请确认以下工单信息，可修改后提交。"
    _msg_buf.clear()
    _msg_yielded = True
    yield {"event": "token", "data": parsed["message"]}
```

**影响范围**（初稿已列，确认无误）：
- LLM 输出 `action=submit` + 字段齐 → 弹窗（原直接入库）
- `ticket_collecting` 字段集齐自动提单（L1864-1869 设 `action=submit`）→ 弹窗
- 收集超限强制提单（L1870-1876，`_force_submit=True`）→ 弹窗（用户可改 project）
- 字段不齐（`check["ok"]=False`）→ 保持现有 `stage:need_fields` 引导补充，不变

### 3.2 前端改动（`ChatPanel.tsx` processLine，~L736 后）

// 转工单确认弹窗：后端字段齐全 → event:status + stage:review → 弹窗（复用 ticketConfirm，与按钮路径一致）

- 弹窗 UI、字段编辑、`handleConfirmTicket`、`qaConfirmTicket` 调用**全部复用现有**，0 新增。
- `stage:review`（对话路径/SSE）与 `stage:draft_ready`（按钮路径/HTTP）两通道共存，前端分别处理：`processLine` 监听 review，`handleSubmitTicket` 监听 draft_ready，弹窗逻辑殊途同归。

## 四、初稿遗漏的风险点与对策（评审重点）

### 风险1：phase 转换（最关键）
`_apply_action_phase`（L801-805）：`action=submit` → `phase=escalated`，在 L1900 调用（submit 执行之前）。
- 改成 review 不入库后，`action` 仍是 `submit` → `phase` 仍变 `escalated`，但工单没建（draft 待确认）。
- 影响：用户不确认继续对话时，`phase=escalated` 会让 LLM prompt 进入"已提单"语境，可能拒绝继续诊断/补充；而 `last_submitted_ticket` 未设，`_can_submit`（L138）不拦截——行为不一致。

**对策（二选一，请评审）**：
- **A**：review 时把传给 `_apply_action_phase` 的 action 改为 `answer`（`phase=resolved`，语义"诊断完成待确认"），保持不入 escalated；`confirm_submit` 入库后由 `_reset_state_after_submit` 处理 state（需确认它是否置 phase=escalated，若否则补一行）。
- **B**：新增 `agent_state.ticket_pending_confirm=True` 标记，`_apply_action_phase` 见此标记跳过 escalated；`confirm_submit` 成功后清标记。`_can_submit` 增判断：有 pending_confirm 时不拦截继续对话。

推荐 **A**（最小改动，语义清晰）。

### 风险2：重复 review
用户收到 review 弹窗后不确认、继续对话，LLM 可能再次 `action=submit` → 再次 `_build_ticket` → check ok → 又发 review（重复弹窗）。
- 对策：进入 review 前判断 `memory.metadata.ticket_draft` 已存在 → 跳过重复 review，复用现有草稿（前端弹窗已开则不重弹，未开则用 `GET /qa/ticket/draft` 兜底拉回）。

### 风险3：前端 badge/ticketCreatedThisTurn
对话路径以前靠 `result` 事件携带 ticket（L738-740）置 `ticketCreatedThisTurn=true` 刷新 badge。改 review 后建单推迟到 confirm：
- review 时**不置** `ticketCreatedThisTurn`（建单未发生）。
- `handleConfirmTicket` 成功后已 `refreshTasks()`，badge 由它刷新；但 `ticketCreatedThisTurn` 的流末处理（L786）需确认不误触发。

### 风险4：_force_submit（收集超限）文案
`_force_submit=True` 时 `_build_ticket` 兜底 `project="摇人吧服务号提单"`，`_check_required_fields` 判 ok → 走 review。但此时信息仍不全（被强制），弹窗应提示用户核对/补全 project。
- 对策：review 事件 data 增 `force_submit: true` 标记，前端弹窗顶部加黄色提示"信息收集超限，请核对项目等关键字段"。

## 八、最终决策（2026-08-02 评审通过）

**代码查证补充**：后端 `pipeline.py:1932-1954` 的 else 分支**已实现 review 基础**（发 `stage:review` + 存 draft + `parsed.action="answer"` 避免 escalated 污染 _finalize_diagnosis），但缺幂等/force标记/phase回退；**前端 processLine 未接 review 事件**——后端发 review 前端不弹。任务实为：后端补全 + 前端补接。

**风险对策定稿**：

| 风险 | 严重度 | 定稿对策 | 改动 |
|---|---|---|---|
| 1 phase | 低 | review 分支 `_save_agent_state` 回退 `phase=diagnosing`（L1900 的 `_apply_action_phase(submit)` 误置 escalated，每轮 L1699 虽重置但语义不干净）；`_can_submit` 不依赖 phase（L136），无需改 | 后端 ~2 行 |
| 2 重复 review | 中 | **后端幂等**：`memory.ticket_draft` 已存在 → 不重建 draft、不发 review，只 yield token"您有待确认的工单，请先确认"；**前端幂等**：`setTicketConfirm` 已 `visible` 则不覆盖（保留用户编辑） | 后端 ~8 行 + 前端 ~3 行 |
| 3 badge | 低 | review 不发 `result.ticket`（ticket_data=None），`ticketCreatedThisTurn` 不触发；建单靠 `handleConfirmTicket` 的 `refreshTasks()` | 0（确认即可） |
| 4 force 文案 | 低 | review 事件 data 带 `force_submit: true`；前端弹窗 `ticket-confirm__body` 顶部黄色 banner"⚠️ 信息收集超限，请重点核对项目、车型等关键字段" | 后端 1 字段 + 前端 banner |

**实现清单**：
1. 后端 `pipeline.py:1932-1954` else 分支：加幂等（ticket_draft 已存在分支）+ `force_submit` 字段 + `state.phase="diagnosing"` 回退 + `_save_agent_state` 持久化 ticket_collecting 清空。
2. 前端 `ChatPanel.tsx`：
   - `ticketConfirm` state 加 `force_submit?: boolean`
   - `processLine` 加 `status+review` 分支（幂等：已 visible 不覆盖）
   - `handleSubmitTicket`（按钮路径）的 `setTicketConfirm` 补 `force_submit: false`
   - 弹窗 `ticket-confirm__body` 加 force_submit banner
3. `global.css` 加 `.ticket-confirm__banner` 样式。

**不改**：`router.py`、`prepare_ticket`、`confirm_submit`、`_apply_action_phase`、`_can_submit`、`_reset_state_after_submit`。

## 取消确认 / 死锁修复（2026-08 补充）

> 问题：用户滑动页面（手指落在遮罩）→ 弹窗关闭（原仅 `visible:false`，保留 draft）→ 后端 `ticket_draft` 仍在 memory →
> 后续对话走到 review 幂等分支（`pipeline.py` existing_draft 已存在，不发 review 事件）→ 前端收不到 review 事件 → **确认弹窗永不重弹，提单卡死**。

**修复**：
- 前端 `ChatPanel.tsx`：`onClose` 与「取消」按钮统一走 `handleCancelTicketConfirm`——彻底清空本地 `ticketConfirm`（draft=null），并调用 `qaClearDraft` 清后端 `ticket_draft`。
- 弹窗 `closeOnOverlayClick={false}`：杜绝滑动时误触遮罩关闭（重要操作不靠点遮罩放弃）。
- 后端 `pipeline.py` 新增 `clear_draft` + `router.py` 新增 `DELETE /qa/ticket/draft`：清 `memory.ticket_draft`。
- 清掉后，下次对话字段齐全会重新走「无 existing_draft」分支 → 重发 review → 弹窗可再次弹出。

### 刻度规则（按优先级分档）

| 优先级 | 范围 | 刻度单位 | 默认值 | 刻度点 |
|---|---|---|---|---|
| 紧急 / 高 | 0–24 小时 | 每 2h | 8h | 0h/2h/4h/6h/8h/12h/16h/20h/24h |
| 中 | 1–3 天 | 每 1 天 | 2 天 | 1d/2d/3d |
| 低 | 3–7 天 | 每 1 天 | 5 天 | 3d/4d/5d/6d/7d |

- 紧急与高合并到「0–1天按小时」档（刻度值统一存为小时数，中/低按天拖拽但内部换算为小时）。
- 改变优先级时，进度条刻度范围变化，自动重置到该档默认值（避免旧值越界）。

### 数据流

```
Slider 拖到刻度 N → setDeadlineByHours(N): deadline_at = now + N*3600000 (ISO)
  → 写入 ticketConfirm.overrides.deadline_at
  → handleConfirmTicket: overrides = {...ticketConfirm.overrides} （自动带上）
  → qaConfirmTicket(sessionId, overrides)
  → 后端 confirm_submit: draft.update(overrides) → _build_ticket → upsert_task(deadline_at)
  → 新建工单通知模板渲染"截止时间"字段
```
