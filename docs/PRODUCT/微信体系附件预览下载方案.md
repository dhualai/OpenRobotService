# 微信体系下工单附件「预览 / 下载」方案评审

> 关联需求：工单详情页附件预览 + 下载（先支持 md / pdf / 图片）。
> 关联代码：`frontend/src/shared/components/AttachmentViewer.tsx`、`DiscussionPanel.tsx`、`pages/tasks/TaskDetailPage.tsx`；后端 `backend/app/modules/tasks/api/attachment.py`（`/files/{path}` 内联、`/attachments/download` 强制下载）。
> 关联基础：微信 JS-SDK 签名接口 `GET /api/wechat/config/js-sdk-config`、前端 `shared/utils/wechatJsSdk.ts`（`initWechatJsSdk` / `setupWechatShare`）。

## 附件上传耗时优化（档1+档2，2026-08-12）

### 背景
对话区上传图片/附件时 TTFB 可达 20s。定位：**主因在 AI 服务（8401）`_upload_events` 第1段 MinIO 上传是同步阻塞调用且串行**——`minio_client.upload_bytes` 裸调在 async 函数里卡住整个事件循环，上传期间该进程所有其它 SSE/问答请求被阻塞；多文件串行累加；全部传完才回执 `file_saved`。次要：大图 base64 编码 + VLM 首 token；前端 `fetch` 无上传进度回调（体感放大）。

### 档1：后端异步上传 + 并发 + 逐文件回执（`ai/api/router.py` `_upload_events`）
- MinIO 上传与预签名 URL 生成（同步 SDK 调用）包到 `asyncio.to_thread`，不再阻塞事件循环。
- 多文件用 `asyncio.as_completed` 并发上传，总耗时 ≈ max(单文件) 而非 Σ。
- 逐文件 `yield {"event":"file_saved","saved":[item],...}`：单文件传完立即回执，前端几乎立刻看到第一个文件，TTFB ≈ 单文件上传耗时。
- 非流式 JSON 分支 `saved.extend(ev["saved"])` 累积，适配逐文件事件。
- 效果：20s → 预期 2-5s；上传期间不再拖慢其它请求。

### 档2：前端图片客户端压缩（`shared/utils/imageCompress.ts` + `ChatPanel.tsx`）
- 新增 `compressImage(file)`：canvas 重采样到最长边 ≤1920px、WebP（不支持回退 JPEG）质量 0.82；透明图补白底；<300KB / SVG / 非图 / 压缩后反而更大 均跳过。
- `handleFileChange` / `handlePaste` 改 async，选中/粘贴图片先压缩再挂 pendingFile，Toast 提示压缩前后体积。
- 效果：10MB 原图 → 1-2MB，上行 + base64 + VLM 全链路耗时下降。
- 进度反馈：`fetch` 无上传进度回调，配合档1逐文件 `file_saved` 回执（上传完即推）+ 压缩后体积小，体感已大幅改善；精确上传百分比留待档3（presigned PUT 直传，XHR 可拿进度）。

### 档3（后续）：前端直传对象存储
- 前端拿 presigned PUT URL 直传 MinIO，文件字节不经 8401，event loop 零阻塞；大文件 multipart 断点续传；上传进度由前端 XHR 自管。后端只签 URL + 事后登记元数据/触发 VLM。

## 多文件 + 全类型上传（2026-08-12）

### 背景
现场反馈提单上传仅支持图片和文档，视频/日志/Word/压缩包等不支持，导致问题描述不完整。

### 改造
- **前端 ChatPanel**：`pendingFile: File|null` → `pendingFiles: File[]`，支持多文件累积选择（多次选择追加）；待发送区渲染多文件列表，逐个可移除。
- **文件选择 input**：`fileInputRef`（accept=`*/*`）和 `albumInputRef`（accept=`image/*`）加 `multiple`；相机保持单张。
- **`sendWithFile(files: File[])`**：多文件一次 `qaUploadStream` 上传（后端 `files: List[UploadFile]` 已支持）；`onFileSaved` 逐文件回填进度（已保存数/总数），全部完成后持久化 `fileUrls`（多元素 JSON 数组）。
- **类型无限制**：前端 `accept="*/*"` 已放开，后端 `/api/ai/qa/upload` 无类型过滤，MinIO 存原始二进制。视频/日志/Word/压缩包等任意类型均可上传，单文件 ≤100MB（MinIO 单对象理论上限 5TB，前端 100MB 为体验上限，可调）。
- **图片压缩**：`handleFileChange` 对每个图片文件仍走 `compressImage`（≤1920px、WebP/JPEG 0.82），非图片原样上传。
- **粘贴**：`handlePaste` 粘贴图片追加到 `pendingFiles` 列表。

### 效果
- 现场可上传视频/日志/Word/压缩包等任意类型，问题描述完整。
- 多文件一次发送，逐文件进度反馈。
- 讨论区评论附件上传（`/api/tasks/comments/attachments`）仍为单文件串行，后续统一优化。

## 1. 现状与约束

### 1.1 现状（已具备，无需改后端）
- 内联预览：`GET /api/tasks/files/{file_path}` 代理 MinIO 并返回 `Content-Disposition: inline` 与正确的 `image/*` MIME（见下方 MIME 修复）→ 可直接用于图片 `<img>`、PDF `<PdfViewer>`（pdf.js canvas 渲染）、MD `fetch` 取文本。
- 强制下载：`GET /api/tasks/attachments/download?path=&filename=&token=` → `Content-Disposition: attachment`（带业务 token 鉴权）。
- 图片 MIME 修复（后端）：`attachment.py`（`tasks` / `call` 两模块同构）返回时优先以 `mimetypes.guess_type(filename)` 按扩展名推断 `Content-Type`（如 `image/webp`、`image/bmp`），回退 MinIO 元数据、再回退 `octet-stream`。背景：MinIO 元数据常为 `application/octet-stream`，浏览器 `<img>` 靠内容嗅探仍能显示，但微信原生查看器（`wx.previewImage`）要求严格 `image/*` 会导致微信端图片/缩略图不显示，故需后端强制正确 MIME。
  - **变量顺序 bug 修复（2026-08-06）**：初版 MIME 修复把 `mimetypes.guess_type(filename)` 写在 `filename = object_name.rsplit('/', 1)[-1]` 之前，导致 `NameError`（`filename` 未定义）→ 被外层 `except Exception` 捕获 → 所有附件代理下载返回 404（对话图片点击灯箱加载 404 碎图）。修复：将 `filename` 定义与 `response = minio_client.client.get_object(...)` 一并上移到 MIME 推断之前，确保 `guess_type` 引用到已定义的 `filename`。
  - **详情页附件列表缩略图化（2026-08-07）**：`TicketDetailPage` / `TaskDetailPage` 附件列表此前图片仅 40×40 小图标且 `<img src>` 直接用 object_path（相对路径，浏览器 404 看不到）。改为：图片附件渲染为 96×96 缩略图网格（`.detail-attachment-thumb`，`object-fit:cover`，`cursor:zoom-in`），`src` 改用 `buildPreviewUrl(att)` 构造的 `/api/tasks/files/{minioPath}` 代理 URL（与 `AttachmentViewer` 一致），点击放大走 `openAttachmentViewer`；非图片附件保持文件卡片行。同时 `ImageLightbox` 修复预览闪烁（根因：附件代理下载后端未设 `Cache-Control`，浏览器不缓存，`new Image()` 预加载每次重新请求 → `imgReady` 延迟 → loading 遮罩可见 → 闪烁；而摇人页面 AI 图片走 `/api/ai/media/*` StaticFiles 自带缓存 → 命中缓存 → 无闪烁）。修复三层：① 后端 `call`/`tasks` 两个 `attachment.py` 加 `Cache-Control: public, max-age=86400`；② `ImageLightbox` 把 loading 遮罩从条件渲染替换 DOM 改为 overlay 叠加（`ImageViewer` 始终挂载 + 纯黑 mask 兜底，`loading spinner` 只在 `imgReady=false` 时叠加，`pointer-events:none`），不切换 DOM 消除 DOM 替换闪烁；③ `.t-image-viewer__mask` 改纯黑兜底。另：`AttachmentViewer` 新增 `wxPending` 状态，微信端 `setupWechatFilePreview` 调起期间不渲染 H5 灯箱，消除「灯箱闪现后切原生预览」的闪烁。
- 前端已落地跨端通用的 `AttachmentViewer.tsx`：图片走 `ImageLightbox`、PDF 走 `<PdfViewer>`（pdf.js 渲染到 canvas）、MD 走 `react-markdown` 渲染、其它格式提示下载。PC / H5（含微信 WebView）下均可用；微信端图片/PDF 不再依赖原生查看器（见下）。
- **微信内「其它 / 不支持格式」下载跳转修复（2026-08-11）**：原 `buildAttachmentDownloadUrl` 拼出的是**相对 URL**（`API_CONFIG.TASKS.BASE_URL` 为 `/api/tasks`）。微信内点击「下载」用 `window.open(相对URL)` 打开的是微信内置 WebView 标签页，微信无法下载该文件；用户点「在浏览器打开」后，相对路径在外部浏览器解析失败会落到 SPA 的 404 → 前端未登录重定向到微信 OAuth（`buildWechatAuthUrl`），表现为「提示跳转到微信客户端、无法下载」。修复：① `buildAttachmentDownloadUrl`（`TaskDetailPage` / `TicketDetailPage`）拼成**绝对 URL**（`window.location.origin` + 路径，携带 `token`），外部浏览器打开即直接下载，不再走 SPA 路由；② `AttachmentViewer` 的「下载」按钮在微信内改用 `window.location.href = item.downloadUrl` 跳转当前页到绝对下载地址，让微信正确弹出「在浏览器打开」横幅且指向真实文件；非微信环境仍 `window.open(...)`。同时把「不支持预览」提示改为微信内引导「右上角 ··· → 在浏览器中打开」后点击下载。
- **下载接口 404 / MIME 告警加固（2026-08-11）**：生产出现 `.xlsx`（含中文名）下载 `404`、`.bz2` 下载控制台报 `interpreted as Document but transferred with MIME type application/x-compressed`。根因：① 下载接口 `download_attachment`（`task.py`）与内联接口 `attachment.py` 原先用 `except Exception: continue` 静默吞掉 `S3Error`，中文名对象查找失败（或个别上传把中文名 URL 编码存储）即被跳过 → 404，且无日志难定位；② `.bz2` 等二进制拿 MinIO 元数据 `application/x-compressed` 当 MIME，浏览器当成文档渲染告警。修复（`task.py` 下载 + `attachment.py` 内联两处同改）：a) 查找候选集 = 严格路径 → 跨已知 bucket 兜底（`MINIO_BUCKET`/`COMMENT_BUCKET`/`FILE_IMAGES`）→ 对 object 名 `quote` 再各试一次（兼容中文名编码存储）；b) 不再静默吞异常，记录 `logger.warning` 真实原因，404 详情带上「末次错误」；c) 下载接口对压缩/办公/可执行等二进制扩展名强制 `application/octet-stream`（消除「interpreted as Document」告警、确保走下载），仅 PDF/JSON 保留专用 MIME；d) 下载响应加 `Cache-Control: no-store`。两页详情（系统任务 / 摇人历史）共用 `TASKS` 接口，故一并修复。

### 1.2 微信内置浏览器（WebView）硬约束
| 能力 | 行为 | 结论 |
|---|---|---|
| `<a download>` | 被忽略，下载属性无效，点击只是「打开」而非「保存到本地」 | 无法靠 HTML 强制下载 |
| 图片 | 普通 `<img>` 可显示；`ImageLightbox` 用真实 http(s) URL → 安卓/iOS 均可「长按保存」 | 可用，但体验不如原生 |
| PDF | iOS 微信 WebView 不渲染 `<iframe>` 内 PDF，但**支持 canvas**；改用 pdf.js 渲染到 canvas 即可在微信内直接预览 | H5 pdf.js 渲染（不再依赖微信原生 `previewFile`） |
| Office（doc/xls/ppt）、zip 等 | WebView 无原生查看器 | 必须用 `wx.previewFile` |
| Markdown | 微信无原生渲染 | 仅能「应用内渲染为 HTML 后展示」 |

核心矛盾：**H5 的「下载 / 预览」语义在微信里不成立**，必须改用微信 JS-SDK 提供的原生能力。

## 2. 推荐方案：复用 JS-SDK 原生能力

项目已有 `initWechatJsSdk`（基于 `GET /api/wechat/config/js-sdk-config` 注入 `wx.config`）。本方案在其基础上扩展，无需新增后端接口。

### 2.1 能力映射
| 格式 | 微信原生 API | 说明 |
|---|---|---|
| 图片 | `wx.previewImage({urls, current})` | 全屏、滑动切换、长按保存到相册，体验最佳 |
| Office / 部分格式 | `wx.previewFile({url, name, size})` | 调起微信内置文档查看器（支持 doc/xls/ppt 等），可下载/转发；**PDF 不在此列**（走 H5 pdf.js） |
| Markdown | 保持「应用内渲染」（`react-markdown`） | 微信无原生支持；可选「md→pdf→wx.previewFile」升级，但必要性低 |
| 其它 / 不支持格式 | 提示「点右上角 … 在浏览器打开」 | 兜底，引导用户用系统浏览器 |

### 2.2 实施要点
1. **扩展 jsApiList**：在详情页调用 `initWechatJsSdk` 时，`jsApiList` 增加 `'previewImage'`、`'previewFile'`（与现有 `'updateAppMessageShareData'` 等同批注入）。✅ 已落地：`setupWechatShare` 初始化即注入共享 `TASK_JS_API_LIST`，含 `previewImage`/`previewFile`。
2. **新增 `setupWechatFilePreview`**（`wechatJsSdk.ts`）：对图片调 `wx.previewImage`、对 pdf/office 调 `wx.previewFile`；调用前确保 `wx.config` 已完成（可复用 `setupWechatShare` 的初始化守卫）。✅ 已落地。
3. **`AttachmentViewer` 微信分支**：检测到微信 UA（`/MicroMessenger/i`）且 `window.wx` 就绪时：
   - 图片 → `wx.previewImage`
   - office → `wx.previewFile`（PDF 不调原生，走 H5 pdf.js 渲染）
   - pdf → **不调** `wx.previewFile`；`wxPreviewable` 已剔除 `pdf`，由 `AttachmentViewer` 渲染 `<PdfViewer>`（pdf.js 将每页绘到 canvas，微信 WebView 支持良好）
   - md → 仍走应用内 `react-markdown` 弹窗
   - 调用失败（未注入对应 API / 域名未配）→ `try/catch` 兜底回退当前 H5 预览 + 「在浏览器打开」提示（当前 `AttachmentViewer` 已内置该提示）。✅ 已落地（`AttachmentViewer` 在微信 UA 优先调 `setupWechatFilePreview`，成功后由微信接管并关闭 H5 弹窗）。
4. **URL 要求**：`wx.previewImage` / `wx.previewFile` 的 `url` 必须：
   - 域名已加入公众号「JS 接口安全域名」；
   - 公网可访问。`/api/tasks/files/{path}` 后端代理**无需登录**（靠 object_path 不可猜测性保护），同域下微信可抓取；若附件落在需鉴权或非常规域名的私有 MinIO，仍建议先转成**带签名（presigned）的公网 URL**（P2，接口如 `/api/tasks/files/signed?path=&token=`）。

### 2.3 私有文件公网可达性（关键）
当前 `/api/tasks/files/{path}` 是「后端→MinIO 代理 + cookie 鉴权」，微信服务器侧无法抓取。两种补齐方式：
- **短期**：主附件下载本就带 `token`，可新增「带签名内联 URL」接口（如 `/api/tasks/files/signed?path=&token=`，返回 302 跳转到 MinIO presigned GET 或后端带 `inline` 的临时公网链接），供 `wx.previewFile/previewImage` 使用。
- **长期**：工单附件bucket 设为可公开读（或按 path 前缀 CDN 化），直接拿 MinIO presigned 公网 URL。

## 3. 方案对比

| 方案 | 体验 | 工作量 | 风险 | 建议 |
|---|---|---|---|---|
| A. 仅 H5（当前 `AttachmentViewer`） | 图片/PDF/md 在 PC/H5 可用；微信内 PDF 不显示、下载无效 | 已落地 | 低 | 作为基线，必须保留 |
| B. JS-SDK `previewImage`+`previewFile`（推荐） | 图片/PDF/office 在微信内原生查看、可保存 | 中（复用签名 + 扩展 jsApiList + 公网 URL） | 中（需配安全域名 + 公网 URL） | **主推**，与现有「转发到微信群」共用签名基础设施 |
| C. 引导「在浏览器打开」 | 兜底，用户手动操作 | 极低 | 低 | 必须作为 B 的失败兜底 |
| D. 后端生成临时下载页 / 二维码 | 重，且微信对下载仍受限 | 高 | 高 | 不推荐 |

**结论**：A 为基线（已完成）；B 为微信增强主推，复用既有 JS-SDK 签名，仅需扩展 `jsApiList` 与补齐「公网可访问的内联 URL」；C 为失败兜底（已内置）。

## 5. 风险与注意
- `wx.previewFile` 对格式/大小有限制（超大文件体验差），超阈值应回退 C。
- 安全域名未配置会导致 wx API 静默失效 → 必须 `try/catch` 兜底到 H5 预览。
- 私有附件转公网 URL 须带有效期签名，避免附件永久外泄。
- MD 渲染坚持不加 `rehypeRaw`，防止附件内恶意 HTML 造成 XSS。
