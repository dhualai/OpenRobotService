# 业务规则

> 本文记录 OpenRobotService 项目的核心业务规则、约束和决策，供测试开发和代码编写时参考。
> 与代码相关的业务逻辑见 `docs/CODEBASE_OVERVIEW.md`，产品需求见 `docs/PRD.md`。

---

## 一、角色与权限

### 1.1 角色定义

| 角色 | 标识 | 说明 |
|------|------|------|
| 客户 | `customer` | 现场人员，可提交工单、咨询、查看自己提交的工单 |
| 工程师 | `engineer` | 实施工程师，可接单处理、转派、讨论、上报 |
| 项目经理 | `manager` | 可派单、处理、讨论、查看本项目工单 |
| 上级领导 | `leader` | 可接收上报、决策、查看全局工单 |
| 系统管理员 | `admin` | 全部权限、用户与项目管理 |

### 1.2 权限规则

- 提交工单、参与讨论是所有角色的通用能力
- 权限码格式：`backend:{resource}:{scope}:{action}`
- `require_permission(perm, project_id)` 支持 admin 直通、`resource:*` 通配
- 开发环境可用 `/api/auth/dev-login` 跳过微信 OAuth 获取 JWT
- `frontend/.env.local` 的 `VITE_DISABLE_AUTH_GUARD=true` 可跳过前端守卫

## 二、任务状态机

### 2.1 状态流转

```
待派单(pending_assignment) → 已派单(assigned) → 处理中(in_progress)
                                                        │
              ┌───────────────────┬──────────────────────┼──────────────────────┐
              ▼                   ▼                      ▼                      ▼
         待讨论(discussing)   已上报(escalated)      已解决(resolved)       已关闭(closed)
                                                                              │
                                                                              ▼
                                                                        处理中(in_progress) ← 重开
```

### 2.2 状态合并规则（外部任务源同步）

当禅道等外部源同步任务时，状态取较后：

| 本平台状态 | 序号 | 外部来源 |
|------------|------|----------|
| `new` | 0 | `wait` |
| `in_progress` | 1 | `doing` |
| `pending` | 1（同级） | `pause` |
| `resolved` | 2 | `done` |
| `closed` | 3 | `cancel` / `closed` |

合并规则定义在 `app/integrations/engine.py` 的 `merge_status()`：
- incoming 序号 ≤ local 序号 → 不动（返回 None）
- incoming 序号 > local 序号 → 推进（返回 incoming）

### 2.3 工单任务类型映射（禅道 → 核心）

| 禅道 type | 核心 TaskType |
|-----------|---------------|
| `devel` | `feature` |
| `test` | `support` |
| `design` / `research` / `misc` | `other` |
| 空 / `None` | `other` |

### 2.4 任务优先级映射

| 禅道 pri | 核心 Priority |
|----------|---------------|
| 1 | `urgent` |
| 2 | `high` |
| 3 | `medium` |
| 4 | `low` |
| 空 / 非数字 | `medium` |

---

### 2.5 工单看板超时统计

- 后台管理工单看板的超时工单仅统计 `in_progress`（处理中）状态；挂起、申请挂起、待处理及其他状态均不计入。待处理数等其他指标保持原口径。
- 以系统任务中最新的当前阶段截止时间 `curr_step_endtime` 为唯一依据，只有当前时间严格超过该时间点才计入；尚未到期、恰好到期或未设置当前阶段截止时间的工单不计入，不回退到旧 `deadline_at`。
- 当前阶段截止时间每次更新后，重新统计时使用新时间点。汇总数量、下钻列表及已超时时长使用相同口径；时间按数据库 naive UTC 比较，列表按当前阶段截止时间升序排列。

## 三、外部任务源集成

### 3.1 插件化设计

- 每个任务源是一个独立包，位于 `app/integrations/sources/` 下
- 通过 `TASK_SOURCES_ENABLED` 配置启用（如 `["zentao"]`）
- 插件实现 `TaskSourceAdapter` 接口，仅负责"拉取 + 翻译成 ExternalTask"
- 状态合并、账号映射、入库由 `SyncEngine` 统一处理
- 移除一个源：删除对应目录 + 从配置中去掉 → 核心零改动

### 3.2 同步规则

- 方向：单向只读（外部 → 本平台），不回写
- 触发：Airflow DAG 定时触发 `POST /api/tasks/sources/{name}/sync`
- 鉴权：独立 API Key（`X-API-Key`），与用户 JWT 分离
- 幂等：按 `(source, external_id)` upsert，可安全重跑
- 容错：单条失败不中断整批

## 四、测试隔离规则

### 4.1 数据库隔离

- **单元测试**：conftest.py 使用占位模块阻止真实 DB 连接，不需要 MySQL
- **集成测试**（`test_standard_task_creation_db.py`）：通过 `TEST_DATABASE_URL` 环境变量连接独立 MySQL，无此变量时自动 skip
- 生产 DB 连接串由 `settings.DB_CONFIG` 注入，测试环境不读取

### 4.2 外部服务隔离

- 微信功能测试：可用 `/api/auth/dev-login` 降级模式，无需真实微信环境
- MinIO 测试：不依赖真实对象存储
- AI 模块测试：需要真实 LLM API key 和网络连接（`ai/tests/test_llm_api.py`）

### 4.3 外部接口契约

- 后端 API 路由以 `/api/` 为前缀
- AI 服务路由以 `/api/ai/` 为前缀
- 微信回调路由以 `/api/wechat/` 为前缀
- 前端 `/api/*` 经 vite 代理或 nginx 分发：`/api/ai/*` → AI 服务，其余 → 业务后端

## 六、项目管理规则

### 6.1 项目唯一键约束

- **项目编号**（`project_code` / `project.code`）与 **项目名称**（`name`）均为项目的唯一 key。
- 后台「项目管理 → 项目导入 → USP 项目」新建项目时，以下字段为必填：**项目名称、项目编号、项目状态**。
- 创建（`POST /api/admin/projects/`）与更新（`PUT /api/admin/projects/{id}`）时，后端会先与库中已有项目比对：
  - 项目编号或项目名称已存在 → 返回 `409 Conflict`，提示「项目编号/项目名称『xxx』已存在，请重新输入」。
  - 更新时排除当前项目自身（`exclude_id`），避免自比较误判。
- 并发提交兜底：即使绕过前端校验，数据库 `project.code` 唯一索引冲突也会被转换为 `409` 提示，而非 500。
- 前端新建页对三个必填字段做提交前校验，并把后端的 409 提示原样展示给客户（Toast 警告）。

## 七、知识贡献榜与匿名归档审核（2026-10-15）

- 内容审核通过不代表闭环：报告为 `approved`，工单保持 `archiving`；生成提问人、报告解答人及内容审核人三条 `pending_audit` 奖励，进入现有“后台管理 → 运营与数据 → 奖励管理 → 待财务审核”，不新增审核入口。三方金额取已启用的 `task_archive` 配置，身份或金额配置缺失则拒绝提交，不吞掉奖励失败后继续归档。
- 财务拥有原奖励管理入口权限及 `frontend:admin:reward-audit:write` 时，可查看工单、归档报告、内容审核意见及价值点。勾选任意一方奖励，整单锁定并处理三方，不允许部分通过；闭环奖励不参与自动通过。财务驳回须填写意见，三方不发奖、工单不入榜。
- 财务通过后三方奖励变为 `pending`（可领取），工单变为 `archived`，知识发布同事务提交；贡献月份按工单提问时间的北京时间自然月确定，不按财务闭环月份确定。待财务记录不提前计算过期时间，领取有效期从财务通过起算。重复操作不重复发奖或计分；财务待审或已驳回时不能通过普通工单状态接口绕过闭环。
- 本次复用既有奖励账户和微信转账链路，不在财务审核事务内调用微信；“奖励入账”不代表微信零钱已到账，后者以原支付回调/查单结果为准。存量已完成归档数据不自动重建财务审核或补发奖金。

- 一期静默开始，前端不宣传具体开始日期或倒计时；2026-10-19调整内部统计覆盖北京时间2026-08-01 00:00至2027-01-01 00:00，不含结束时刻，支持8月至12月月榜。创建和首次有效归档都须在统计期间；8月前历史工单不补计，归档须报告审核通过。
- 知识沉淀统一按提问时间 `tasks.created_at` 的北京时间自然月归属贡献，问题列表的时间排序及展示使用该字段。例如8月提问、10月完成归档的工单计入8月，不计入10月；`first_approved_at` 保留真实首次有效归档时间，不用提问时间覆盖。重开、重提或更换报告不增加次数、不更换首次计分用户或跨月重计。
- 日期口径调整不自动创建缺失的知识发布记录、不重建已冻结或已发奖快照、不补发奖金、不更改财务审核与提现规则；存量异常闭环须单独核对。
- 提单与接单按用户归并为唯一综合计奖月榜；有效贡献数降序，相同再按相关当月工单收到的有效点赞数降序。前三各100元、第4—10名各50元，不分角色另发一份。综合榜原计分、冻结快照及计奖保持不变，独立角色榜不新增分类奖金。
- 最佳提问人榜仅包含当月有效沉淀工单的提问人，按提问数量独立排名；最佳解答人榜仅包含对应工单的解答人，按接单/解答数量独立排名。仅报告通过但待财务审核、财务驳回或尚未归档的工单不计入；财务通过、奖励入账并完成公开归档后计入，不要求用户已提现或微信零钱转账成功。两个榜各自只累计本角色工单的有效获赞作为同数量排序依据，再按最后贡献时间及用户ID稳定排序；只有另一角色贡献的用户不占本榜名额。（2026-10-21调整）
- 同用户同工单双角色暂计一次并标记待确认；完全同分若跨第3/4或第10/11奖励边界，最终核验暂不通过，不能自行扩大奖励名额。
- 全部登录用户可查公开榜单及通过报告，提单/接单身份可公开，审核人身份始终不公开。未通过正文不进入公开问题榜。
- 后台首页“知识贡献榜”整块卡片（标题、“查看榜单”入口、前三名和提示文案）由独立权限 `frontend:admin:knowledge:show` 控制。权限管理显示“显示知识贡献榜”启停开关，角色管理可对任意系统/项目角色勾选或取消；用户任一实际角色获得该权限且权限已启用即可显示，不再按角色名称写死。未勾选默认隐藏，用户名admin、`isAdmin`、通配权限及原角色名称不替代明确授权；全局开关关闭后所有角色均隐藏。初始化仅补充权限定义，不自动给任何角色授权，不重置已有的启停或角色配置。
- 用户详情继续下发 `can_view_knowledge_contribution`，前端默认隐藏，角色加载失败、退出或切换账号时不沿用旧标记，隐藏时不请求卡片榜单数据。配置后刷新用户详情生效；角色权限授予/撤销及权限更新/删除清除当前进程缓存，多进程其余实例最多沿用现有60秒缓存。本次仅控制首页卡片可见性，不改变公开知识接口、独立榜单页面或匿名审核的原有访问规则，不新增数据库表或字段。
- 最佳提问人和最佳解答人各自预览本榜前三名，完整人员榜各展示本榜前十名，头像每行三人；本榜仅显示对应角色的数量、名次、有效获赞及实际已获金额，不混入另一角色数量或综合名次，综合名次仅在综合榜展示。点击可按月份查看该用户提单/接单的已公开归档工单，不因此开放未归档或原始私有工单。角色筛选及排名使用首次发布的贡献归属，不按后来改派的人重新计分；同人同工单双角色在两个独立榜各计一次，综合榜仍去重计一次。
- 已公开知识详情提供独立讨论区，登录用户可发布1—2000字纯文本并分页查看；不公开原工单内部评论，讨论不改变工单状态、不计贡献或奖金。审核人参与讨论时作者匿名，正文继续隐藏审核人身份及敏感信息；问题撤回或失去有效公开资格后讨论不可读写。
- 平台名单派审时仍优先回避提单人、当前接单人及报告作者，候选不足时沿用派审服务的回落策略；前置派审成功后，以实际分配结果为准，不再因审核人兼为提单人、接单人或报告作者而拒绝提交、通过或驳回。派审失败或未选出审核人不能提交，兼容参数不能代替派审结果。匿名报告仅当前分配审核人可处理，改派后原审核人无权操作，审核动作仍须状态及revision匹配、通过必填意见与价值点、驳回必填意见。审核人不能用原任务详情、文档、关联列表或WS绕过匿名页面；财务审核及奖励发放流程不变。（2026-10-21调整）
- 榜单总览为平台指定名单、已有分配/意见记录的人员及管理员展示评审工作台入口；名单人员无需先收到任务。入口可见不代表获得其他人的报告权限，管理员也不能代看/代审未分配给自己的报告。待审数量及列表不受活动月份限制，审核身份统一匹配用户ID/账号/OpenID。
- 通过、驳回均须意见；通过另须价值点。驳回意见只供当事人及该意见作者，历史按报告提交版本保存，重提不覆盖。
- 活动报告须包含问题概述、问题场景、复现条件、原因分析、解决方案、验证结果、适用范围、遗留问题八个Markdown章节，各节正文不能为空。AI初稿不能覆盖已有或已经提交的内容。
- 点赞按用户/工单去重，可取消；本人提单/解答及当前审核的问题不能自行点赞计奖，风险无效或待核验点赞不计有效获赞。月榜用事件还原月末点赞状态。
- 每个用户按北京时间自然日最多成功点赞5个不同问题，每日00:00重置；仅计当日成功点赞事件，历史仍有效的点赞不占当天名额。同日同题重复请求或取消后重赞不重复占额，取消及后续判无效不返还当天名额；失败请求不占额，取消操作不受限额拦截。达到上限后对新问题点赞返回429及中文说明，列表、人员工单与详情使用同一后端校验。首页知识贡献榜卡片及榜单页不常驻展示此规则，仅在用户尝试超额点赞时弹出后端限制提示，不增加奖金激励提示。（2026-10-21调整）
- 2026-10-16起知识榜单移除异常观察与月度结算入口及操作界面，管理员也不显示；不因移除界面自动发奖或删除历史奖励记录。2026-10-20起综合/提问/解答前三预览仅展示数量，不再展示预计奖金；2026-10-21起完整角色榜头像下仅展示本榜的提问数或解答数及已获金额，月度综合排序和内部计奖不变。
- 已获金额读取现有奖励账本，按提问月份汇总 `task_archive` 的 `reporter`/`assignee` 奖励及通过原幂等来源ID关联的当月 `knowledge_monthly` 奖励。只计 `pending`、`withdrawing`、`success`、`expired`，即财务已通过的历史入账金额，包含未提现、提现中、已到账及曾入账后过期的奖励；待审、驳回、审核人奖励和无关奖励不计。跨月发奖仍归原贡献月，不按发奖/提现日期移月；无实际入账记录显示0，不能用预计奖金回填，也不将展示投影写回冻结快照。
- 奖金激励方式由专门入口提醒，知识首页及榜单各页不再分散展示奖励金额规则、叠加规则、核验/发放或结算说明；后端内部提示不直接透出。排名、计奖和奖励数据不变；本轮不新增该提醒入口。榜单顶部文案为“让每一次问题的解决，都沉淀为知识。”，“问题榜单”更名为“知识榜单”。优质问题卡片整体可进入公开归档详情，点赞不触发跳转，返回保留列表上下文。
- 保留的后台兼容接口仍要求admin或 `backend:knowledge_incentive:manage`；异常核验不作为第二轮内容审核，未完成既有核验不得入账月榜奖金，前端不再提供这些操作。
- 后台兼容服务仍保留月末冻结、风险修订、重新核验及发放幂等保护；发放中禁止并发更改计奖点赞。月榜奖励通过 `knowledge_monthly` 来源幂等入账，可与单题、优质奖励叠加。
- 入账不等于微信转账成功；提现继续使用现有奖励/转账链路。本次未新增单题6元自动入账，优质奖金规则待定不能按0元完成结算；挂赏追加与活动宣传轮播仍在后续范围。

### 7.1 高价值问题独立专区（2026-10-20）

- 平台管理员独立发布问题、悬赏整数分金额及截止时间；工单关联可选，不建占位工单。独立问题公开为“平台发布”，关联问题为匿名提问人，答案题内匿名，发布人不默认获得提问奖。
- 状态及结果管理仅允许原admin身份或全局“超级管理员/管理员”角色；服务端派生 `can_manage_knowledge_challenges`，前端不能通过普通内容审核/财务角色或按钮标记获得管理权。原知识贡献榜卡片可见性权限继续控制首页同级高价值卡片，公开内容接口对登录用户开放。
- 到期无内容审核、无专家派审、无全量管理员确认；按有效答案赞降序、首次正式提交时间升序、答案ID升序选出唯一最佳，零赞同样排序。无已提交合规答案则结束且无解答奖，草稿不参评。
- 题赞只决定问题榜热度；普通问题、关联同题、独立问题共用北京时间每日5题额度，取消不返额、跨入口不重复占额。答案另计每日5条，不得自赞；用户行锁序列化额度检查。
- 仅截止前、征集中且可见的问题允许新增答案/修订/计奖点赞；后台每60秒扫描到期状态，页面和写接口不依赖扫描及时性。暂停不自动延期，到期仍自动结算；结果及奖励写入同一事务，失败可重试。
- 每人每题的已发布解答仅可重新提交修改一次；卡片编辑入口仅对本人可用，进入编辑时明确提醒。首次发布、保存私有草稿及取消编辑不消耗修改次数；成功提交修订后，草稿及再次提交均由后端拒绝。复用答案正式修订历史计数，不新增数据库字段；修订保留原答案ID、点赞及首次提交时间，截止后仍不能修改。
- 管理员可暂停/恢复/截止前延期/取消/隐藏；已结算后可不予通过、改选或恢复截止快照中的合规回答，原因及版本必填，参与者不得自行调整本题结果。已生成的财务记录不直接覆盖、删除或自动改发第二名，差异留待原财务路径处理。
- 最佳解答以 `knowledge_challenge` 独立来源、问题ID及 `answerer` 角色幂等创建奖励，进入既有奖励管理；不复用 `task_archive` 三方来源，不改变原审批、转账、提现或原工单状态。
- 工单来源按原提问时间，独立来源按首次正式发布时间归属北京时间自然月；草稿、编辑、恢复不重置月份。不自动生成原提单/接单贡献数或扩展原活动资格。
- 社区优选知识标注未经专业验证，在专区已结束及结果入口可读，不虚构归档报告、审核意见或标准RAG认证。首次实现以文字解答为主，不新增附件上传/脱敏副本系统，不将社区内容自动摄取为标准RAG答案。
- `KNOWLEDGE_CHALLENGES_ENABLED=false` 停止新发布、参与和到期生成新奖励，历史浏览、管理纠正和已存在财务记录仍按原规则保留；不会撤回已支付资金。
