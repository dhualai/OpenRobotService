## 一、产品愿景与产品边界

### 1.1 一句话定位

一个面向工业移动机器人（AGV/AMR）行业的、开箱即用、可自托管的微信服务号平台，覆盖 AGV/AMR 项目**进场前准备 → 部署实施 → 报障运维 → 交付管理**的全生命周期，服务 **B 端**（机器人公司/企业客户/项目管理方）与 **C 端**（现场工程师、客户方一线使用者），并由 AI 沿"需求 / 供给 / 管理"三种视角全流程深度参与引导。（详见 [PRODUCT.md](./PRODUCT.md) 一、二节）

### 1.2 产品边界声明（重要，用于对齐团队认知）

我们做的是覆盖 AGV/AMR 项目**全生命周期**的项目管理平台——从进场前准备、部署实施，到报障、处理、运维管理的完整链路，同时服务 **B 端**（机器人公司/企业客户/项目管理方）与 **C 端**（现场工程师、客户方一线使用者）。**不做**售前技术方案生成类产品（如通过 AI 对话输出选型/部署技术方案）——那属于决策链路更前端的另一类工具。这个边界决定了本产品里 AI 引导的目标是"**精准诊断问题 + 推进任务闭环**"，而不是"生成方案文档"。团队在做功能取舍时，凡是偏向"方案生成"的能力都不在本产品范围内，遇到此类需求应识别为范围外并升级到产品经理确认。

> 已知市场上存在面向 AGV 售前场景的 AI 对话工具（输出技术方案类），与本产品赛道不同，此处不做竞品分析，仅做边界区隔说明。

### 1.3 北极星指标（3-6 个月）

远期目标是成为"好用且通过 AI 引导的交付平台"。"好用"必须是可测量的，而不是主观描述，建议锁定以下 5 个指标作为 3-6 个月的验收标准：

| 指标 | 定义 | 现状 | 3-6个月目标 |
|------|------|------|------|
| **AI 自助解决率** | 「我要摇人」在线咨询中，AI 不转人工即让用户认为问题已解决的比例 | 待建立埋点 | **[待团队拍板目标值]** |
| **转人工信息完整度** | 转工单后，人工工程师平均需要向用户二次追问的轮次 | 待建立埋点 | 趋近于 0（AI 应已收集齐全信息） |
| **工单闭环时长** | 从提交到 `closed` 状态的中位耗时 | 待建立统计 | **[待团队拍板目标值]** |
| **服务号活跃度** | 月活跃用户数 / 次周留存率 | 待建立统计 | **[待团队拍板目标值]** |
| **知识库净增有效条目** | 每月经人工审核入库的新知识条目数（体现"越用越聪明"） | 0（尚未跑通知识生产闭环） | **[待团队拍板目标值]** |

> 这 5 个指标的具体数值需要产品经理牵头团队在本周内拍板，本文先给出指标定义与埋点需求，作为后端/AI 工程师本周需要预留的数据采集点。

| 环节 | 前端职责 | Agent（知识库/问答）职责 |
|------|---------|------------------------|

| 边界 | 不自行判断"能否解决"，只透传 Agent 的判定结果做 UI 展示 | 不负责工单列表/详情等纯展示型页面的数据组装 |

> 该 Agent 的模型/Prompt/流程版本迭代记录，见 [十二、AI Agent 版本迭代管理规范](#十二ai-agent-版本迭代管理规范)。

```
- 边界与异常：<网络失败/超时/知识库无命中/权限不足等场景的处理>
- 验收标准：<可勾选的具体断言，例如"输入XX后3秒内返回流式响应首字节">
```

| 处理草稿 | 提供任务详情上下文接口给 Agent 调用 | 生成处理结果草稿文本，供工程师编辑后提交 |
| 边界 | 派单的最终写入动作、状态机校验（`ALLOWED_TRANSITIONS`）始终由后端把控 | Agent 只做"建议"，不直接修改任务状态，避免 AI 误判导致派单错误无法追溯 |

> 该 Agent 的模型/Prompt/流程版本迭代记录，见 [十二、AI Agent 版本迭代管理规范](#十二ai-agent-版本迭代管理规范)。

### 7.3 状态机（沿用架构文档定义，本周不改动）

```
待派单 → 已派单 → 处理中 → {待讨论 / 已上报 / 已解决 → 已关闭}
```

> 已解决 → 已关闭 支持"重开"回到处理中；已关闭时触发知识生产闭环（AI 总结 → 人工审核 → 入知识库），此闭环是否本周启动需产品经理确认（见开放问题）。

### 7.4 功能点规格

沿用第六节模板，**[待后端 Owner + 派单 Agent Owner 认领并逐条补全]**。

以下决策已在此前的 admin 模块设计评审中确认，本周实施必须遵守：

- `管理人员/管理员` 对应后端角色 `leader`；`admin` 为平台超级管理员

- 机器人数据 v1 仅手动导入，USP 推送接口暂缓，但表结构预留未来对接接口
- Admin API 前缀统一为 `/api/admin`
- 前端新增集中式 API 模块 `frontend/src/api/admin.ts`
- 日报唯一性约束：`(project_id, report_date, reporter_user_id)`，一人一项目一天一份
- Admin 模块与共享前后端基建、AI 内部实现保持隔离，仅做最小化组合根注册
- 旧页面处置：进度看板并入 dashboard；人员看板/项目HR/资源管理从导航移除但保留代码
- 目标任务生命周期：`pending_assignment → assigned → in_progress ↔ waiting → resolved → closed`，上报是独立维度；admin 侧只能通过任务模块契约/适配器消费，不得重构任务模块本身

## 十二、AI Agent 版本迭代管理规范

**Owner**：知识库/问答 Agent 工程师、派单 Agent 工程师、风险分析 Agent 工程师，各自独立维护自己负责的 Agent。

### 12.1 为什么需要

三个 Agent 都会持续迭代模型选择、Prompt、检索/流程策略。没有版本记录会导致改动原因无法追溯、效果变差不知道回滚到哪个版本、产品经理/测试无法追溯某次效果变化的原因。

### 12.2 文档存放规则

每位 Agent 工程师在 `docs/agents/` 下维护**各自独立**的版本文档，不共用一份文件：

| 文档 | 对应 Agent | Owner |
|------|-----------|-------|
| `docs/agents/knowledge-qa-agent.md` | 提单/知识问答 Agent（我要摇人） | 知识库/问答 Agent 工程师 |
| `docs/agents/dispatch-agent.md` | 派单 Agent（系统任务） | 派单 Agent 工程师 |
| `docs/agents/risk-agent.md` | 风险分析 Agent（后台管理） | 风险分析 Agent 工程师 |

### 12.3 每次迭代需记录的内容模板

```
### v<版本号> · <日期>
- 变更类型：模型切换 / Prompt 调整 / 流程逻辑变更 / 检索策略变更
- 变更内容：<具体改了什么>
- 变更原因：<为什么改——效果不好？新需求？成本优化？>
- 效果对比：<若有 A/B 或前后测试数据，没有则写“待观察”>
- 回滚方式：<如何恢复到上一版本>
```

### 12.4 更新时机与验收挂钩

- 每次真正调整并上线后**即时记录**，不允许积攒到周末补写
- 涉及 Agent 变更的功能点验收时（见 11.2 提测标准），需检查对应版本文档已更新，作为验收标准的一部分
