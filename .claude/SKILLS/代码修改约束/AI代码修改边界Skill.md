# AI 代码修改边界 Skill

> **用途**：约束 AI（Claude Code 等）在本仓库（OpenRobotService）修改代码时的行为边界，防止"顺手改了别人的代码"。产品经理要求：AI 只能修改与当前主线任务相关的内容；凡涉及修改基座（共享前后端基建）或其他人负责的模块，必须先问产品经理，得到明确同意后才能动手。
> **适用范围**：本仓库内所有由 AI 执行的代码修改任务。人工直接指示的、范围已经明确圈定的改动不受此约束限制（比如产品经理明确说"把 A 模块和 B 模块一起改了"）。

---

## 一、核心原则

1. **只改主线相关的代码**：当前任务要解决的问题、要实现的功能点，只触碰为完成它所必须修改的文件。不顺手重构、不顺手清理"看起来不对"的其他代码、不顺手升级依赖、不顺手统一代码风格。
2. **不确定归属就先问，不要自行判断**：如果一个文件是否"属于当前任务范围"存在疑义，默认视为**不属于**，先问产品经理，不要假设"应该没问题"就改下去。
3. **改动基座或他人模块前，必须先获得明确同意**：见第三节。这是硬性规则，不因为"改动很小"或"看起来是显然的 bug"而豁免——发现问题可以报告，但不能未经确认直接改。

## 三、什么算"需要先问"的改动

以下任意一条命中，**必须先向产品经理确认，说明要改哪个文件、为什么必须改、影响范围，等待明确同意后才能动手**，不能先斩后奏：

- 要修改的文件不在当前任务对应的模块目录下（对照第二节的表）。
- 要修改共享基建/基座代码——即使只是为了让本模块的新功能跑起来而"顺便"加一行注册、改一个共享类型定义、调整一个公共 hook。
- 要修改另一个 Agent（知识问答 / 派单 / 风险分析）的 Prompt、模型选择或内部流程代码。
- 要修改数据库迁移中涉及其他模块归属的表结构，或改动一个被多个模块共用的表。
- 要删除、重命名、大范围移动不属于当前任务范围的文件（哪怕是"看起来是死代码"）。
- 任务描述本身模糊，不清楚是否包含"顺带"修复某个跨模块问题。

**允许直接做、不需要先问的**：

- 在归属清楚的当前任务模块目录内新增文件、修改文件。
- 按已有约定做最小化的组合根注册（例如已在 `docs/PRD.md` 中明确写下"Admin 模块与共享前后端基建保持隔离，仅做最小化组合根注册"这类**已经拍板过**的例外，仍需照做但不必每次重新确认，除非改动明显超出"最小化"的范畴）。
- 纯只读的调研、排查、列现状（比如写 `docs/这周要修改的后台管理的功能点.md` 这类文档）。

---

## 四、如何"先问"

发现需要越界修改时，按以下格式向产品经理提出，不要含糊带过：

```
需要修改范围外的代码：
- 文件：<具体文件路径>
- 归属：<对照第二节，这是谁负责的模块/是否是基座>
- 为什么必须改这里：<不改会导致什么问题，或者为什么无法在当前模块内绕开>
- 影响范围：<这个改动可能影响到哪些其他功能/模块>
- 建议方案：<如果有更小侵入性的替代方案，一并给出>
```

等待产品经理明确回复"同意"/"可以改"/给出具体指示后，才能执行。如果产品经理说"先不改，记一下"，就只记录问题（可以写入 `docs/` 下的问题清单），不动代码。

---

## 五、边界之外的例外处理

- 如果任务本身就是产品经理明确要求的"跨模块联调"或"改基座"任务（比如"把 admin 的看板接口和共享的 API client 一起改一下"），本 Skill 不适用于该次任务已经被明确授权的部分，但**授权范围之外**的部分仍然适用本规则——不能因为一次任务被批准跨模块，就默认后续所有改动都不用再问。
- 任何一次"被批准的越界"，只对当次任务、当次明确列出的文件有效，不构成对未来类似改动的默认许可。
