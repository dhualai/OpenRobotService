# 07 - 常见故障场景

> 按用户可感知的**症状**分类，每个场景给出一套逐步排查路径。
> 每步检查包含：查什么日志 → 关键字符串 → 判断标准 → 下一步。

---

## 场景 1：机器人不动 / 没有路径

**症状**：机器人在原地不动，等了很久也没有新路径下发

### 排查路径

```
Step 1: 机器人状态是否正常？
  → 查 DynamicMap 日志: "收到机器人数据"
  → 检查目标机器人的相关日志:
     - "机器人: {id}---需要更新障碍" → 车已被标记为障碍
     - 机器人 can_plan_path 是否为 True
     - "机器人不在当前所有地图层上" → mapId 不匹配
     - "机器人类型不存在" → type 不在 robotTypes
  → 正常 → Step 2

Step 2: 机器人是否有任务？
  → 查 TaskManager 日志: "当前任务：{tasks}--------"
  → 检查目标 robot 的 cur_task 是否为 None
  → 有任务 → Step 3
  → 无任务 → Step 6

Step 3: TMS 是否在运行？
  → 查 TMS 日志: "TMS-SERVICES-ALIVE------"
  → 不在运行 → 检查 TMS.turn_on 和 TMS.paused 配置
     (⚠️ TMS.paused 默认 True!)
  → 在运行 → Step 4

Step 4: DynamicMap 是否可用？
  → 查日志: "动态地图----获取成功" vs "动态地图Actor获取失败"
  → 获取失败 → 检查 DynamicMap Actor 是否存活
  → 可用 → Step 5

Step 5: 路径规划是否被触发？
  → 查 DynamicMap 日志: "接收到TMS路径"
  → 没有 → TMS 子 Actor 未触发规划
     可能原因: get_robots_data() 返回 None (DynamicMap 正在更新中)
     查日志: "robot data updating:True" 是否频繁出现
  → 有 → 检查 update_paths 的校验日志:
     - "当前删除路径处理中----本次更新拒绝" → cancel 中
     - "路径校验通过---可更新" → 正常的
     - "Robot:{id}--路径已完成/已被取消/Index超过..." → 路径过期

Step 6: 没有任务 → 为什么没分配？
  → 查 TaskManager 日志: "当前所有车辆信息"
  → 检查目标 robot:
     - battery_percentage 是否 >= working_charging_battery (25%)
     - working_state 是什么 (CHARGING/ERROR?)
     - can_assign_business_task 是否为 True
     - cur_task 是否为 None
     - task_sync_state 是否为 True ("等待车辆任务同步")
```

## 场景 2：任务分配了但机器人不去执行

**症状**：TaskManager 显示"任务分配成功"，但机器人一直没有动作

### 排查路径

```
Step 1: 确认任务真的发送成功
  → 查日志: "任务分配成功: {[(robot_id, task_id)]}"
  → 如果没有 → 查日志: "任务分配结果发送失败"
  → 如果有 → Step 2

Step 2: 确认后端收到的任务
  → 查日志: "发送任务后端返回结果: {response}"
  → 检查 response.data 中每项的 status
  → 如果 status != "SUCCESS" → 后端拒绝该分配

Step 3: 确认路径已下发
  → 查 DynamicMap 日志: "发送路径---"
  → 查日志: "收到响应----{data}" (更新路径的后端响应)
  → 如果有 "后端current Task一致性不满足" → task_node_id 不匹配
  → 如果有 "该车异常状态----{id}----该车路径取消" → can_move=False

Step 4: 确认路径已到达机器人
  → 后端通过 /updatePaths 接收路径 → 下发给机器人
  → 检查日志: "存在路径未被接收" → 后端未全部接收
```

## 场景 3：机器人碰撞 / 绕路 / 路径异常

**症状**：机器人走错路、两车逼近、绕远路

### 排查路径

```
Step 1: 是否有碰撞告警？
  → 查日志: "检测到车辆碰撞-----Robot:{a}&Robot:{b}"
  → 如果有 → 两车距离 < 0.3m，物理上已经很近

Step 2: 检查锁区是否正常
  → 查 DynamicMap 日志: "锁区冲突：----{r1}--->{r2}"
  → 冲突 → 说明两个预约锁区重叠了 (应该由 MAPF 保证不重叠)
  → 查日志: "冲突触发-路径更新---{robot_id}--"
  → 如果有 exit_to_debug=True → 主动 exit(1)!

Step 3: 检查路径校验
  → 查日志: "路径校验失败" → 路径非法
  → 查日志: "路径中经过的库位点" → 违规进入库位
  → 说明 TMS 算出的路径有问题

Step 4: 检查是否有手动锁区阻挡
  → 查日志: "创建锁区成功" → 哪些锁区被创建
  → 查日志: "固定锁区冲突" → 固定锁区拦截了路径
  → 检查是否有锁区未启用但实际生效
  → 查 /getTrafficLocks 确认当前活跃锁区

Step 5: 电梯相关死锁？
  → 查日志: "[ELEV-DIAG] 进梯边等待占用,保留路径不截断" 在反复出现
  → 结合 "[ELEV-DIAG] 电梯占用刷新" → 检查占用是否被授予
  → 两车都在等同一电梯 → 死锁
```

## 场景 4：充电异常（不充电 / 乱充电 / 充不上）

**症状**：机器人电量低但不充电，或在不需要时充电

### 排查路径

```
Step 1: 确认自动充电开关
  → 查配置: auto_charge 是否为 True
  → 查配置: paused 是否为 False
  → 查日志: "充电逻辑判断 auto_charge: True charge_triggered: True"

Step 2: 检查电量阈值
  → 查日志: "各地图单元待充电车辆: {map_id: [(robot_id, battery)]}"
  → 如果为空 → 所有车都未达到充电阈值
  → 确认当前时段:
     - 非定时充电时段: 
        紧急 < 20%, 工作 < 25%, 闲时 < 70% + 空闲 > 300s
     - 定时充电时段内:
        工作 < 80%, 打断 < 90%
  → 查日志: "当前所有车辆信息" → 逐个确认每辆车的 battery_percentage

Step 3: 检查充电桩可用性
  → 查日志: "充电桩实时状态: {status}"
  → 如果某充电桩 enable=False → "充电桩 {id} 不可用"
  → 如果所有充电桩都被占用:
     - 常规充电: 放弃分配
     - 紧急充电 (< 20%): 尝试抢占 → 查日志 "尝试停止充电"

Step 4: 紧急充电排查
  → 查日志: "紧急充电Robot: {id} 当前分配充电桩: {id}"
  → 查日志: "尝试停止充电后端返回结果: {response}"
  → 如果 response.data 为空 → 抢占失败
  → 查日志: "紧急充电任务分配失败"

Step 5: 定时充电时段检查
  → 检查 fixed_times 配置 → 当前时间是否在定时充电时段内
  → 如果是，电量阈值会升高 (默认 80%/90%)
  → 可能刚好处在时段边界，行为突变
```

## 场景 5：地图加载失败

**症状**：POST /updateMaps 返回错误，DynamicMap 无法初始化

### 排查路径

```
Step 1: 确定错误类型
  → 查日志: "地图文件不存在----Map id:{id}---Hash:{hash}"
  → 原因: 4 级目录都找不到对应文件
  → 检查 map_dir 配置是否正确
  → 检查磁盘上是否有文件:
      ls {map_dir}/preprocessed_maps/{map_id}/{hash}.json
      ls {map_dir}/minimum_preprocessed_maps/{map_id}/{hash}.json
      ls {map_dir}/none_preprocessed_maps/{map_id}/{hash}.json
      ls {map_dir}/load_level_preprocessed_maps/{map_id}/{hash}.json

Step 2: 如果没有预处理文件 → 检查预处理是否执行过
  → 查 MapPreprocess 日志: "预处理开始----{request_id}"
  → 查 ProgressCollector: POST /updatePreprocessState
  → 如果 state="UNTREATED" → 从未预处理过
  → 如果 state="ERROR" → 预处理失败，检查错误消息

Step 3: 如果有文件但加载失败 → 检查文件完整性
  → json 是否合法
  → preprocessedData 字段是否完整
  → hash 是否匹配

Step 4: 增量刷新问题
  → 查日志: "单地图增量刷新请求" → 确认是增量模式
  → 查日志: "单地图增量刷新----maps 为空，忽略" → maps 为空
```

## 场景 6：预处理卡住或失败

**症状**：/updatePreprocessState 返回持续 PROCESSING，进度条不动

### 排查路径

```
Step 1: 确定当前卡在哪个阶段
  → 查日志: "Report progress-----Module:{module}"
  → moving_shape → 正在计算扫掠形状
  → distance_matrix → 正在计算距离表
  → conflict_matrix → 正在计算冲突矩阵
  → 如果 state="QUEUED" 但 module 无进展 → 尚未派发

Step 2: 如果卡在 moving_shape 开头
  → 查日志: "地图初始化中" 和 "地图初始化完成" 之间的时间
  → PathPlanningMap.__init__ 在大图上可耗时 30-97s
  → 如果两者之间时间超长 → 地图太大，正常等待

Step 3: 如果卡在 distance_matrix
  → 节点数 × 节点数的 Floyd-Warshall/Dijkstra
  → 大图可能需要几分钟
  → 检查 num_sub_workers (默认 8) 是否配置过低

Step 4: 如果卡在 conflict_matrix
  → 这是计算量最大的阶段 (shapely 几何运算)
  → 查日志: 如果有 cancel_request → 
     "cancel_all_children 超时({n}s)" → 子 task 没在 15s 内终止

Step 5: 检查是否 OOM
  → 查日志: "内存超限，停在 level {n}"
  → 或: "DistributedPreprocessor actor 异常死亡"
  → RayActorError 在 preprocess_base 中 → 说明 worker 被 kill 了
  → 降低 max_memory_ratio (默认 0.8) 或增大内存

Step 6: 分级阶段问题
  → 查日志: "[Dispatcher] submit map_id={id}" 
  → 查 Dispatcher 状态: "[Dispatcher] status" 
  → 如果 running 有任务但长时间不完成 → worker 可能在分级阶段卡住
  → 尝试 cancel 后重新预处理
```

## 场景 7：跨楼层调度不触发

**症状**：某楼层车多任务少，另一楼层任务多车少，但车不转移

### 排查路径

```
Step 1: 确认总开关
  → 查配置: enable_auto_cross_map 是否为 True
  → 查配置: paused 是否为 False

Step 2: 确认有合法通道
  → 查日志: "合法的转移：{elevators}--{traversal}"
  → 如果 traversal 为空 → 没有合法的楼层间通道
  → 检查 device_stations 中是否有 ELEVATOR 类型的设备点
  → 检查 functional_points 是否被正确更新

Step 3: 确认候选车辆
  → 查日志: "Cross Map Candidate Robots: {[robot_ids]}"
  → 如果为空 → 所有车被过滤掉:
     - task_sync_state 为 True
     - cur_task 不为 None
     - 在跨楼层中 (registered_transition_events)
     - 在当前楼层不够久 (< cross_map_interval = 15s)

Step 4: 确认拍卖计算
  → 查日志: "拍卖计算 Robot:{id} transition:{from}->{to} cost:{c} profit:{p}"
  → 如果 profit <= cost → 转移不划算，不执行
  → cost 主要取决于 transition_fixed_cost (默认 2000)
  → profit 取决于: 目标楼层任务数、充电桩数、机器人密度

Step 5: 确认跨楼层任务是否发送成功
  → 查日志: "跨楼层任务发送--{tasks}"
  → 查日志: "发送跨楼层任务返回结果: {response}"
  → 如果有 "跨楼层任务发送失败" → 后端不可达
  → 注意: 发送后 sleep(3) 等待后端处理
```

## 场景 8：AI 建图任务无响应

**症状**：POST /AIMakeMap 返回 taskId，但后续查询永远 PROCESSING

### 排查路径

```
Step 1: 确认任务是否被接受
  → 查日志: "AI地图生成任务已提交，task_id: {task_id}"
  → 如果没有 → 入参校验失败，返回了错误

Step 2: 检查进度
  → POST /getAIMapProgress → task_id 是否正确
  → state 值:
     - PROCESSING (percentage > 0) → 正在执行
     - PROCESSING (percentage = 0) → 可能后台线程还没开始
     - ERROR → 查 message 中的错误信息
     - NOT_FOUND → task_id 不对或超时清理 (>1h)

Step 3: 如果后台线程异常
  → 查日志: "AI地图生成失败: {error_msg}"
  → daemon=True 的线程如果主 Actor 退出会被杀
  → 检查 AIMapServiceActor 是否还活着

Step 4: 如果是动态卡车地图 (AIDynamicMapTruck)
  → 这是回调模式，没有 taskId
  → 查日志: "动态卡车地图任务已受理"
  → 查日志: "动态卡车回调已发送" → 是否回调到了 notificationUrl
  → 查日志: "动态卡车回调请求失败" → 网络问题
  → 查日志: "动态卡车地图生成失败" → 算法异常
```

## 场景 9：配置热更新不生效

**症状**：通过 API 改了配置参数，但行为没有变化

### 排查路径

```
Step 1: 确认更新是否到达服务
  → 查日志: "服务: {name}---收到动态修改配置参数请求: {data}"
  → 如果没有此日志 → ConfigManager._get_updated_config_parameters 校验失败

Step 2: 确认校验是否通过
  → 查 error: "配置项不存在: {section}" → section 名错误
  → 查 error: "配置参数不存在: {id}" → param_name 错误
  → 查 error: "参数未开放修改: {id}" → 不在白名单 → 用 admin 接口
  → 查 error: "参数类型错误" → value 类型不匹配

Step 3: 确认设置生效
  → 查日志: "设置动态修改：{key}：{old}---->{new}"
  → 如果有此日志 → 运行时已生效
  → 但 ini 文件只在 ConfigManager.update_config_parameters 时写入

Step 4: 确认所有相关服务都更新了
  → /refreshSettings 调用链:
     update_services_config_parameters() 遍历所有 service
  → 如果某个 service 的 actor 引用为 None (未启动) → 会抛异常
  → 检查: actors 字典中对应的 service 是否为 None

Step 5: 重启后是否还在
  → 查 ini 文件是否有新值
  → ConfigManager.save_config_parameters() → 写入 config_file
```

## 场景 10：Ray Actor 崩溃或不可达

**症状**：某个服务突然无响应，其他服务报"Actor获取失败"

### 排查路径

```
Step 1: 确认哪个 Actor 出了问题
  → 查日志: "动态地图Actor获取失败--{error}" → DynamicMap 不可达
  → 查日志: "动态地图Actor已关闭----" → DynamicMap 确认挂了
  → 每个依赖 DynamicMap 的 Actor 都会打印此日志

Step 2: 检查 DynamicMap 崩溃原因
  → 查 DynamicMap 日志最后几条
  → 如果有 "主动退出----" → exit_to_debug=True 时主动 exit
  → 如果有 "检测到车辆碰撞" → collision_terminate=True 时主动退出
  → 如果有未捕获的异常 → process_request 的异常处理中
    
Step 3: 检查是否可恢复
  → Actor 崩溃后 Ray 不会自动重启 (除非配置了 max_restarts)
  → 需要手动重启整个 usp-services 进程
  → 或者发送 /reset 请求(如果 Actor 还活着)

Step 4: 网络问题
  → Ray cluster 是否正常
  → 检查 Ray Dashboard
  → 检查 ray.init() 的 address 配置
```

## 场景 11：性能问题（延迟大、CPU 高）

**症状**：系统响应慢，机器人状态刷新延迟大

### 排查路径

```
Step 1: 检查刷新耗时
  → 查日志: "Robot更新耗时:{time}---"
  → 正常应该 < 50ms (取决于机器人数量)
  → 如果 > 200ms → 机器人太多或处理逻辑重

Step 2: 检查并发瓶颈
  → DynamicMap max_concurrency=4
  → 如果 refreshRobotStates 被调用太频繁
     (比如 200ms 一次但每次耗时 300ms) → 积压
  → 查日志: "当前路径-{route}-繁忙中" → 并发冲突

Step 3: 检查是否有大循环
  → refresh_robot_states 中 O(n²) 的碰撞检测 (collision_terminate=True)
  → try_release_node 中的 shape_conflict_free (几何交叉检测)
  → 如果机器人数量 > 100 → 考虑优化

Step 4: 检查预处理是否在后台跑
  → MapPreprocess 是计算密集型
  → 查日志: "Report progress" → 是否正在预处理
  → 预处理不应该和核心调度抢资源 (Ray 会隔离)
  → 但如果在同一台机器上，CPU 和内存竞争会影响

Step 5: 检查日志量
  → 每条 refresh_robot_states 都打很多日志
  → 大日志量可能拖慢 IO
  → 检查日志文件大小 (512MB × 128 个备份)
```

## 场景 12：服务启动异常

**症状**：start_services.py 启动报错或部分服务未启动

### 排查路径

```
Step 1: 检查 Ray 集群
  → ray.init() 是否成功
  → 如果是单机模式: ray.init() 无参数启动本地 Ray

Step 2: 检查配置文件
  → configs/dev_config.ini 是否存在？
  → 如果存在 → 优先加载 (连接 172.17.0.2)
  → 如果不存在 → 加载 configs/config.ini (连接 127.0.0.1)
  → 两个都不存在 → 使用默认配置 (只起 server)

Step 3: 检查各服务的 turn_on
  → 每个服务都有独立的 turn_on 开关
  → 如果 turn_on=False → actors 字典中为 None
  → HTTP 路由不会被注册

Step 4: 检查 actors 初始化
  → init 函数中会创建 Actor 但不会 wait
  → time.sleep(2) 等待启动
  → 如果 2s 不够 → Actor 已创建但未 ready → 后续调用可能失败

Step 5: 检查 run() 调用
  → dynamic_map.run.remote()
  → task_manager.run.remote()
  → tms.run.remote()
  → 如果 run() 中抛异常 → Actor 会退出 (非守护)
```

## 总结：故障排查决策树

```
收到问题报告
  │
  ├── 机器人不动？
  │     └── 场景 1 (机器人不动/无路径)
  │
  ├── 任务分配问题？
  │     └── 场景 2 (分配了不执行)
  │
  ├── 碰撞 / 绕路？
  │     └── 场景 3 (碰撞/路径异常)
  │
  ├── 充电问题？
  │     └── 场景 4 (充电异常)
  │
  ├── 地图相关问题？
  │     ├── 场景 5 (地图加载失败)
  │     └── 场景 6 (预处理卡住)
  │
  ├── 跨楼层问题？
  │     └── 场景 7 (跨楼层不触发)
  │
  ├── AI 服务问题？
  │     └── 场景 8 (AI建图无响应)
  │
  ├── 配置问题？
  │     └── 场景 9 (配置热更新不生效)
  │
  ├── 服务崩溃？
  │     └── 场景 10 (Actor崩溃)
  │
  ├── 性能问题？
  │     └── 场景 11 (延迟大/CPU高)
```
