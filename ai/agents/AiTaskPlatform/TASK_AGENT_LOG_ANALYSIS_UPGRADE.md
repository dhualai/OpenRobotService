# 日志分析升级方案：建立「系统的思考方式」（通用诊断推理框架）

> 状态：方案提议（待评审）
> 背景：2026-08-27 工单 322 实测暴露 3 大问题——**不智能**（时间窗/结论错）、**极慢**（单次 1.5h）、**不系统**（LLM 乱猜）。根因是 LogSubAgent 给 LLM 的只有"通用规则 + 客观事实"，**没有一套系统的思考方法**，LLM 不知道"看到一个现象该怎么一步步推理"。
>
> **核心立场**：我们不要靠一张"高频现象手册"来穷举每种故障——那不智能、不可维护。我们要的是**一套通用的、可复用的系统思考方式（诊断推理框架）**，让分析智能体对**任何**现象（折返、不动、慢、错位、通信断……）都能自主地、有条理地推理到根因。"车辆折返"只是用来**验证这套框架能走到正确根因**的一个例子。

---

## 一、一句话目标

> 把日志分析从「让 LLM 自由 query」升级为「**给它一套系统的推理方法论**：先定义问题 → 拆系统边界 → 分层定位 → 假设-验证-排除 → 时间/对象交叉对照 → 跨模块归因 → 收敛报告」。

这套方法论与**具体故障类型无关**，是"一个人如何系统排查问题"的思维过程，沉淀成 Prompt / 推理循环 / 程序护栏。

---

## 二、通用诊断推理框架（系统思考方式的 7 步）

以下 7 步是**任何故障**都适用的通用推理过程。关键在于每一步都"该查什么、看什么判断、怎么收敛"，而不是让 LLM 在日志里乱翻。

```
① 问题锚定（Define）
   现象是什么？何时发生？哪个对象（车辆/任务/模块）？是否偶发/持续？用户给了什么线索？
   → 产出：{现象, 时间窗, 对象, 偶发/持续}——所有后续聚焦的基准

② 系统边界与依赖链（Model）
   这份日志属于哪个模块？信号从产生到呈现经历哪些环节？
   现象所在模块 ≠ 根因所在模块（车端报错可能来自全局规划/TMS）。
   → 产出：嫌疑环节的依赖链（如 车端 ← 调度规划 ← 全局规划 ← 他车状态）

③ 分层定位（localize，从现象向根因走）
   对每个现象，列出"最可能出问题的环节"候选，逐层向下钻取。
   例（折返）：先判断定位 or 路线 → 若是路线 → 看路线为何被重规划
   → 产出：一条"现象 → 中间环节 → 根因"的探索路径

④ 假设-验证-排除（hypothesize-verify）
   每走一步都带一个"假设"，用日志查询验证它、或排除它。
   → 产出：已确认假设清单 / 已排除假设清单（收敛的核心）

⑤ 时间/对象交叉对照（contrast）
   同一对象在正常时段 vs 异常时段对比（隔离是否偶发）
   异常对象 vs 其它正常对象对比（隔离是否该对象独有）
   是否有其它对象/事件在异常前发生（找到外部触发）
   → 产出：可靠因果——不是"出现了错误码"而是"这个变化导致现象"

⑥ 跨模块归因（attribute）
   沿信号流向查上游/下游：当前日志证据不足时，明确"需要哪个模块日志"。
   例（折返）：车端查不到根因 → 引导用户提供 TMS/全局规划日志 →
   发现高优先级车频繁【可调度↔不可调度】→ 全局规划反复取舍 → 折返
   → 产出：根因归属到正确模块（或明确缺哪份日志）

⑦ 收敛报告（report）
   根因一句话 + 证据链（关键日志行）+ 置信度 + 处置建议 +
   若证据不足 → 明确"需要补充什么数据"而非硬猜
```

**验收铁律**：每一步都必须"有据可依"——要么查日志验证，要么明确"此步需要用户补充数据"。**禁止**像 322 那样凭空用错时间窗、拿 79 行下结论。

## 三、用「车辆折返」验证这套框架（示例，不是要收藏的场景）

把 7 步套到"车来回走"，看框架如何把 LLM 系统地引到正确根因：

```
① 锚定：现象=南区车反复折返/任务不完成；时间=09:20 附近；对象=XQE-6/xp3-13；持续
② 模型：折返呈现在车端/调度，但可能根因在全局路径规划 ← 其它车辆状态（跨模块）
③ 分层定位：折返? → (a)定位问题 or (b)路线问题
     → 先查路线：该车该时段下发路线本身含折返点吗？
        ├─ 路线含折返点 → 路线问题 → 走④
        └─ 路线正常仍折返 → 定位/控制问题 → 查定位（分支收敛）
④ 假设-验证：假设"路线被规划成折返" → 查重规划触发
     → 该车一段时间内有时不折返 → 偶发 → 查【什么事件触发了重规划】
     → 验证：存在重规划/路径取消/一致性校验等前置事件
⑤ 对照：对比异常时段 vs 正常时段 → 找出异常前发生的【外部变化】（他车事件）
⑥ 跨模块归因：车端日志不够 → 引导用户提供 TMS/全局规划日志
     → 找到：有更高优先级车辆在不停【可调度↔不可调度】切换
     → 全局规划反复"考虑它→不考虑它" → 本车路线被反复重规划/挤出 → 折返
     → 根因正确归属【全局规划的优先级/可调度状态抖动】，而非车端
⑦ 报告：根因 + 证据链（高优先级车切换日志 + 本车重规划日志）+ 置信度 + 处置建议
```

> 关键：这 7 步不写死"折返"。换成"机器人不动"只是把 ③ 的分支换成"没任务/没路径/规划没触发/TMS停"，④⑤⑥⑦ 的推理结构**完全一样**。所以是**系统的思考方式**，不是现象清单。

## 四、落地改动（改代码结构，不靠堆场景）

### 4.1 System Prompt 升级：注入「7 步方法论」
让 LLM 显式走方法论，例如新增命令：
- `{"action":"anchor", ...}`（问题锚定：现象/时间窗/对象/偶发）→ 首轮必须先输出
- `{"action":"hypothesis", "step":N, "assumption":"…", "verify_query":{…}, "accept_if":"…", "reject_if":"…"}`
  → 每轮 query 必须绑定一个"验证假设"：通过走下一分支、被排除则换假设/收敛
- `{"action":"contrast", "kind":"time"|"object", ...}` → 强制"正常 vs 异常"对照
- `{"action":"attribute", "module":"TMS", "need_feed":"请提供TMS日志"}` → 跨模块归因/要数据
- `{"action":"conclude", "root_cause":…, "evidence":[…], "confidence":…, "next_step":…}`

### 4.2 首轮「锚定 + 聚光灯」注入（程序前置，不用 LLM 现想）
在 analyze() 里，用现有 discover_facts() + 工单上下文，先程序化产出首轮锚定文本注入：
- 解析出：疑似时间窗、高频车型/任务、错误密集时段、用户给的线索
- 直接告诉 LLM："现象来自工单：…；日志事实：…；请先锚定问题，再沿 ③ 分层定位"

### 4.3 跨模块归因 → 落到「要数据」而非硬猜
- ⑦ 收敛时，证据不足或需其它模块日志 → 结论必须带"建议用户补充：TMS/全局规划/定位…日志"
- 这正是 322 需要的（车端查不到根因 → 要 TMS 日志），做成框架自带的强制项

### 4.4 性能护栏（解决 1.5h，方法论副产物）
- _MAX_FEEDBACK_CHARS 命中过多时截断 + 聚合统计（高频错误短语 + 分布），不全文回灌几万行 —— P0 止血，独立硬伤，先修
- 时间窗越查越窄、"对象唯一化"引导，从机制上避免 R4 命中 9 万行

### 4.5 手册的角色（降级为"知识"，不是"穷举清单"）
- 手册只承载"领域知识"：各模块日志含义、关键信号关键词、正常流程串 —— 供 ②建模 和 ③分层定位 参考
- 不再靠手工罗列"每个故障场景的排查路径"。方法论驱动推理；领域手册提供证据语义。二者解耦：
  - 方法论（通用思考方式）→ 固化在 Prompt + 循环 + 护栏（代码）
  - 领域知识（每模块日志讲什么）→ 手册（数据，可迭代）

### 4.6 新增「CLI 只读排查工具」（U老师 自己用命令辅助分析）
**目标**：除了受控的 `LogIndex.query`（结构化定位：时间窗/车型/任务/错误码），再给 LLM 一个**受控只读 Shell 工具**，让它能像工程师一样对日志做灵活的文本级探查，作为 ③分层定位 / ⑤对照 / ⑥跨模块归因 的取证手段。
**约束（已对齐）**：
- 环境：**本地**（U老师 AI 进程所在机器），作用对象是已下载/上传/拉取的日志文件 + 缓存目录。
- 范围：**只读白名单** —— grep / head / tail / sed(-n 只读) / awk(只读) / wc / cat / sort / uniq / cut ；**禁止**写文件、删除、创建、管道到 `rm`/`>`/`>>`、执行未白名单命令（如系统管理/服务操作）。
- 防护：路径限制在日志缓存目录内；单命令**超时**（如 10s）；输出**截断**（复用 feedback 截断策略，防刷屏/防 LLM 卡死）。
- 集成：作为 7 步方法论的一个 action ——
  `{"action":"shell", "analysis":"本轮想验证的假设/探查目标", "cmd":"grep -n '一致性校验失败' debug_logs.log | head -50"}`，
  与 `hypothesis/contrast` 并列，命中结果同样回灌前需截断 + 聚合。

> 说明：这是"排查执行工具"，与方法论深度融合；跨模块要服务器日志时仍走 ⑥「要数据」提示用户补充（本次范围不含 SSH 拉取，除非后续单独立项）。

## 六、验收标准（用 322 判断框架是否"会系统思考"）

一条合格的分析，应体现**思考过程**而非结果硬凑：
- ✅ 首轮锚定：现象/时间(09:20)/对象(XQE-6)/持续
- ✅ ②建模：意识到"折返可能根因在全局规划/他车，而非车端"
- ✅ ③分层：先判"定位 or 路线"→ 聚焦路线重规划，而非一开始抓"一致性校验失败"
- ✅ ⑤对照：正常 vs 异常时段、他车 vs 本车 → 找到外部触发
- ✅ ⑥归因：需 TMS/全局规划日志时明确要数据，不硬猜
- ✅ ⑦报告：根因"高优先级车频繁可调度切换 → 反复重规划 → 折返" + 证据链 + 置信度 + 下一步
- ✅ 耗时：单次 <5-10 分钟（索引 build 除外）

## 七、风险与原则

- **方法论 ≠ 场景库**：验证的是"这套 7 步能让 LLM 对任一新现象自主推理"，不是为每个现象写手册。某现象反复出现才考虑固化为手册"知识"。
- **引导是软约束**：需配合 hypothesis 的 accept_if/reject_if + 步进护栏把游离的 LLM 拉回方法论。
- **领域知识渐进**：模块手册逐步补，但推理主框架（7 步）一步到位、通用、可复用。
