## 1. 现码和设计差在哪

当前主流程：`Step0 → Step1 → Step2 打标（模糊命中跳过 3–6）→ Step3 三路召回 → Step4 精排 → Step5 负载均衡(关) → Step6 LLM（失败交 None）→ Step7 对接人→项目经理`。  
Step5 负载均衡代码保留，配置 `enabled=false`，本版不打开。

| 设计点 | 改前 | 本版已改成 |
|--------|------|------------|
| Step0 指定人找不到 | 静默进智能派单，无 tip | 继续走后续，写 `specified_name`，tip 走 `build_redispatch_tip` |
| Step0 画像不完整 / 拼音 | tip 只在「未派到指定人」时生成 | 四种结果都按表写 tip（完整画像可不提醒） |
| Step2 模糊强信号 | 无 | 命中则跳过 3–6，进 Step7。词表本版含 `[问题描述不完整]` |

| Step4 倾向人 | 与对接人共用 ×2 + floor（且 floor 现码未生效） | `max(当前分, 0.9)` |

2. `ranking/fallback_decision.py` + `dispatch_flow.py` Step7：对接人 → 项目经理；都空则未指派 + tip

## 3. 关键口径（实现时按此写）

### 3.1 Step0 tip（与重派同一出口）

Step0 指定人和重派倾向人共用 `task_dispatch_log` 字段，GET 时由 `build_redispatch_tip` 拼文案。不另开 `tip_signals`。

| 情况 | 写入 | tip |
|------|------|-----|
| 人在，画像完整 | `preferred_id=此人`，`matched_pref=True` | 不提醒 |
| 人在，画像不完整 | 同上 + `profile.missing` | 您指定的接单人画像不完整 |
| 拼音全拼命中 | 同上 + `pinyin_match=True` | 拼音找到的是【谁】，有可能不准确 |
| 指定人找不到 | 无 `preferred_id`；`profile.specified_name=指定名` | 没找到您指定的【谁】，已按智能派单处理 |
| 指定多人 | 按顺序找人，派上的那人 + `specified_multi=True` | 工单暂时只允许分配一个处理人；同名则再叠同名句；画像不完整叠「接单人画像不完整。」 |

找不到人时，`specified_name` 挂到后续智能派单结果的 `profile` 上一起落库。Step1–6 有门槛：只有画像完整（部门、职级、责任模块）的人才能进候选池。Step7 对接人/项目经理是配置的兜底人，不看这道门槛。重派未派到倾向人：列表 / 气泡 / 详情同一条详情模板（谁没派上、改派给谁、原因、下一步），不再用「暂未采纳」短句。

### 3.2 Step2 打标

标签从本步起进 `ranked_scores` 和候选快照 `tags`，一路传到 Step6 prompt，中途不丢。

| 现码 tag | 新 tag | 来源 |
|----------|--------|------|
| 自提单人 | **提单人** | `ticket.creator` |
| 项目对接人 | 不变 | `project.contact_person_id` |
| 上次倾向 / 用户倾向 | **倾向接单人** | `ticket.preferred_assignee`（重派表单） |
| （无） | **原用户不满意的接单人** | `ticket.prev_assignee` |

不踢自提人（现码已是标记不踢，保持）。

模糊截断：

- 配置 `vague_strong_signals.enabled` + `keywords`
- 本版词表：`[问题描述不完整]`（出现在标题或问题描述即命中）
- `keywords` 为空 → 不截断
- 命中 → 跳过 Step3–6，直接 Step7，理由固定：「描述含模糊强信号，无法可靠召回」

### 3.3 Step3 L1 原因与人数

`LlmRecall` 仍返回分数给精排；另出原因字典给仲裁。

- `RecallResult.llm_reasons: {engineer_id: "一句话原因"}`
- prompt 的 JSON 从 `{engineer_id, confidence}` 扩成 `{engineer_id, engineer_name, confidence, reason}`
- 解析不到 reason 就空字符串，不阻断打分
- 原因只进 Step6 仲裁 prompt，不进提单人 tip

人数规则（不用分数阈值当主开关）：

- 候选人数 ≤ `single_round_max`（默认 12）：单轮只要 Top `single_top_k`（默认 5）
- 人多：按 `batch_size`（默认 8）分批，每批只要 Top `batch_top_k`（默认 3）
- 各批胜者并集全部进 Step4，不再做第二轮决选、不再按 5 截断（三批最多 9 人）
- 旧配置键 `final_top_k` 仅作 `single_top_k` 的别名

### 3.4 Step3 L3 转派（只留接口）

`history_recall.arecall` 返回值保持 `{id: score}`。另加可选旁路：

```python
recall_result.transfer_signals = {
    "boosts": {B_id: {"delta": +x, "reason": "..."}},
    "penalties": {A_id: {"delta": -y, "reason": "..."}},  # 用来削 L1 LLM 分
}
```

本版旁路恒为空。精排预留「先削 LLM 分再加权」，避免下版再拆 ranker。  
**不改** `task.py` reassign，不建表，不写 Qdrant。

### 3.5 Step4 精排

人已经不多，本步只算分排序，**不对仲裁再砍 TopK**。

- 取消对接人 ×2：`contact_bonus` 对对接人不再乘
- 倾向接单人：`total = max(total, 0.9)`，不加倍
- 对接人 / 提单人 / 原不满意接单人：只打标，不加分
- 职级轻折扣保持 0.90
- 权重仍 0.70 / 0.15 / 0.15
- 现码 `contact_floor`（0.8 且 `> 1.0` 才生效）实际是死代码，删掉，避免和 0.9 保底打架

### 3.6 Step6 仲裁（编号不改）

合法出口只有一个：`None`（很难决策 / 问题暂不清 / 调用失败 / 解析到名单外 id）。  
**禁止**在本层回精排 #1。

改动：

- 候选窗口 = 精排全量，不再 `[:topk]`
- `llm_decision_topk` 保留配置但本版不截窗（可置 0 = 不截）
- prompt 拆成：**公共铁律** + **产品附录**
  - 摇人吧服务号：沿用现有子界面 → 模块负责人逻辑（从硬线索改成附录，不按模块名硬套前端/后端）
  - 调度 USP / 车端：附录占位一句「本产品暂无额外规则，只用公共铁律」
  - 其它 / 未识别：只用公共铁律
- 铁律写入 prompt，解析也卡：
  - `engineer_id` 必须从「ID:」精确复制
  - 名单外 id / 自造 id → 视为找不到 → `None`
  - JSON 增加 `can_decide: false` 作为合法出口
- 选中某人：`reasoning` 仍是给提单人的一句话；日志另记「依据：L1 原因 / 错派 / tag」（不进 tip）
- LLM 异常：`return None`，不再造一条 #1 的 AssignmentResult

### 3.7 Step7 兜底（编号不改；Step5 负载均衡保留且关闭）

只执行，不再选人。

解析顺序：

1. 本单项目对接人（现有 `_resolve_contact_assignee`）
2. 本单项目经理：读 `project.project_manager_id`（库里已有；AI 侧 `ProjectDelivery` 已补只读字段）
3. 配置 `project_manager_id` 仅作项目字段为空时的最后兜底

这三人都是配置的兜底人，**不看** Step1–6 的画像完整门槛；人不在准入池也照派。

理由：

| 从哪来 | 理由 |
|--------|------|
| Step2 模糊截断 | 描述含模糊强信号，无法可靠召回 |
| Step6 交出来 | 当前画像下难以判定合适接单人 |

**对接人、本单项目经理、配置项目经理三者都空时的返回口径：**

- `assign_ticket` 返回 `AssignmentResult`：`engineer_id=""`，`profile.unassignable=true`，**不编精排 #1**
- Worker 写 `task_dispatch_log`（空 `assigned_id`），**不写** `tasks.assigned_to`，不发「已派单」通知
- GET / 列表走同一出口 `build_redispatch_tip`：提单人看到「暂时无法派单：项目未配置对接人和项目经理…」
- 工单保持「新建 + 未指派」；下一轮扫描再试；若仍无人可派，不重复刷日志轮次（tip 已在）
- 配置了对接人或项目经理后，下次扫描会真正派上，tip 被新一轮日志覆盖

设计稿写「二者必有其一」，实现按项目字段取，不再用「无对接人且 fallback 才转项目经理」的旧条件。

`FallbackDecision` 现码按分数选人，本版改成只接收「对接人 / 项目经理 + 理由」，不再看精排。

## 5. 数据流（改完后）

```
Step0 指定人
  ├ 命中 → 派指定人 + preferred_id/matched_pref → 写回
  └ 未指定 / 找不到（specified_name）→ 继续智能派单
        │
Step1 候选收紧（本版不动）
        │
Step2 打标（标签全传）
  └ 描述含 [问题描述不完整] → 跳过 3–6 → Step7
        │
Step3 三路召回（L1 带原因；转派旁路空）
        │
Step4 算分不截窗；倾向人保底 0.9；对接人不加分
        │
Step5 负载均衡（保留，enabled=false，流程未调用）
        │
Step6 仲裁（全链 + 铁律 + 附录）
  ├ 选中 → 写回（一句话理由给提单人）
  └ 很难决策 / 失败 / 名单外 id → Step7
        │
Step7 对接人 → 本单项目经理 → 配置项目经理
  ├ 有人 → 写回 fallback，带真实理由
  └ 都空 → 未指派 + profile.unassignable；写日志给 tip；不写 assigned_to
```

## 6. 风险

| 风险 | 等级 | 处理 |
|------|------|------|
| 不截 Top3 后仲裁名单变长、幻觉点名 | 中 | 解析卡 ID；名单外一律交 Step7 |
| 项目对接人、项目经理都空 | 中 | 配置兜底；再空则失败重试，不拔 #1 |
| AI 侧 `ProjectDelivery` 缺项目经理列 | 高 | 已补只读字段，不迁表 |
| tip 改生成条件后旧工单话术变化 | 低 | 无 `specified_name` 走原四分支 |
| 描述带 `[问题描述不完整]` 的单会跳过召回 | 中 | 仅认该标记；口语词不截断 |
| 转派空接口被误当成已学习 | 低 | 日志写明 `transfer_signals=empty` |

## 7. 验收（按批）

1. 指定「不存在的人」→ 智能派单仍出结果，提单人 tip 含「没找到」
2. 指定人画像缺部门 → 仍派此人，tip 含「画像不完整」
3. 「胡建南」拼音命中「胡健楠」→ 派后者，tip 提示可能不准确
4. 描述含 `[问题描述不完整]` → 跳过 Step3–6，派对接人或项目经理；无该标记则走召回
5. 重派：原接单人带「原用户不满意的接单人」，新填人带「倾向接单人」，且出现在 Step6 prompt
6. L1 日志 / 仲裁 prompt 能看到 `id（姓名）+ 原因`
7. 对接人综合分不再 ×2；倾向人分低于 0.9 时被抬到 0.9
8. Step6 返回名单外 id 或 `can_decide=false` → 派对接人 / 项目经理，理由不是精排 #1
9. LLM 调用失败 → 同上，不出现 “fell back to top1”
10. 对接人与项目经理都空 → 不派人；提单人 tip「暂时无法派单」；工单仍未指派
