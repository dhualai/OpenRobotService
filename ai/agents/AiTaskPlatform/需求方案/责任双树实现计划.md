## 0. 目标与非目标

**目标**

1. 通用树节点（不限层）+ `org` / `skill` 两棵树  
2. 人-节点挂载（solid / dotted）  
3. 技能树 v1 = 迁移现 `module_tree_nodes`；组织树 v1 = 公司→部门浅树 + department 建议挂载  
4. Assigner Step1 改为组织实线子树池；Step3 技能命中为主；虚线不进 Step1 hard  

**非目标（本计划不做）**

- 虚线自动推断进 hard  
- 完美无限深拖拽 UX（先 path + 展开 + 挂载编辑）  
- 技能树按代码仓库目录重建  
- 一次删光旧三层 API（先双读兼容）

## 1. 数据模型

### 1.1 新表（建议名）

**`resp_trees`**（树实例）

| 列 | 说明 |
|----|------|
| `id` | PK |
| `kind` | `org` \| `skill` |
| `name` | 如「公司组织」「技能-调度USP…」或统一一棵技能大根 |
| `status` | draft / approved（可与现审批对齐后置） |

**`resp_nodes`**（通用节点）

| 列 | 说明 |
|----|------|
| `id` | PK |
| `tree_id` | FK → resp_trees |
| `parent_id` | nullable = 根 |
| `name` | 展示名 |
| `description` | 业务描述 |
| `keywords` | JSON array |
| `anchor` | TEXT，技能树兼容旧 anchor |
| `owners` | JSON array of user_id（编制负责人） |
| `linked_node_id` | nullable，跨树弱关联（组织组 ↔ 技能域） |
| `sort_order` | 同级排序 |
| `legacy_ref` | nullable JSON，迁移留痕 `{product, iface_name, func_name, old_id}` |

索引：`(tree_id, parent_id)`；技能树迁移期可保留旧 `(product, func_name)` 唯一语义在应用层校验。

**`resp_node_links`**（人挂载）

| 列 | 说明 |
|----|------|
| `id` | PK |
| `user_id` | 工程师 |
| `node_id` | FK → resp_nodes |
| `link_type` | `solid` \| `dotted` |
| `source` | `manual` \| `synced_from_dept` \| `inferred` \| `migrated_from_engineers` |
| `confidence` | float nullable |
| 唯一 | `(user_id, node_id, link_type)` 或 `(user_id, node_id)` 以业务裁定（建议一用户一节点一条，改 type 即升级） |

### 1.2 旧表策略

| 旧资产 | 策略 |
|--------|------|
| `module_tree_nodes` | 阶段 A 只读源；阶段 B 迁移进 `resp_nodes`（skill）；阶段 C assigner/管理端切新表后冻结；阶段 D 再删 |
| `module_trees` | 若仍在，维持现策略，不扩大写入 |
| `users.responsibility_modules` | 过渡期仍可由技能树 solid 挂载 + owners **派生同步**（兼容准入校验）；长期改为读挂载 API |
| `users.department` | 只驱动「建议挂载」，不写 hard |

### 1.3 迁移脚本（阶段 B）

1. 创建 `kind=skill` 树；每个旧 `product` 作为技能树一级节点（或根下一级）  
2. 每个 `iface_name` → 子节点；每个功能行 → 叶子（keywords/anchor/owners←engineers）  
3. `legacy_ref` 写入旧 id，便于回滚对照  
4. 对每个 engineers[]：插入 `resp_node_links` solid + `migrated_from_engineers`  
5. 创建 `kind=org` 树：根「公司」→ 去重后的 department 名子节点；按 `users.department` 生成 **建议** solid（`synced_from_dept`），或先只写「建议」不落库等运营一键采纳（推荐：**先落 synced solid，管理端可改/可拆**，并出缺口清单）

幂等：按 `legacy_ref.old_id` / department 名可重复跑。

## 2. 后端 API（阶段 C）

路径建议挂在现有 admin 模块旁，或扩展 [`backend/app/modules/admin/api/module_tree.py`](backend/app/modules/admin/api/module_tree.py)：

| 方法 | 路径（示意） | 说明 |
|------|----------------|------|
| GET | `/admin/resp-trees?kind=org\|skill` | 树列表 |
| GET | `/admin/resp-trees/{id}/nodes` | 整树或懒加载子节点 |
| POST/PATCH/DELETE | `/admin/resp-nodes` | CRUD 节点（不限层） |
| PUT | `/admin/resp-nodes/{id}/owners` | 编制负责人 |
| GET/PUT | `/admin/resp-links` | 人挂载；支持按 user / 按 node 查 |
| POST | `/admin/resp-links/accept-suggestion` | department 建议 → solid |
| GET | `/admin/resp-gaps` | 缺口清单 |
| POST | `/admin/resp-trees/reload-ai` | 通知 AI 热更新（对齐现 module_tree reload） |

WebSocket 并发编辑：可后置于阶段 E；v1 先用节点行级更新（继承现功能行并发收益）。

服务层新建 `resp_tree_service.py`，**不要**在旧 `module_tree_service.py` 里无限堆分支。

## 3. 管理端 UI（阶段 C/D）

现页 [`ModuleTreeManage`](frontend/src/pages/admin/) 演进或并列「责任树」页：

1. Tab：**组织树** | **技能树**  
2. 左侧树（展开/path）；右侧：描述、关键词、owners、挂载人列表（实线/虚线标签）  
3. 人员页：展示实线/虚线挂载 + 「根据部门建议」按钮  
4. 缺口清单页：三列问题（无节点 / 无挂载 / 无 owners）  
5. v1 不做复杂跨树拖拽；弱关联用下拉选 `linked_node_id`

## 5. 阶段排期（建议）

| 阶段 | 内容 | 预估 | 完成标准 |
|------|------|------|----------|
| **A** | 表结构 migration + ORM + 空服务读写 | 小 | 本地可 CRUD 节点/挂载 |
| **B** | 迁移脚本：skill←module_tree_nodes；org←department | 中 | 双边数据可对账；旧 id 可追溯 |
| **C** | Admin API + 双 Tab 管理端最小可用 | 中 | 能改 owners/挂载、看缺口、建议采纳 |
| **D** | Assigner 双树消费 + feature flag + 单测 | 中大 | flag on 时 Step1/3 行为符合口径；flag off 旧行为不变 |
| **E** | 文档：更新 `派单系统说明.md` Step1；拓扑页；关掉 legacy 写入 | 小 | 口径与线上一致 |
| **F** | （可选）冻结并删除旧表 | 另议 | 观察期后再做 |

每阶段一次 PR；不要把 A–D 揉进单 PR。

## 6. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 迁移后 Step1 池过大 | 无组织命中不收紧；有命中用最深组节点；监控候选人数 |
| 运营不补挂载 | 缺口清单 + 准入 tip；department 建议一键采纳降摩擦 |
| 双写不一致 | flag 切换窗口只读旧或只读新；禁止长期双写 owners |
| 「车端软件」同名混淆 | UI 标明树 kind；linked_node_id 展示「关联组织/技能」 |
