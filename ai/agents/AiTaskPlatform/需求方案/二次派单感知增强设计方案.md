## 一、目标与背景

### 1.1 现状（已具备的能力）

现有二次派单链路已经打通（非从零开始）：

| 环节 | 现状 | 说明 |
|---|---|---|
| 入口 | 工单列表「重新派单」按钮 + 对话内工单气泡「重新派单」 | `HistoryTickets.tsx` / `ChatPanel.tsx` |
| 弹窗 | **必选** 倾向处理人（UserSelect）+ 可选备注 | 目前择人无排序、无画像提示 |
| 后端 | `POST /tasks/{id}/re-dispatch`，`preferred_assignee` **必填** | 清 `assigned_to` + 状态回 `new` + 写 `metadata_info.preferred_assignee` + 发布 Redis 事件异步重派 |
| 派单引擎 | `preferred_assignee` 作为**强加权信号**（×`contact_bonus`，默认 2.0），Step 2.6 被过滤时**强制保留** | 已是"增加倾向权重"，**并非 100% 采纳**（最终由 Step6 LLM 结合精排窗口决定） |
| 结果 | 派单 Worker 写回 `assigned_to` + metadata（`assignee_name/assign_confidence/assign_reasoning/assign_decision_type/assigned_at`） | 前端通过轮询感知新接单人 |

### 1.2 三板斧差距（本次要补齐的"感知"）

现有链路**作为决策黑盒**：用户看不到①意向权重语义、②候选排序与画像、③为什么没派到指定人。本次三需求分别补这三处感知：

| 编号 | 需求点 | 现状差距 | 设计要点 |
|---|---|---|---|
| R1 | 意向派单人提示 + 权重说明 | 弹窗"必选倾向人"无任何语义说明；且**强制必选**不符合"指定人不一定采纳"的语义 | **倾向处理人保持必填**、备注可选；文案明示"不保证 100% 采纳，仅增加倾向权重" |
| R2 | 候选按首次派单权重排序展示 Top10 + 人员画像 | `UserSelect` 无排序、无画像；**Top10 精排中间结果未持久化**，仅存于 worker 日志 | 快照并入新表 `task_dispatch_log.candidates`（见 §4.2） |
| R3 | 未派到指定人 → 被派人画像解释理由 + 固定派单引导 | 派单完成后只展示新接单人姓名，**无理由、无画像、无转派引导** | 结果透出画像+reasoning；未达指定人时给"讨论区转派单"引导 |
| R4 | Step0 指定**不约束画像** + 派到无画像人时提醒补画像 + 同名/拼音匹配处理 | Step0 按姓名静默取第一个命中，**无画像约束、同名不确定、无拼音兜底** | Step0 直接指派不校验画像；派单结果提醒补画像；同名按**画像完整度**、完整度相同走**单轮 LLM**；姓名未命中加**拼音**兜底 |

> **产品调性**：本次不新增"强制固定派单"按钮。倾向人始终是**加权**而非**锁定**；若用户要"必定派给某人"，设计上引导走**讨论区转派单**（复用现有 `operation_type=reassign` 转派链路），避免与智能派单的决策权打架。

## 二、总体交互流程（目标态）

```
【首次派单】智能派单 → 系统按精排权重 ①→②→③… 择一接单
      │
      ▼
【用户不满意，点「重新派单」】
  弹窗打开 ⟶ 请求: 获取候选列表(Top10)
      │        └─ ② 返回: 按"本次将沿用的权重顺序"排序的 Top10 候选人
      │                 每个候选人附【人员画像】(部门/职级/责任模块/职责/倾向标记)
      ▼
  弹窗展示:
    ├─ R1 提示条: 「意向处理人（必选）— 不保证100%采纳，仅作为倾向权重加权」
    ├─ R2 候选列表: Top10 权重排序（默认展开），从中选择意向人（必选）
    └─ 备注框（换人原因，可选）
      │
      ▼
  确认重派 → POST /re-dispatch（preferred_assignee 必填 + remark 可选）
      │
      ▼
  [轮询派单完成] ── 拿到新 assignee ──▶ 展示派单结果提醒（气泡/列表页单行）:

      └─ R3 引导: 「如需固定派单，可 @ 接单人在讨论区转派单」（纯文字）
```

## 三、需求逐条细化

### 3.1 R1：意向派单人提示 + 权重语义说明

**现状问题**
- 弹窗目前**强制必选**倾向处理人，与"指定人不一定采纳"的新语义冲突（用户会误以为选了就必定派到）。
- 无任何文案解释"倾向＝权重"。

**本次改动（前端为主，后端保持必填口径）**

1. **校验规则保持「倾向处理人必填、备注可选」**（维持现状口径）：
   - 现状：`ReDispatchRequest.preferred_assignee` 为 `str` 必填，弹窗"选择倾向处理人（必选）"。
   - **本次不放开必填**：倾向处理人仍必选，备注仍可选。理由：重派每次都应给算法明确的"倾向于谁"信号，避免"裸重派"退化为重复跑相同精排；同时强制必选与"不保证100%采纳（仅加权）"**并不矛盾**——必填=要求用户表达意图，加权=是否采纳由系统决定。
   - 本次 R1 的实质改动落在**文案与感知**：在必填选择的基础上，明示"倾向＝加权而非锁定"，消除"选了就必定派到"的误解。

2. **弹窗顶部提示条（文案样例）**：
   > 「可指定一位**意向处理人**。指定后系统会**增大该人的被选中权重**，但**不保证 100% 采纳**（最终以智能派单综合评估为准）。若需**必定派给某人**，请派单后在讨论区让接单人转派。」

3. **备注意义**：作为"换人原因 / 给新处理人的说明"，随 `preferred_assignee_remark` 透传给算法与系统评论；可填可不填。

**涉及改动点**

| 层 | 文件 | 改动 |
|---|---|---|
| 后端 API | `backend/.../tasks/api/task.py` | 校验与请求体**维持现状**（倾向人必填/备注可选）；无需改动或仅加返回结果字段 |
| 前端 | `HistoryTickets.tsx` / `ChatPanel.tsx` | 弹窗保持"必选倾向人+可选备注"；**新增提示条**（不保证100%采纳/仅加权）；配合 R2 候选列表 |
| 派单引擎 | 无需改动 | `preferred_assignee` 缺省即不启用，天然兼容 |

### 3.2 R2：候选 Top10（按权重顺序）+ 人员画像

**现状问题**
- `UserSelect` 只按用户列表/项目成员拉人，**无排序、无画像**，用户是"盲选"。
- 派单引擎**精排 Top 中间结果只在 worker 日志打印，未持久化**，前端拿不到"权重顺序"。

**核心数据问题：Top10 从哪来？**
派单引擎 `DispatchFlow.aassign()` 内部会产出 `ranked_scores`（按 `total_score` 降序，含 llm/semantic/history/total 各维度），但**不落库、不对外暴露**。要展示"权重顺序 Top10"，必须把该数据导出。以下三个方案按"实时性 vs 成本"权衡：

| 方案 | 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| **A 实时预演接口** | 新增 `GET /tasks/{id}/redispatch-candidates`：打开弹窗时调用后端 → 后端同步唤起 `assigner` 召回+精排 → 返回 Top10 + 画像 | 最新、权重与正式重派一致 | 每次打开弹窗都多耗一轮 **L1 LLM 召回**（成本/时延） | 可作为 B 的"刷新"增强（可选 M4） |
| **B 持久化精排快照** | 每次派单把 Top10（含画像摘要顺序）持久化到 **新表 `task_dispatch_log.candidates`（JSON 列）**；重派弹窗直接读最新一条 | 零额外 LLM、秒开；候选与结果同轮内聚；二次/多次重派重复用 | 快照可能因人员/负载/配置变化过时（标注"基于最近一次派单评估"） | ★ **首版主选** |
| **C 仅存 Top1 + realtime Top10** | 首次只存最终被派人，弹窗时才拉 Top10 | 折中 | 仍需预演 LLM，且无快照可读 | 少用 |

> **本次建议（采纳用户方向）**：首版 **B（持久化快照）为主**，且**候选快照不再单独给 Task 开新字段，而是并入新表 `task_dispatch_log`**：在派单日志表上加一列 `candidates`（JSON），把"**某一轮派单的完整评估**（候选 Top10 + 最终结果）"作为一个整体、逐轮落库。理由：① 候选与结果**本就同轮产生**，同表存放天然内聚、无需两张载体；② 天然保留**历史多轮快照**，弹窗默认读"最近一条"，可回看、可审计；③ 避免在 `tasks` 上再堆字段、也避开 `re_dispatch_task` 的 `meta.pop(assign_*)` 清理逻辑。A（实时预演）留作可选增强（M4）。

**人员画像数据来源与接口**
- 画像 = `EngineerProfile` 字段：`name / department(部门) / job_level(职级) / responsibility_modules(责任模块) / duty_text(职责)`。
- 建议新增"候选人画像"聚合接口返回结构（新增 `RedispatchCandidate` DTO）：

```jsonc
{
  "rank": 1,
  "engineer_id": "1001",
  "name": "张三",
  "department": "智能规划研究院",
  "job_level": 1,
  "modules": ["调度USP:监控:路径规划", "调度USP:调度:任务分配"],
  "duty": "负责无人车调度规划与路径优化……",
  "scores": { "llm": 0.95, "semantic": 0.0, "history": 0.30, "total": 0.79 },
  "tags": ["项目对接人"]   // 可选：项目对接人标记（拉起候选时用户尚未选倾向人，故不标用户倾向）
}
```

**前端展示（R2）**
- 弹窗候选人列表改为**按 `rank` 权重顺序**展示 Top10（**默认展开**，便于用户一眼看到推荐排序并从中选意向人）。
- 每候选展示：排名徽标 + 姓名 + 部门/职级 + 责任模块（chips）+ 职责一句话；用户从列表中**选择意向人**（必选）。
- 顶部提示"排序 = 系统按本工单匹配度的倾向权重（**本次重派将沿用的顺序**）"。

**涉及改动点**

| 层 | 文件 | 改动 |
|---|---|---|
| 派单引擎 | `dispatch_flow.py` | 将 `ranked_scores`（Top10）+ 画像导出为可序列化结构；或暴露一个 `get_candidates_snapshot()` |
| DB 模型 | 新增 `TaskDispatchLog`(表 `task_dispatch_log)` 含 **`candidates`(json)** 列 | 派单时将 Top10 快照写入该轮日志的 `candidates`（B） |
| 后端 | Worker 落库处 | 每次派单写一条 `task_dispatch_log`，候选 Top10 存 `candidates` 列 |
| 后端 API | `task.py` | 重派弹窗/详情读 `task_dispatch_log` **最新一条**的 `candidates` 返回（B）；可选 M4 再增 `GET .../redispatch-candidates`（A） |
| 前端 | 重派弹窗 | 换用带排序+画像的候选列表组件（读最新快照） |

### 3.3 R3：未派到指定人 → 被派人画像 + 理由 + 固定派单引导

**现状问题**
- 派单完成前端只显示新接单人姓名，**没有画像是谁、为什么是他、为什么没派到指定人**。
- 无"固定派单"出口引导。

**本次改动**

1. **派单结果信息透出画像 + 理由（读 `task_dispatch_log` 最新一条）**：
   - 派单 Worker 每次派单（含重派）写一条**追加式派单日志**到新表 `task_dispatch_log`（见下），记录：`task_id / dispatch_round / 意向人(preferred) / 实际接单人(assigned) / assign_reasoning / assign_confidence / assignee_profile(部门·职级·模块·职责)`。
   - 前端轮询到新 assignee 后，从该表**最新一条**取 `assigned + assignee_profile + assign_reasoning + assign_confidence`，生成派单结果提醒（气泡/列表页单行）。
   - **为什么新开表而不只塞 metadata_info**：
     - R3 判定需要"本次重派的意向人 X + 实际 Y + 理由"**成对留存**；而 `metadata_info` 的派单相关键在下次重派会被 `meta.pop(assign_*)` 清理、意向人也会被覆盖，无法解释"历史那次为什么没派到"。
     - 派单解释本质是**历史记流水**（1:N、append-only），天然适合独立表；新表同时为后续派单质量看板/评测集回流（见 `派单系统摸底与改进方案.md` §四 P1-④⑤、§七 D4）打基础。
   - 做法：`metadata_info` **不再存派单详情**（reasoning/confidence/画像 均移除，无读取方）；派单详情完全走 `task_dispatch_log`。`metadata_info` 仅保留重派意图键 `preferred_assignee / preferred_assignee_remark` 及其它非派单元数据。

2. **"未派到指定人"判定与文案（R3 情况②）**：
   - 判定条件：本次重派**用户指定了** `X`（preferred_assignee）**且** 最终 `assigned_to != X`（此时 `X` 画像完整）。
   - 命中 → 派单结果提醒展示：
     > 「您指定的意向处理人 **X** 因综合评估未被选中，本次派给了 **Y**。派单理由：<reasoning>。若仍希望由 **X** 处理，可 **@ 接单人 Y 在讨论区转派单**，或再次重新派单。」

3. **"派到无画像人"判定与文案（R4 情况①）**：
   - 判定条件：最终 `assigned_to` 对应工程师的 `profile.missing` 非空（画像不完整）。
   - 命中 → 派单结果提醒提示：
     > 「该接单人 **Y** 的画像还不完整，缺少：<missing 中的部门/职级/责任模块>。建议 **Y** 补全画像，以便后续派单更精准。」
   - 说明：此分支不阻断派单，仅作画像补全提醒（Step0 不约束画像，R4）。

4. **被派人画像展示**（派单结果内）：
   - 部门 / 职级 / 责任模块（chips）/ 职责一句话 / 匹配置信度（`assign_confidence`）；画像字段缺失处显示"待补充"并关联 R4 的补画像提示。

5. **固定派单引导**：
   - 文案明示出口 = **讨论区转派单**（复用现有 `operation_type=reassign` 转派链路：在讨论区 @ 接单人，由其将工单转派给目标人，并给提单人/新接单人推送通知）。
   - **只做纯文字引导，不做「去讨论区」跳转按钮**（已定 D2）。文案如"……可 @ 接单人 Y 在讨论区转派单"，用户自行在讨论区操作。

**涉及改动点**

| 层 | 文件 | 改动 |
|---|---|---|
| 派单引擎 | `dispatch_flow.py::_log_assignment_result` | 将被派人画像 + reason 一并写入结果对象（供落库） |
| DB 模型 | 新增 `TaskDispatchLog`(表 `task_dispatch_log`) | 追加式：task_id/round/意向人/实际接单人/reason/confidence/profile(含**missing 字段**)/**candidates(候选Top10)** |
| 后端 | Worker 落库处 / `task.py` | 每次派单写一条 `task_dispatch_log`（含 `candidates`、`profile.missing`）；`ticket` 详情/重派查询读该表最新一条 |
| 前端 | 重派轮询完成处 | 读 `task_dispatch_log` 最新一条生成派单结果提醒；判定"未派到指定人"/"派到无画像人"；渲染对应解释与提示 |

### 3.4 R4：Step0 指派不约束画像 + 同名处理（新产品要求）

**产品要求**
> 走 Step0（提单人指定/倾向指定）时，对指定的工程师**不做任何画像约束**——只要明确了是谁，就**直接按姓名指派**，不校验该人画像是否完整/是否匹配工单。
> 目的：**以派单驱动画像补全**——先把人派出去，让其介入工单同时补全画像，避免"因画像不完整而派不出去"的死锁。

**现状（代码口径）**
- `dispatch_flow.py::_detect_preferred_assignee`（Step0）→ `_match_engineer_by_name`：**精确 > 包含匹配，返回第一个命中即指派**。
- 当前 Step0 **本来就不按画像过滤**（直接指派人），与该产品要求一致；真正的缺口是**同名（同名不同 user_id）时静默取第一个，可能派错人**。

**本次改动**

1. **Step0 规则明确定义「不约束画像」**：
   - 结构化指定 `[指定处理人:XXX]` / 倾向人 `preferred_assignee` → 只按身份匹配（**优先 user_id/工号**，其次姓名），命中即指派（`confidence=0.95`，`decision_type=auto`）。
   - **不校验** department / job_level / responsibility_modules 是否完整或匹配（`duty_text` 不作为完整性判定）；未命中姓名则走正常派单（延续现状）。
   - 派向"画像不完整"的人仍正常落库，并由派单结果提醒**提示其需补充画像**（见下）。

2. **同名（同名工程师多人）处理 —— 按画像完整度分配（决策 D6b，已定）**：
   - **根因**：`_match_engineer_by_name` 只取第一个命中，同名时依赖 engineers 顺序，不确定。
   - **已定规则**：同名命中多人时，**按画像完整度排序再分配**——
     - 对每个同名候选计算画像完整度：命中画像关键字段（`department / job_level / responsibility_modules`，`duty_text` 不参与）的数量/比例，**命中字段越多、画像越完整者优先**。
     - 即：**只要有画像（哪怕不完整）就优先于完全无画像的同名人派单**；不完全要求"画像完整"，只要求"相对更完整"。
     - **画像完整度相同时（如都完整、或都缺同一字段如部门）→ 用单轮 LLM 抉择**：因为用户意图范围已收敛到这几个同名人，Step0 明确指向的就是这些人，直接用**一次轻量单轮 LLM** 结合工单/备注/上下文，在**这 N 个同名人小集合内**挑一个，**不静默取第一个**、也不再默认走全量候选确认。
   - **同名也提醒用户**：一旦发生"基于姓名匹配命中多人"的同名场景，派单结果提醒额外提示"存在同名工程师，本次按画像完整度/LLM 评估选择了其中一位"，让用户知晓本次择人的依据。
   - 结构化含 user_id/工号时（A 方向）仍优先按唯一标识直接命中，不触发同名流程。

3. **拼音/近似名匹配 —— 同音近音错别字兜底（决策 D7，已定）**：
   - **触发时机**：Step0 姓名匹配（精确 > 包含）**全部未命中**时，才兜底触发。
   - **问题**：提单人指定"胡建楠"但打成"胡建南"，姓名精确/包含匹配不到，直接走正常派单 → 用户明确指定意图丢失。
   - **规则（确认：全拼一致）**：把输入名与每个工程师姓名**转全拼（pinyin）**比对，**全拼完全一致**即视为命中（捕捉同音/近音错别字，如 楠/南 均 `nán`）。
     - **模糊程度控制（"程度不大"）**：只做**全拼一致性匹配**，不引入编辑距离/部分拼音/首字母等更激进模糊——精准捕捉同音错别字，但不扩散成大量误匹配。
     - 多音字取常用读音；需引入依赖 `pypinyin`（加入 AI 服务 requirements）。
   - **置信度略降（确认）**：拼音命中终究非原字，`confidence` 由默认 0.95 **略降为 0.85**（`decision_type` 仍为 `auto`），以示"近似匹配、需用户确认"。
   - **命中多人**（同音名多人）→ 复用 **D6b 同名链路**（画像完整度 → 单轮 LLM），不静默。
   - **感知（重点，必做）**：拼音命中 **必须返回并提醒用户**——派单结果提醒提示"按拼音匹配到 **XXX**（与原输入不同字，如 胡建南→胡建楠），如非此人请更正"，让用户发现并纠正错别字。
   - **兜底**：拼音也未命中 → 返回 None 走正常派单（延续现状）。

4. **结果感知（派单结果的多分支）**：
   - **情况① 派到无画像的人**：派单结果提醒提示"该接单人的画像还不完整（缺：部门/职级/责任模块 中的哪些），建议其补全，以便后续派单更精准"。
   - **情况② 倾向人符合画像、但最终未派到**：派单结果提醒解释为什么没派到（reasoning）+ 转派引导（纯文字）。
   - **情况③ 存在同名**（`name_collision=true`）：派单结果提醒提示"存在同名工程师，本次按画像完整度选择了其中一位"，让用户知晓择人依据。
   - **情况④ 拼音/近似名匹配**（`pinyin_match=true`）：提示"按拼音匹配到 XXX（与原输入不同字），如非此人请更正"。
   - 情况①/③/④可叠加：同名 + 拼音命中 + 被派者画像不完整 → 多条提示并存。

**涉及改动点**

| 层 | 文件 | 改动 |
|---|---|---|
| 派单引擎 | `dispatch_flow.py::_match_engineer_by_name` | 姓名精确/包含未命中后，**拼音全拼一致**兜底匹配（`pypinyin`）；同名多人按**画像完整度**排序、完整度相同走**单轮 LLM** |
| 派单引擎 | `dispatch_flow.py` Step0 | 落库时标记：画像完整性（`profile.missing`）、是否同名命中（`name_collision`）、是否拼音匹配（`pinyin_match`） |
| 派单引擎 | `schemas.py::AssignmentResult` | **新增字段** `name_collision` / `pinyin_match`（bool，一路传到 Worker 落库） |
| 依赖 | `ai/requirements.txt` | 引入 `pypinyin`（拼音全拼转换） |
| 后端 | 画像完整性判定 | 定义 `profile.missing` 规则（判定字段=部门/职级/责任模块；`duty_text` 不参与）+ 同名完整度排序 |
| 前端 | 派单结果提醒 | 新增分支：派到无画像人→补画像提醒；符合画像未派到→解释+转派引导；同名→按完整度择人提示；拼音命中→近似名提示 |

### 3.5 匹配层实现细节（R4/D6b/D7 落地）

#### 完整匹配链（`_match_engineer_by_name`）

```
① 精确匹配 name → 唯一命中【直接指派】
② 包含/被包含匹配 → 唯一命中【直接指派】
③ ①/② 未命中 → 拼音全拼一致匹配（pypinyin，多音字取常用读音）
   └ 命中 1 人  → 指派，confidence=0.85，pinyin_match=true，必返回"按拼音匹配"提醒
   └ 命中多人   → 走下方"同名/同音多人抉择"
④ ①②③ 均未命中 → 返回 None，走正常派单
```

#### 同名/同音多人抉择（画像完整度 → 单轮 LLM）

1. **画像完整度排序**：按 `department / job_level / responsibility_modules` 命中数（多→少）排序；`missing` 越少者优先。
2. **完整度不同** → 取最完整者。
3. **完整度相同** → **单轮 LLM 抉择**：
   - **输入**：工单`标题` + `描述`（可含重派备注）。
   - **指令**：提示"用户已指定处理人，但匹配到多个同名候选人，请从中选定一位"；给出 N 个候选的 **`id` 列表（原样复制，保证与候选一致）**，要求 LLM 返回选定 `id` + 理由。
   - **输出**（结构化 JSON）：`{ "selected_id": "...", "reason": "..." }` 或 `{ "can_determine": false }`。
   - **处理**：
     - 选出且 `id` 合法（∈ 候选 id，且一致）→ 指派，`reasoning` 附 LLM 理由。
     - **分辨不出**（`can_determine=false` / 返回 `id` 不在候选内）→ **随机选一个**，返回提醒（派单结果提醒："同名未能区分，已随机选择"）。
     - **LLM 调用失败** → **兜底返回默认第一个**，返回提醒（"同名评估失败，已按默认选择"）。

#### confidence 落点
- 拼音命中：`AssignmentResult.confidence_score = 0.85` **直接改**（决策落地）；`decision_type` 仍 `auto`。
- 单轮 LLM 选出（非拼音）：confidence 维持默认口径。

#### AssignmentResult 字段扩展（直接加字段）
```python
class AssignmentResult(BaseModel):
    ...
    name_collision: bool = False   # 本轮是否同名/同音命中多人
    pinyin_match:   bool = False   # 本轮是否经拼音近似名命中
```
- Worker 落库时，把这两个标记与 `profile.missing` 一并写入 `task_dispatch_log`。

### 3.6 展示层交互细节（气泡卡片「派单结果提醒」单行）

**载体**：工单气泡卡片（`ChatPanel.tsx`）在底部操作区下方，**单独占一行**展示「派单结果提醒」条。

> **响应式确认**：**不在**「已派单·XX」与「[重新派单]」之间塞提醒（PC 可行，但**手机端二者几乎无间距**）。统一改为 **提醒条独立成一行**，放在操作区（已派单 + 重新派单）**下方**——PC/手机一致，无需响应式切换。

**结构示例（在截图的卡片底部操作区下方加一行）**：
```
✓ 已派单 · 张文星    [重新派单]
[派单结果提醒：指派人存在同名情况，已为您选择…]   ← 新增：单独一行，可点击
```

**交互规则**：
- **数据**：气泡基于**列表**数据渲染 → 列表接口 `GET /tasks` 每项带轻量 `redispatch_tip`（一句话摘要字符串，后端生成）。
- **展示**：`redispatch_tip` 单行渲染、**限宽 + 超长用 `...` 省略**（`text-overflow: ellipsis`）；无提醒则 `redispatch_tip = null`，该行不显示。
- **样式（颜色区分，重点）**：提醒条**使用警示色**（推荐琥珀/橙黄文字 + 可配浅底 + ⚠ 图标），**区别于卡片普通灰文与蓝色强调**，突出"需用户注意"；具体色值以设计规范为准。
- **点击**：点击提醒条 → **进入工单详情**（详情页可查看派单信息与评论区；重派结果的感知载体即气泡/列表页的提醒条，**无独立"结果卡片"UI**）。
- **文案前缀统一**：`派单结果提醒：` + 摘要。

**`redispatch_tip` 生成规则（后端，四分支 → 一句话，按优先级合并）**：
| 分支 | 摘要文案 |
|---|---|
| ② 未派到指定人 | `未派给您指定的【X】，已派给【Y】` |
| ④ 拼音匹配 | `按拼音匹配到【Y】（与输入【X】不同字）` |
| ③ 同名命中 | `指派人存在同名，已按评估选择【Y】` |
| ① 画像不完整（可叠加追加） | ＋`；该接单人画像不完整，待补充` |
| 无特殊情况 | `redispatch_tip = null`（不显示该行） |

### 3.7 展示层交互细节 —— 列表页 `HistoryTickets.tsx`「派单结果提醒」单行

**载体**：列表页每个工单条目，**在「所属项目」（`history-row__project`）之下、人员流转（`task-card2__people`，提单人→接单人）之上**，单独新增一行 `history-row__tip`。

> **位置结论（已确认）**：不放底部操作区（已挤），也不放操作行下方；紧邻"派单状态"最贴切——**放在所属项目下方、接单人流转上方**，与派单信息语义衔接（"派单结果"就挂在派单展示区上方）。单占一行，对移动端友好。

**结构示例（对应列表卡，插入位置见 ←）**：
```
┌────────────────────────────────────────────┐
│  缺陷 | 工单列表偶发点不进去 #600 2026/08/25 │
│  [指定处理人：张文星] 用户反馈工单列表点不... │
│  所属项目：摇人吧服务号                       │
│  [派单结果提醒：指派人存在同名，已为您选择…] │  ← 新增 history-row__tip（单独一行）
│  贾  贾爽 → 张  张文星                       │  ← task-card2__people（人员流转）
│  ------------------------------------------  │
│  [处理中][中]   [催办][上报][重派][撤回]      │  ← history-row__bottom（操作行）
└────────────────────────────────────────────┘
```

**交互规则**：
- **数据源**：同一 `GET /tasks` 列表项的 `redispatch_tip`（见 §4.1），无需额外请求。
- **渲染**：在 `所属项目` 行之后插入 `t.redispatch_tip ? <div className="history-row__tip">派单结果提醒：{t.redispatch_tip}</div> : null`；单行、限宽、超长 `text-overflow: ellipsis`。
- **样式（颜色区分，重点）**：提醒行**使用与卡片正文（灰）/蓝色强调均不同的警示色**，突出"需用户注意"——推荐**琥珀/橙黄**文字（如 `#B45309`/`var(--amber)`，非错误红），可配极浅警示底色与 ⚠ 小图标增强辨识；具体色值以设计规范为准，但**必须肉眼可辨区别于普通文本**。
- **点击**：列表整行本就可点击进详情，提醒行**跟随整行点击**即可（target 一致），无需单独绑定/特殊冒泡处理。
- **无提醒**：`redispatch_tip = null` → 不渲染该行，正常卡高度/间距。
- **文案前缀**：与气泡一致 `派单结果提醒：`。

## 四、数据与接口设计

### 4.1 接口契约（前后端对齐）

**核心决策（已确认）**：详情接口 `GET /tasks/{id}` 扩展一个 `redispatch` 子对象，一次调用同时承载 **R2 候选快照** 与 **R3 派单结果信息**，前端不必额外开请求；无快照/无日志时 `redispatch` 为 `null`，前端优雅降级。

| 接口 | 变更 | 说明 |
|---|---|---|
| `GET /tasks/{id}`（详情） | **扩展 `redispatch` 子对象** | 最主用接口：重派弹窗读 `candidates`（R2），重派轮询完成后读 `result`（R3 派单结果信息）。 |
| `GET /tasks`（列表） | **每项新增 `redispatch_tip`（string?）** | 气泡卡片单行提醒的直接数据源（见 §3.6）；轻量一句话摘要，超长前端省略 |
| `POST /tasks/{id}/re-dispatch` | 基本不变 | 请求体 `{ preferred_assignee(必填), remark(可选) }` 维持现状；异步重派（清 assigned_to + 发事件），**响应仍为 `TicketResponse`**（无需带 result），前端靠轮询详情拿最终结果。 |
| `GET /tasks/{id}/redispatch-candidates` | 保留（可选 M4） | （方案A）实时预演 Top10；可选 query `refresh=true`，仅在需要"刷新候选"时用。 |

#### `GET /tasks/{id}` 响应结构（`TicketResponse` + 新增 `redispatch`）

```jsonc
{
  // ...既有 TicketResponse 顶层字段（id/title/status/assigned_to/...）
  "redispatch": {                       // 最新一轮派单的完整评估（读 task_dispatch_log 最新一条）
    "dispatch_round": 2,
    "candidates": [                     // 【R2】本轮精排 Top10 快照（重派弹窗列表）
      {
        "rank": 1,
        "engineer_id": "1001",
        "name": "张三",
        "department": "智能规划研究院",
        "job_level": 1,
        "modules": ["调度USP:监控:路径规划"],
        "duty": "负责无人车调度规划与路径优化……",
        "scores": { "llm": 0.95, "semantic": 0.0, "history": 0.30, "total": 0.79 },
        "tags": ["项目对接人"]     // 可选：项目对接人标记
      }
    ],
    "result": {                          // 【R3】本轮派单结果信息（驱动提醒条）
      "assigned_id": "1001",
      "assigned_name": "张三",
      "preferred_id": "1002",            // 意向人（重派才有）
      "preferred_name": "李四",
      "confidence": 0.85,
      "decision_type": "auto",
      "reasoning": "……派单理由……",
      "profile": {                       // 被派人画像 + 完整性
        "dept": "智能规划研究院",
        "job_level": 1,
        "modules": ["调度USP:监控:路径规划"],
        "duty": "……",
        "missing": ["job_level"]          // 缺失字段（R4 补画像提醒用）；无缺失=空数组
      },
      "matched_pref": false,             // 是否派到意向人
      "name_collision": false,           // 是否同名命中（同名提醒）
      "pinyin_match": true               // 是否拼音近似名命中（近似名提醒）
    }
  }
  // 无任何派单记录（task_dispatch_log 空）时：redispatch = null
}
```

> **轮询判定升级**：前端重派完成后，改以 `redispatch.result` 是否出现（而非仅 `assigned_to_name`）判定派单完成，从而能直接生成派单结果提醒（画像/理由/同名/拼音提示）。
>
> **客户端渲染依赖**（派单结果各分支）：
> - `result.profile.missing` 非空 → 情况① 补画像提醒
> - `result.preferred_id && result.preferred_id !== result.assigned_id` → 情况② 未派到指定人 + reasoning + 转派引导
> - `result.name_collision` → 情况③ 同名提醒
> - `result.pinyin_match` → 情况④ 近似名提醒

### 4.2 数据落位（两个载体，职责分离）

本次引入**一个主载体** `task_dispatch_log`，与既有 `metadata_info` 各司其职：避免把结构化数据塞进异构 JSON 袋、也避免与重派的 `meta.pop(assign_*)` 清理逻辑互相踩踏。**不再给 `tasks` 新增字段**（候选快照与派单解释同轮内聚落入新表）。

**【R2 + R3】每一轮派单的完整评估 → 新表 `task_dispatch_log`（append-only，1:N）**
```
task_dispatch_log
├─ id             PK
├─ task_id        FK → tasks.id（索引）
├─ dispatch_round int         # 第几次派单/重派（自增）
├─ preferred_id   varchar?    # 本次意向人（重派必有；首次派单可能为 NULL）
├─ assigned_id    varchar      # 实际接单人 users.id
├─ confidence     float
├─ decision_type  varchar      # auto / recommend / fallback
├─ reasoning      text         # 派单理由
├─ profile        json         # 实际接单人画像 {dept, job_level, modules, duty, **missing**}
│                             #   missing: 该人画像缺失字段 [job_level, responsibility_modules, ...]（R4 提醒补画像用）
├─ candidates     json         # 【R2】本轮精排 Top10 快照
├─ matched_pref   bool         # 是否派到意向人（前端 R3 判定可用，或前端自行比对）
├─ name_collision bool         # 【R4】按姓名命中 >1 人即 true（与完整度是否可区分无关），派单结果同名提醒用
├─ pinyin_match   bool         # 【R4】本轮是否经"拼音/近似名"匹配命中，派单结果近似名提示用
└─ created_at     datetime
```

**首次派单也落库**：`task_dispatch_log` **每次派单（含首次）都写一条**——首次派单 `preferred_id=NULL`、`candidates` 写首次精排快照；这样重派弹窗才能读到"首次派单精排快照"作为 R2 候选列表数据源（`name_collision` 首次派单一般 false，重派才可能 true）。

> 数据来源：`name_collision` / `pinyin_match` 由 Step6/Step0 写入 `AssignmentResult`（见 §3.5），Worker 落库时原样搬运到此表。`profile.missing`、`candidates` 也由 Worker 在落库时一并写入。`matched_pref / preferred_id / assigned_id` 用于驱动"未派到指定人"（情况②）与同名（③）、近似名（④）提醒。

`profile.missing`（R4 画像完整性）：运行时比对 `EngineerProfile` 判定字段，缺失即列进 `missing`。**判定字段只含 `department` / `job_level` / `responsibility_modules` 三项**（`duty_text` 仅用于展示、**不参与完整性判定**）；其中 `responsibility_modules` **全空结构**（空 dict/list/None）才算缺失。前端据此生成"该接单人需补全：职级、责任模块…"提示。同名择人（D6b）按这 3 项命中数多→少排序，`missing` 越少（画像相对更完整）者优先派。

`candidates` 每项结构（与 R2 弹窗直接对应）：
```jsonc
{ "rank": 1, "engineer_id": "1001", "name": "张三",
  "profile": { "dept": "智能规划研究院", "job_level": 1,
                "modules": ["调度USP:监控:路径规划"], "duty": "..." },
  "scores": { "llm": 0.95, "semantic": 0.0, "history": 0.30, "total": 0.79 },
  "tags": ["项目对接人"] }
```

> 弹窗取数：`GET /tasks/{id}` 详情读 `task_dispatch_log` **最新一条**（`ORDER BY dispatch_round DESC LIMIT 1`），`candidates` → R2 列表，`assigned/profile/reasoning/confidence` → R3 派单结果信息。

**【既有】`tasks.metadata_info` 只保留重派意图键**：`preferred_assignee / preferred_assignee_remark`（+ 其它非派单元数据，如诊断/附件等）。**派单详情字段已从 `metadata_info` 移除**（`assignee_name/assignee_id/assign_confidence/assign_reasoning/assign_decision_type/assigned_at`，经核查全库无读取方，为冗余死数据）。完整画像、候选快照、派单理由/置信度/同名/拼音标记一律存 `task_dispatch_log`（append-only）。`task.py` 重派时 `meta.pop(assign_*)` 仅清理历史遗留的旧键，不再影响新逻辑。

### 4.3 边界与异常

| 场景 | 处理 |
|---|---|
| 倾向人在 Top10 之外 / 被过滤 | 列表仍把该人高亮标出（"倾向人未进候选"），交 LLM 协商（延续现有）
| 候选 < 10 人 | 有多少展示多少，排名保留
| 快照不存在（首版缺失/被清） | 退回现有 `UserSelect` 全量列表并提示
| 快照过时（B） | 标注"基于最近一次派单评估"；可选 M4 提供"刷新"走实时预演（A）
| 倾向人**未选**（非法） | **拒绝**并提示"请选择意向处理人"（R1 保持必填口径）；备注可空 |
| 派到**画像不完整**的人（R4 情况①） | 派单结果提醒该人需补全 `profile.missing` 列出的字段，不阻断派单 |
| 同名（多人命中） | 按 **D6b**：按画像完整度排序选人（`missing` 少者优先）；结构化带 id 直接用；完整度相同→**单轮 LLM** 在小集合内抉择，不静默取第一个 |
| 同名且完整度相同 | 两者 `missing` 相同（都完整/都缺同字段）→ **单轮 LLM** 结合工单上下文在 N 个同名人内选一，不静默、不走全量确认 |
| 姓名精确/包含**未命中** | 触发**拼音全拼**兜底匹配（D7）；拼音也未命中 → 走正常派单 |
| 拼音命中多人 | 复用 D6b 同名链路（画像完整度 → 单轮 LLM）；并提示"按拼音匹配"（`pinyin_match`） |
| Step0 指定人**无画像** | 仍直接指派（R4 不约束画像）；画像完整性仅用于派单结果提醒 |
| `task_dispatch_log` 无记录 | 派单结果提醒降级为仅显示当前 `assigned_to` 姓名（不展示画像/理由）
| `re-dispatch` 已拦截（指定处理人/非ai工单/无权限） | 保持既有拦截，不进入新弹窗

## 五、非功能考虑

- **成本**：预演接口（A）每次重派新增一次 L1 LLM 召回。重派为**低频动作**，可控；如预算敏感首版只做 B。
- **实时性**：重派必须实时，无强一致性要求；快照允许短暂滞后并明确标注。
- **兼容性**：所有新增字段均 optional，未启用时（无快照/无画像/未指定人）前端平滑降级，不破坏既有重派。
- **权限**：候选人/画像接口沿用任务级权限（与查看工单一致）。

| **D7** | 拼音/近似名匹配（同音近音错别字兜底） | ✅ **已定**：姓名精确/包含未命中时，**拼音全拼一致**即命中（`pypinyin`）；`confidence` 略降 **0.85**；只做全拼一致、不做编辑距离等激进模糊 | 捕捉"胡建楠→胡建南"类同音错别字；命中多人复用 D6b；拼音命中**必返回**"按拼音匹配、如非此人请更正"提示 |
