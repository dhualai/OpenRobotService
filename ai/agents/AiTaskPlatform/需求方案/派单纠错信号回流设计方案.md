# 派单纠错信号回流设计方案（转派 reassign → 派单学习）

> **状态**：草案 v0.1（2026-09-02，待评审）
> **范围**：`ai/agents/AiDiagnosisPlatform/assigner` 智能派单 + `backend` 转派(reassign)/重派(redispatch)链路 + `ai/core/retrieval.py` 知识沉降
> **目的**：把「处理人转派」这一人工纠错动作产生的信号（工单真实领域 + 谁才是正确处理人 + 转派原因）**反向喂给派单**，让 AI 越派越准。
> **对齐**：复用 `task_resolutions`（project domain）已验证的「验证回填 verified」机制，为派单历史 `dispatch_history` 建立等价的反馈修正通道。

---

## 一、背景与问题

### 1.1 现状：AI 派单不靠人工纠错自愈

AI 首次派单经常不准，人工补救有两条路：

| 补救方式 | 动作 | 现有信息 | 是否回流AI |
|---|---|---|---|
| **重新派单 redispatch** | 工单拧回 `new`，AI 重新推荐 | 用户在重派表单选倾向人 + 备注（`preferred_assignee` / `preferred_assignee_remark`） | ⚠️ 部分（Step6 作为 LLM 上下文，已实现） |
| **处理人转派 reassign** | 接单人直接把单转给另一人，并**必填转派原因** | 新处理人 + 原因（存成评论）、无原处理人 | ❌ **完全未利用** |

**核心痛点**：转派是最直接的「人工纠错」，它明确表达了——
> 「这个单子 **不该** 给原处理人 A（领域不符/不合适），**应该** 给新处理人 B（对的人），因为 **原因：xxx**」。

这笔宝贵的标注样本，目前：
1. 原因散落在**评论**里（`重新指派原因：xxx`），非结构化；
2. `TaskOperationLog` 只记 `new_assignee`，**没有原处理人、没有原因字段**；
3. **完全没有流入** `dispatch_history` / `responsibility_modules` 画像 / 历史召回。

### 1.2 价值洞察：转派 = 派单体系的「verified」反馈

参考 `ai/core/retrieval.py` 的两套知识沉降：

| 沉降通道 | Domain | 用途 | 是否有验证反馈 |
|---|---|---|---|
| `task_resolutions` | `project` | AI **诊断**检索历史方案 | ✅ **有**：`verified`（confirmed×1.15 / recurred×0.85 / rejected×0.70）回填加权 |
| `dispatch_history` | `dispatch` | AI **派单** L3-A 路按解决人聚人 | ❌ **无**：只记最终解决人，无纠错修正 |

**转派(reassign A→B) 在语义上等价于给派单历史打上 `rejected A` + `confirmed B`**，与 `task_resolutions` 的 verified 反馈完全同构。我们要做的，就是为派单历史补上这块缺失的反馈闭环。

---

## 二、目标与非目标

### 目标
1. **采集**：转派时完整、结构化地记录纠错信号（工单、原处理人、新处理人、原因、时间、判定领域）。
2. **沉降**：把纠错样本作为「强化样本」写入派单知识库，携带打标信息（新处理人=confirmed，原处理人=rejected）。
3. **回流**：历史召回（L3-A 路）召回时，对「被转派验证过的正确人」加权提权，让下次相似工单聚到对的人。
4. **可解释/可复盘**：能追溯「为什么给 B 加权重」（来自哪次转派、原因是什么）。

### 非目标（本期不做）
- 不让转派信号做过度的硬规则（如「只要转过就锁死给 B」）——保持「加权提示 + LLM 综合决策」主权。
- 不做实时在线学习（派单建议仍走「召回→精排→LLM」，沉淀用离线/事件驱动回填）。

---

## 三、总体方案

整体分三块，逻辑上是一个闭环：

```
【采集】转派/重派 → 结构化纠错样本（原人+新人+原因+领域）
   │
   ▼
【沉降】写入派单知识库 dispatch_history（新增 feed_type / from_assignee / reason / verified 字段）
   │
   ▼
【回流】L3-A 历史召回按 verified 加权（confirmed 提权 / rejected 降权）→ 精排 → LLM 决策
```

### 3.1 数据模型

#### 3.1.1 `TaskOperationLog`（backend，操作日志）——转派时补充结构化字段

在 `reassign` 分支（`backend/app/modules/tasks/api/task.py`）落库时，`detail` 从目前的 `{"new_assignee": id}` 扩为：

```json
{
  "new_assignee": "B",
  "from_assignee": "A",            // 原处理人（转派发生时的 task.assigned_to）
  "reason": "该领域不属于我，B 负责 XXX",   // 转派原因（必填，已从评论前置提取）
  "feedback_type": "reassign"      // 标记：reassign=处理人转派
}
```

**说明**：`from_assignee` 即转派发生前 `task.assigned_to`（原处理人）；`reason` 当前在前端作为评论提交，需在转派请求体中一并携带（见 §3.2）。

#### 3.1.2 新增派单纠错知识集合（Qdrant，复用 dispatch_history 或独立）

**采用「复用 `dispatch_history` + 扩展字段」为主，独立集合为备选**。理由：L3-A 路已经对 `dispatch_history` 聚合打人，复用可使纠错样本零改召回框架即被检索到。

在 `ai/core/retrieval.py::index_dispatch_history` 的 payload 增加字段：

```json
{
  // ……现有字段……
  "engineer_id": "B",              // ★ 新处理人（纠错后的正确人）——L3-A 聚人的核心
  "feed_type": "reassign",         // 样本类型：normal(普通历史) / reassign(转派纠错) / redispatch(重派纠错)
  "from_assignee": "A",            // 被否定的原处理人
  "reason": "……",                  // 转派原因
  "verified": "confirmed",         // ★ 参照 task_resolutions 的 verified：reassign=confirmed(新处理人)
  "rejected_id": "A"               // 被否定人（为 rejected 降权用）
}
```

> 备选（若担心混淆普通解决历史与纠错样本）：新建独立集合 `dispatch_feedback`，`retrieve_dispatch_history` 同时查两个集合并去重。**推荐先用复用方案跑通，独立集合作为扩展项。**

#### 3.1.3 （可选）新增 `task_reassign_feedback` 表（backend，关系型，供回填/复盘）

为稳妥落地「原处理人/新处理人/原因」的结构化审计与离线回填，建议新增一张 append-only 表（也可先不建表、直接存 Qdrant payload，二期再补表）：

```sql
CREATE TABLE task_reassign_feedback (
    id            BIGINT PRIMARY KEY AUTO_INCREMENT,
    task_id       BIGINT    NOT NULL,
    from_assignee VARCHAR(50) NOT NULL,   -- 原处理人 users.id
    to_assignee   VARCHAR(50) NOT NULL,   -- 新处理人 users.id
    reason        TEXT      NOT NULL,     -- 转派原因
    source        VARCHAR(20) DEFAULT 'reassign',  -- reassign / redispatch
    created_at    DATETIME  NOT NULL DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_task (task_id),
    INDEX idx_to   (to_assignee),
    INDEX idx_from (from_assignee)
);
```

## 五、正确标准与口径（关键决策）

1. **正确处理人 = 每次转派的新处理人（to_assignee）**（已与需求方确认）。
   - 不做「等工单最终关闭再覆盖」的延迟补标（保持实时），但 Qdrant 中若后续工单关闭由最终解决人沉底 `feed_type='normal'`，两类样本并存，靠 `feed_type` 区分、`verified` 权重共同作用。
2. **转派原因必填**（前端已保证），本方案把它从「评论文本」升级为「结构化字段」，供派单/复盘结构化使用。
3. **不做硬规则**：转派信号只通过 L3 历史召回加权 + LLM 上下文呈现，最终决策仍由「精排 + LLM」主权，避免误把一次性转派当成永久正确答案。

## 六、风险与权衡

| 风险 | 说明 | 缓解 |
|---|---|---|
| 转派≠领域归属 | 转派原因可能是「太忙/临时」，不一定是「领域不符」 | 用原因文本是否含领域线索 + 统计置信：同一 (领域→B) 多次转派才显著提权；单次仅轻加权 |
| 稀释普通历史 | 纠错样本与真实解决历史混在同一集合 | 用 `feed_type` 区分 + `verified` 权重分离，普通 `normal` 样本仍主导 |
| 重复/循环转派 | A→B→A 抖动 | 检测同工单内循环，避免重复写入造成噪音 |
| 历史数据无 reason | 存量 `TaskOperationLog` 无原因字段 | 从评论 `重新指派原因：` 前缀迁移回填（离线脚本），缺失则不产生纠错样本 |
| 实时性 vs 批次 | 事件驱动保持及时性 | 采集用事件触发，沉降可批处理（脚本兜底） |

## 七、验收建议

1. 构造一个「AI 首次派给 A、处理人转派给 B、原因含领域」的工单，验证：
   - `TaskOperationLog.detail` 含 `from_assignee / reason / feedback_type`；
   - `dispatch_history`（或 `dispatch_feedback`）出现 `feed_type='reassign'`、`engineer_id=B` 的样本；
   - 下次相似工单派单时，L3-A 路 B 的分数因 confirmed 加权而提升，A 因 rejected 降权。
2. 验证可解释性：精排/`TaskDispatchLog.reasoning` 能说明「B 因转派验证提权」。
3. 回归：对既有普通历史工单，确认 `feed_type` 默认 `normal`，原派单行为不回退。
