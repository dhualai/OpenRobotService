## 1. 虚线挂载（已确认）

| 项 | 口径 |
|----|------|
| 允许挂在 | 组织树或技能树上**任意已知节点**（含祖先，如只知公司） |
| `link_type=dotted` | 虚线；`source` 可为 `manual` / `inferred` / `synced_from_dept` |
| **Step1 hard** | **不进**。公司级虚线不得把全公司塞进候选池 |
| **Step3** | **可进**：展示「可能相关」；允许轻度加分，不得单独作为 hard 准入 |
| 升级 | 补全部门/组后改为 `solid`，或改挂到更具体节点 |

## 2. 两棵树 v1 范围（已确认）

### 2.1 同一套节点模型，两棵树实例

- 不限层数；每节点：`name` / `description` / `keywords[]` / 编制 `owners[]`
- 人与节点关系走**挂载表**（实线/虚线），不单靠节点 `owners`
- `tree_kind`：`org` | `skill`（不同 root，**禁止同一物理节点身兼两树**）

### 2.2 技能树 v1

- **迁移**现有「产品 → 界面 → 功能」`module_tree_nodes` 为技能树初始数据（深度约 3，可继续加深）
- keywords / anchor / engineers 迁入节点字段与挂载；派生 `module_keywords` 等仍由技能树生成
- 切法跟**用户可感知能力/界面功能**，不照抄组织层级、不按代码仓库目录切

### 2.3 组织树 v1

- 浅树起步：`公司 → 部门`（部门名对齐现有 `users.department` 及别名）
- 需要时再在部门下挂「组 / 产品单元」（解决一部门多产品）
- owners 可先空或从已知经理字段填；**存量 department 只作「建议挂载」**，一键采纳为实线，不静默当成唯一真相

### 2.4 「车端软件」双身份

- 组织树：`… → 某研究院 → 车端软件组`（编制）
- 技能树：一级或根下的 `车端软件`，下挂能力/故障域
- 两边用同名或 `linked_node_id` **弱关联**；不强制叶子一一对应

## 3. Step1 收紧（已确认）

| 项 | 口径 |
|----|------|
| 废弃 | 以 `dept_to_product` **一部门 → 单一产品** 作为唯一 hard 门闩的长期依赖 |
| 改为 | 用工单定位到的**组织节点**（或项目/组线索）→ 取该节点**子树内实线挂载**人作为候选池；能定位到组用组，否则用部门子树并集 |
| 无组织命中 | **不做**公司级一刀切收紧；交给 Step3 技能召回 + 后续步骤（与现行「过严误杀」权衡一致：宁可池子偏大，也不用错误产品 hard） |
| 技能树 | **不单独做 Step1 hard 踢人** |
| 画像准入 | 过渡期：无实线组织挂载 ≈ 画像缺口（tip / 降级策略与「责任模块不全」同类），用缺口清单逼运营补挂，而不是继续迷信旧 department 字符串 |

一部门多产品：组织树上「部门节点下多个组节点」，人实线挂到组；不再靠一张扁平映射表硬拆。

## 4. 派单主链（目标态摘要）

```
工单文本
  → 技能树命中（关键词 / 轻量分类，可多）
  → 组织树定位（项目/组线索；可空）
  → Step1：组织实线子树候选池（虚线不进）
  → Step3：技能命中节点 owners + 实线挂载人为主；虚线仅标记/轻加分
  → Step4–6：卡片同时展示组织 path + 技能 path
```

---

## 5. 交互原则（已确认方向）

1. 人/树页：按 `users.department` **高亮建议节点**，一键采纳实线  
2. 缺口清单：有 department 无节点 / 有人无挂载 / 节点无 owners  
3. 改挂载要轻（勾选/拖人）；复杂审批后置  
4. `users.department` / 旧 `responsibility_modules`：**引导导入 + 可改**，不再作为派单唯一真相
