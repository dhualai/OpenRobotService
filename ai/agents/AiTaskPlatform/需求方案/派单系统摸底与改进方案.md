# 派单系统摸底与改进方案

> **状态**：摸底基线（2026-08-27）
> **范围**：`ai/agents/AiDiagnosisPlatform/assigner` 智能派单全链路
> **目的**：逐环节确认每个环节"是否起作用、是否有益"，对标业界成熟方案，形成可执行改进清单。

---

## 一、结论速览

- 现有骨架「**三路召回 → 精排(加权) → LLM 综合决策**」是标准的 **Retrieve-Rank-Rerank** 形态，方向正确。
- 已做的两项关键修正（**关闭 L2 锚文本语义召回**、**移除负载均衡**）解决了暴露出的主要误派（产品经理被功能工程师压掉）。
- 仍有 **2 处"关键词/锚文本匹配"残留**（部门 R5、模块收紧）与 **1 个评价/回归体系缺失**，需按 P0/P1 处理。

| S6 | LLM 综合决策 | 高分取#1；低分触发 LLM 窗口重选 | 🔵 在用 | ✅ 与"尊重精排"一致 |

### 关键历史问题（本次排查实锤）

1. **config.yaml 曾缺失 `ranker_weights`**，导致实际用代码默认 `llm=0.30/semantic=0.35/history=0.10`，**锚文本语义权重(0.35)反超 LLM(0.30)**——这是"LLM 分最高的产品经理却派不准"的根因之一。
2. **负载均衡**：产品经理在途=8 → 总分被打到 0.14，跌出 Step6 决策窗口（top3），窗口里没有产品经理 → LLM 只能在算法工程师里选（LLM 原始输出都写明了"候选人列表中无产品设计模块负责人"）。
3. 修复后（关 L2 + 去负载均衡 + LLM 权重 0.85）：吴佳秀精排 **#1（0.833）**，进入决策窗口，需求单正确落在产品经理。

## 三、业界对标与借鉴（调研摘要）

调研范围：开源 ITSM 自动分派（Zammad/osTicket/Faveo/UVdesk）、LLM 路由（LangGraph/LlamaIndex router）、检索重排范式（Retrieve-Rank-Rerank）、SLO/技能矩阵/负载均衡最佳实践、派单评估体系。

**一句话结论**：业界共同指向——
> **确定性规则只做"资格/硬约束护栏"，LLM 做"决策主脑"，负载均衡永远只是"有资格多人里的软性 tie-breaker"。**

| # | 借鉴点 | 出处 | 落地到本架构 |
|---|---|---|---|
| A | 必达规则前置护栏（condition→action） | Zammad trigger / ITSM rule engine | 确定性"角色硬约束"（如必须产品经理）做候选/决策硬过滤，不过加权 |
| C | 为每个候选角色建语义 description + LLM 结构化选择 | LlamaIndex RouterQueryEngine | Step6 给 LLM 提供 `[角色, 职责语义描述, 证据]`，输出结构化 `(角色, 置信度, 理由)` |
| D | pre-filter + post-validator + HITL | LangGraph guardrails | 规则锁定的不交 LLM；LLM 低置信 → 人工确认队列 |
| E/F | 关键词/BM25 降级为"召回生成"，LLM 只处理小候选集 | Pinecone two-stage / RAG | 关键词只在召回用，不进精排主导分；LLM 决策只处理 top3~15 |
| G/H | 资格过滤 与 负载均衡 分层；唯一承接者保护 | Faveo / ITSM | 资格硬过滤独立于打分；候选数==1 时锁死并转升级/人工，不降级硬派 |
| I/J | 角色分桶评估 + golden set 回归 | 检索评估 | 按应派角色分桶看 precision@1/误派率；回归集纳入 automation |
| K | 反馈闭环 + LLM-as-judge 评测理由 | 生产级 agent 评测 | 记录承接人改派 + LLM 评"派单理由合理性"，回流评测集 |

## 五、评估指标体系建议

衡量"派单准不准"应分层：

- **离线指标**：`precision@1` / `accuracy@1`（最终派的角色=应派角色）、`recall@K`（应派角色是否在 top-K 内，防"关键词把 PM 挤出候选"）、`NDCG/MRR`（次级）、**角色级混淆矩阵**（必须按角色分桶，只看总精度会掩盖对非功能角色的不公平）。
- **在线/反馈闭环**：承接人**接受/改派率**（最真实信号）、解决时长与 SLO 违规率（误派会显著拖长）。
- **LLM-as-judge**：用更强 LLM 按"角色职责 rubric"评 `(工单, 系统理由, 应派角色)` 合理性；对**理由质量**的评估比只评"选对没"更稳定，更易暴露"表面匹配误导"（如理由是锚文本命中但角色职责不符）。
