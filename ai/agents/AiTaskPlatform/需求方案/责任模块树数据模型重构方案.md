# 责任模块树 · 数据模型重构方案（功能级行模型）

> 状态：方案定稿（待实施分阶段推进）
> 日期：2026-08-24
> 目标：让责任模块树满足**多人并发编辑**（改一个功能只影响该功能），并**去掉 config.yaml 责任树快照回写**，AI 派单改读"责任树内存缓存 + 热更新"。

---

## 1. 背景与问题

### 1.1 现状
- **存储**：`module_trees` 表**每产品一行**，`tree_json`(JSON) 存"产品→界面→功能"整棵树。用户在 `ModuleTreeManage` 前端编辑整棵树的**本地副本**，保存时**整体提交**。
- **写回**：保存后后端把整棵树写 DB，再 `export_to_config` 导出到 `ai/agents/AiDiagnosisPlatform/assigner/config/config.yaml` 的 `module_tree` 块，并通知 AI `reload`。
- **AI 读取**：`settings.py` 从 config.yaml 的 `module_tree` 派生 `module_classify / module_keywords / module_anchor_texts` 三套 map，供派单（semantic_recall / module_router / expertise_recall / product_keys 等）。

### 1.2 根因问题（多人并发覆盖）
- 多人同时编辑**同一产品的不同功能**时，由于存储粒度是"整棵产品 JSON"、前端整体提交，**后保存者用旧快照覆盖整棵产品树**，导致先保存者的修改丢失。
- 尝试用"节点级 merge + 功能级冲突检测"缓解，但整树 JSON 的 merge 逻辑复杂、易错（本次已发现前后端键名不一致 `changedFuncs` vs `changed_funcs` 导致节点级合并**从未真正生效**），且架构上无法彻底解决"单元格级"并发。

### 1.3 重构方向
把存储粒度降到**功能级行**：每功能一行。用户改一个功能 = 只更新那一行，**天然并发安全**（不同功能 = 不同行 = 互不干扰）。同时**去掉 config 快照回写**，AI 侧维护"责任树缓存"并热更新。

---

## 2. 目标数据模型

### 2.1 新表：`module_tree_nodes`（功能级行模型，**去除 key、用 id 定位**）

每行 = 一个"功能"的完整独立记录，含其在产品/界面下的归属。

> **关键决策（2026-08-25）**：去掉旧整树 JSON 时代的 `iface_key` / `func_key`，改用**数据库自增主键 `id`** 作为唯一定位。原因：AI 派单与用户画像**只用 name/keywords/anchor/界面名，不用 key**；且 key 由"中文名前两字拼音+hash"生成，**改名会让 key 漂移**，反而在行模型下制造"删旧行+插新行"的麻烦。改用 id 后，**功能改名/界面改名 = 只 update 那一行（或一组行）**，更简单。

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | int PK auto | **主键（唯一定位，前端编辑/审批都用它）** |
| `product` | varchar(64) | 产品名（如 调度USP / 摇人吧服务号） |
| `iface_name` | varchar(128) | 界面名（作为分组/展示键） |
| `iface_order` | int | 界面排列序号（决定聚合时界面顺序） |
| `func_name` | varchar(128) | 功能名 |
| `func_order` | int | 界面内功能排列序号 |
| `keywords` | JSON | **关键词数组（保留，与旧结构一致）** |
| `anchor` | TEXT | 功能描述/锚文本 |
| `engineers` | JSON | 负责工程师 id 数组 |
| `updated_at` | datetime | 最后更新时间 |

**唯一约束**：`(product, func_name)` 唯一（沿用现状"每功能名产品内唯一"语义，保证定位不歧义）。不建单独界面表：界面以 `iface_name` + `iface_order` 冗余在功能行上，读取时按 `product` 分组、`(iface_order, func_order)` 排序聚合回树。

### 2.2 旧表 `module_trees` 去留
- 过渡期**保留**，用于回滚/对比。
- 阶段 4 前端切换后、阶段 5 确认稳定后**删除**（含 tree_json 逻辑）。

### 2.3 派生结果（不变）
- `users.responsibility_modules`：仍由「功能行 → engineers」聚合出三层 `{产品:{界面:[功能]}}`，**结构不变**（AI 派单/前端 UserManage 依赖）。
- AI 三套 map（module_classify / module_keywords / module_anchor_texts）：仍由树结构派生（改数据来源，见 §4）。

### 2.4 补充要点（查漏后新增）
1. **排序字段**：`iface_order` / `func_order` 承载界面与功能的排列序，聚合时决定树顺序。新增界面/功能时分配 order（取当前 max+1）；**前端若未来加"拖拽排序"**，走批量更新 order 的专用接口。
2. **界面改名落行**：改界面名 = 一个事务内批量 `UPDATE` 该界面下所有功能行的 `iface_name`（保留 `iface_order` 不变），避免出现"新旧界面并存"。
3. **定位用 `id`，不再有 key 漂移**：前端编辑/审批用行 `id` 定位；`func_name` 仅作展示与业务名。**功能改名 = 只 update 该行（改 func_name/keywords/anchor/engineers）**，不受 key 影响；界面改名同理只改 iface_name。
4. **产品内功能名唯一**：`(product, func_name)` 唯一约束，保证"同一产品下同名功能"不歧义（跨界面仍可达，界面仅属分组/展示）。
5. **迁移（旧整树 → 行）**：逐个功能拆成行，`func_name`/`iface_name` 取旧树中的 name；`id` 由迁移自增生成；旧 `func_key`/`iface_key` **不迁移**（任务会用 func_name 定位），但若线上有审批单已引用旧 key，需在迁移时把审批单的定位改为 `func_name`（或标注旧审批单作废）。

## 3. 后端改造

### 3.1 模型层
- 新增 `backend/app/models/module_tree_node.py`：`ModuleTreeNode` ORM（列见 §2.1，去掉 key）。
- `backend/app/models/__init__.py`：注册。
- **新增 alembic 迁移**（`module_trees` 无迁移，需为新表建 `upgrade`：`create_table('module_tree_nodes')` + `(product, func_name)` 唯一约束）。
- 视需要：`module_tree_edits` 审批单的定位字段由 `iface_key/func_key` 改/兼容为 `func_name`（或按 id 存储，见 §3.3）。

### 3.2 service 层（`module_tree_service.py` 重写核心）
读取（聚合为树，供后端 API & AI 用）：
- `get_all_trees() -> {产品:{interfaces:[...]}}`：从 `module_tree_nodes` 查询，按 `product` 分组、`(iface_order, func_order)` 排序，聚合回 `interfaces[]` / `functions[]` 结构（**返回结构与旧 API 完全一致，前端阶段 2/3 无感**）。

保存（按功能行 upsert，天然并发安全）：
- 前端每"改一个功能"提交 **单功能变更** `{id, product, iface_name, func_name, keywords, anchor, engineers}` → 后端按 `id` upsert（`id` 存在则 update，否则 insert）；`id` 由后端分配（新增时返回给前端）。
- 界面级操作（新增/删除/改名界面）→ 拆成对该界面下所有功能行的批量 update / delete；或单独处理界面 order。
- 删除功能 → `delete` 该行（按 id）。
- 删除产品 → `delete product=...` 所有行。

同步：
- `sync_to_user_profiles`：基于新行聚合的三层画像回写（**逻辑保留**，读数据源改为行表聚合）。
- `export_to_config` / `_ASSIGNER_CONFIG_PATH`：**删除**（不再回写 config.yaml 的责任树；config.yaml 其余配置照旧，仅移除 `module_tree` 块）。

### 3.3 API 层（`module_tree.py`）
- **兼容过渡**：`GET /module-tree/`、`GET /products`、`GET /func-hashes`、`GET /candidates`、`GET /permission` 返回结构不变。
- `PUT /module-tree/`：
  - 阶段 2：仍接收旧整体提交，但后端内部改为「按功能差异写行表」——可继续兼容旧前端（或直接切换新前端）。
  - 阶段 4 起：改为接收**单功能操作**（新增/更新/删除节点），彻底去掉 per_product/merge/force/冲突检测。
- **新增读接口**（AI 用）：`GET /module-tree/export`（或复用 `GET /`），返回聚合后的完整树，供 AI 拉取缓存。
- 审批单（submit-edit/edits/approve/reject）：定位改为**按行 `id`**（或按 `(product, func_name)`），`apply_function_change` 由按 iface_key/func_key 改为按 id 应用；原审批单系列**当前前端未接入**，维持后端可用即可。

## 4. AI Assigner 改造（去 config 快照 → 缓存 + 热更新）

### 4.1 读取路径
- 移除 `settings._build_from_tree(config_md)` 与 config.yaml 的 `module_tree` 依赖。
- 新增：AI 通过**后端读接口**拉取责任树（启动时 + reload 时），在内存构建 `module_tree / module_classify / module_keywords / module_anchor_texts`。
  - 实现一个 `_load_module_tree() -> {产品:{interfaces:...}}`：`GET` 后端 `/module-tree/export`（带 AI 侧 token / 内网调用）。
  - `_build_from_tree` 逻辑**复用**（从树结构派生三套 map），仅数据来源由 config 改为后端接口。

### 4.2 热更新与缓存
- `AssignerConfig.reload()`：拉取最新责任树并重建三套 map。
- **缓存刷新策略**：
  - 责任树不大（几十~几百功能），**每次保存/reload 全量拉取+重建**三套 map 即可（代价小、无增量一致性负担）。
  - 初始化时机：AI 进程启动时 `ensure_dispatch_ready()` → 首次构建时拉取；保存后由后端 `POST /reload` 触发刷新。
  - 刷新失败则**保留旧缓存**并告警（不因一次性拉取失败而清空派单数据）。
- `dispatch_flow.reload_config()`：`self._config.reload()` + 失效 semantic/history/expertise 缓存 + **补失效 personnel（工程师画像）缓存**（现状缺失，树保存后 users.responsibility_modules 有 600s TTL 缓存，需在此失效，否则派单滞后最多 10 分钟）。
- 后端保存成功 → 仍调 `POST /api/ai/assigner/reload`。

### 4.3 config.yaml
- 移除 `module_tree:` 顶级块及其派生（手工三套 map 本就为空，无需处理）。
- 若后端 `export_to_config` 删除后，config.yaml 不再被后端写责任树；AI 侧不再读该块。
- 派生数据：三套 map 完全改为运行时由后端接口数据生成。

## 5. 前端改造

### 5.0 前端如何"组织这些行"（关键释疑）

**前端完全不感知"行模型"，永远操作后端聚合好的"产品→界面→功能"树。**

```
产品（摇人吧服务号）
 └─ 界面 A（我要摇人）      ← iface_order 决定排序
     ├─ 功能 a（AI对话）      ← 每功能 = module_tree_nodes 的一行，func_order 决定排序
     ├─ 功能 b（提单）
     └─ ...
 └─ 界面 B（系统任务）
     └─ ...
```

- **读**：`GET /module-tree/` 仍返回 `{产品:{interfaces:[{key,name,functions:[{key,name,keywords,anchor,engineers}]}]}}`。后端从行表 `SELECT` 后，按 `iface_order → func_order` 排序，在**内存聚合回树**。→ `ModuleTreeManage` 的界面折叠 / 功能列表 / `MindmapView` 的 SVG 总览**结构与现在完全一致，展示层零改动**。
- **写**：用户在树上**编辑某个功能**（改名/关键词/锚/工程师），前端把"这一个功能"连同其产品/界面/位置提交（单功能接口）→ 后端 `UPDATE` 那一行。**「在界面上看到的仍是树，但落库是行」**——并发安全由行保证，前端无需任何 merge/冲突逻辑。

**结论**：可视化组织结构 = 保持现状的"产品→界面→功能"树；变化的只是**保存在后端的物理粒度**（行）与**提交的动量**（单功能而非整树）。

### 5.1 `ModuleTreeManage.tsx`（阶段 4 重点）
- 数据读取：仍 `GET /module-tree/` 拿聚合树（结构不变，展示层基本不动）。
- **编辑模型改为单功能行**：用户编辑"一个功能"（改名/关键词/锚/工程师）→ 调用**单功能保存接口**（新 API），不再维护 `dirtyProducts/perProduct/func_hashes/forceProducts` 整树状态。
- 删掉：整树提交、节点 merge 意图、功能级冲突弹窗、`markFuncChanged` 等复杂度。
- 新增界面 / 改界面名 / 删功能 / 删界面 → 对应单操作接口（批量 UPDATE 该界面下各行 / 删除行）。
- 移除对 `func-hashes` 的依赖（功能级并发已由"行"天然保证，无需哈希比对）。
- 保留：顶部保存栏、Ctrl+S、自动保存与否维持现状（本次已取消自动保存，仅手动）。

### 5.2 `MindmapView.tsx`
- 仍消费 `{interfaces:[{functions:[...]}]}` 结构（聚合后不变），**无需改动**。

### 5.3 `UserManage.tsx`
- `normalizeRm` 消费 `users.responsibility_modules` 三层结构，**不变**。

## 6. 分阶段实施计划（每阶段可验证、可回滚）

| 阶段 | 内容 | 交付/验证 | 风险 |
|---|---|---|---|
| **P1** | 新增 `module_tree_nodes` 表 + 模型 + alembic 迁移；写**迁移脚本**把现有 `module_trees.tree_json` 拆行灌入 `module_tree_nodes`（幂等）。旧表保留。 | 新表数据 = 旧表；SQL 校验行数/内容。 | 低 |
| **P2** | 后端 service 重写：读聚合（返回结构与旧API一致）+ 按功能行 upsert；`PUT` 兼容旧前端整体提交（内部转行写）但改为行模型；同步画像保留。**验证：单功能编辑、A/B 改不同功能各存各的。**
 **P2 旧前端兼容策略**：旧前端仍发整体树。后端 `save_trees` 收到后：
 1. 以新行表当前状态为基准，与提交树做**功能级 diff**（按 `(product, func_name)`）：提交有而 DB 无 → insert；均有且内容变 → update；DB 有而提交无**且**非用户显式删除 → 忽略（不删，因旧快照缺失不代表删除，避免误删）。
 2. 显式删除（removed 产品/功能）→ delete 对应行。
 3. 这样即使旧前端整树提交，也只落差异行——**不同功能依旧各自保存不互覆盖**，为 P4 前端切单功能打底。 | 旧前端不改也能用，且并发安全。 | 中 |
| **P3** | AI：新增 `_load_module_tree()` 走后端读接口构建缓存；reload 失效 personnel 缓存；删除 `export_to_config` 及 config.yaml 责任树块。**验证：保存树后 AI 派单仍正常。（保留旧 `module_trees` 回滚。）** | AI 派单不依赖 config 责任树。 | 高（AI 核心） |
| **P4** | 前端 `ModuleTreeManage` 改为"单功能行"编辑与保存，移除整树提交/merge/冲突弹窗。**验证：编辑体验正常、并发天然安全。** | 前端彻底简化。 | 中 |
| **P5** | 清理：删旧 `module_trees` 逻辑/表、seed 反向脚本、config 责任树残留、遗留调试日志；压测与回归。 | 干净收尾。 | 低 |

> 注：P2 可先行修复当前已确认的**前后端键名不一致（changedFuncs vs changed_funcs）**这一紧急 bug（在重构 P2 落地前，先让现有节点级合并至少能部分生效），避免线上继续存在"改不同功能丢数据"。
